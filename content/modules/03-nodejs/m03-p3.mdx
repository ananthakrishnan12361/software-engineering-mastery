<TopicSection id="m03-p3-sec-a" letter="A" title="Topic Introduction">

#### What is this?

A production backend is exposed to the public internet, where every incoming HTTP request is untrusted until verified. Backend security combines **identity & access control** (**Authentication**, **JWT**, **Refresh tokens**, **Session management**, **Authorization**, **RBAC**, **OAuth fundamentals**) with **perimeter & data-layer defenses** (**Rate limiting**, **CORS**, **Security**, **Input sanitization**, **SQL injection**, **NoSQL injection**, **API security**).

#### Why does it exist & what problem does it solve?

Weak token verification (`alg: "none"`), missing refresh-token revocation, broken object-level authorization (BOLA/IDOR), permissive `CORS` with credentials, unthrottled login endpoints, and string-concatenated SQL or raw MongoDB query objects are the top root causes of real-world data breaches.

#### Where is it used in real-world software?

Every SaaS backend, fintech API, healthcare portal, and OAuth2 identity provider enforces these layers at the API gateway, Express middleware, and database query boundary.

</TopicSection>

<TopicSection id="m03-p3-sec-b" letter="B" title="Fundamentals (Simple Mental Models)">

<TopicAnchor id="m03-p3-topic-authentication" />

#### 1. Authentication: Proving Identity & Hashing Passwords Properly

**Authentication (AuthN)** verifies *who* a caller is using passwords, passkeys (WebAuthn), API keys, or federated OAuth2/OIDC tokens. Never store plaintext or fast-hashed (`MD5`/`SHA-256`) passwords—always hash with a memory-hard adaptive KDF (**Argon2id** or **`scrypt`** / `bcrypt`) and per-user random salt.

Compare secret API keys, webhook HMAC signatures, and session hashes using constant-time comparison (`crypto.timingSafeEqual`) so attackers cannot leak secrets byte-by-byte via response timing side channels.

<TopicAnchor id="m03-p3-topic-jwt" />

#### 2. JWT (JSON Web Tokens): Signed Claims, Not Encrypted Secrets

A **JWT** (`header.payload.signature`) is a compact **signed** token (JWS), **not encrypted**—anyone holding the token can Base64Url-decode the header and payload, so never put passwords, PII, or secrets inside JWT claims.

Always verify the signature against an explicit expected algorithm allowlist (e.g., `["RS256"]` or `["EdDSA"]`, rejecting `alg: "none"` and HMAC key-confusion), and validate `exp` (short TTL like 5–15 min), `iss`, and `aud` on every request.

<TopicAnchor id="m03-p3-topic-refresh-tokens" />

#### 3. Refresh Tokens: Rotation & Reuse Detection

Because short-lived access JWTs cannot be easily revoked mid-TTL without a central lookup, **refresh tokens** (long-lived opaque random tokens stored hashed in Redis/DB and delivered in `HttpOnly; Secure; SameSite` cookies) mint fresh access tokens.

Use **Refresh Token Rotation with Reuse Detection**: every `/auth/refresh` call issues a new refresh token and invalidates the old one. If an already-used refresh token is presented again (indicating theft), revoke the entire **token family** immediately and force re-login.

<TopicAnchor id="m03-p3-topic-session-management" />

#### 4. Session Management: Stateful Server Sessions vs. Stateless Tokens

**Session management** tracks authenticated user state across requests. **Stateful sessions** store a random opaque session ID in an `HttpOnly` cookie backed by Redis/DB—allowing instant server-side revocation on logout, password reset, or suspicious IP changes.

Whether using stateful sessions or short-lived JWTs + rotating refresh tokens, always regenerate session IDs after login (preventing **session fixation**), bind idle and absolute timeouts, and invalidate active sessions on password change.

<TopicAnchor id="m03-p3-topic-authorization" />

#### 5. Authorization: Stopping Broken Object-Level Access (BOLA / IDOR)

**Authorization (AuthZ)** answers *what an authenticated caller is allowed to do*. The #1 API vulnerability in OWASP API Top 10 is **BOLA (Broken Object-Level Authorization / IDOR)**—where User A requests `GET /orders/999` (belonging to User B) and the server checks login (`401`) but forgets to verify ownership.

Always scope database queries by the authenticated tenant/owner (`WHERE id = $1 AND user_id = $2`), never trusting a `userId` or `tenantId` supplied in `req.body` or `req.params`.

<TopicAnchor id="m03-p3-topic-rbac" />

#### 6. RBAC: Roles, Permissions & Principle of Least Privilege

**Role-Based Access Control (RBAC)** decouples endpoints from hardcoded role strings (`if (role === "admin")`) by mapping **Users -> Roles -> Fine-grained Permissions** (e.g., `editor` grants `["post:read", "post:write"]`, while `admin` adds `["post:delete", "user:invite"]`).

Check **permissions** (`requirePermission("invoice:approve")`) at route middleware and combine RBAC with **ABAC** (attribute checks like `invoice.tenantId === user.tenantId`) so a tenant admin can never approve another company's invoices.

<TopicAnchor id="m03-p3-topic-oauth-fundamentals" />

#### 7. OAuth Fundamentals: Delegated Authorization, PKCE & OIDC

**OAuth 2.0** delegates *authorization* (letting App A access your Google Drive via scoped `access_token`s without sharing your password), while **OpenID Connect (OIDC)** adds an `id_token` on top for *authentication*.

Modern SPAs and mobile apps must use the **Authorization Code Flow with PKCE** (Proof Key for Code Exchange) and a random **`state`** parameter (validated on callback to stop CSRF)—never the deprecated Implicit Flow (`response_type=token`) that leaks tokens in URL fragments.

<TopicAnchor id="m03-p3-topic-rate-limiting" />

#### 8. Rate Limiting: Protecting Endpoints From Brute Force & DoS

**Rate limiting** caps request frequency per IP, user ID, or API key using algorithms like **Token Bucket** (allows short bursts while enforcing steady average rate) or **Sliding Window Counter** backed by Redis for multi-instance consistency.

Apply stricter limits on expensive or sensitive routes (`/auth/login`, `/auth/forgot-password`, `/exports`), and return **`429 Too Many Requests`** with standard `Retry-After` and `RateLimit-*` headers.

<TopicAnchor id="m03-p3-topic-cors" />

#### 9. CORS: Browser Same-Origin Exceptions Without Wildcard Traps

**CORS (Cross-Origin Resource Sharing)** is a browser-enforced policy allowing origin `app.example.com` (over HTTPS) to read responses from `api.example.com` only when the server returns matching `Access-Control-Allow-Origin` headers (and handles `OPTIONS` preflight requests).

Never combine **`Access-Control-Allow-Origin: *`** with **`Access-Control-Allow-Credentials: true`** (browsers block it, and dynamically reflecting arbitrary `Origin` headers without an exact allowlist opens every authenticated endpoint to cross-origin theft!). Remember also: CORS only restricts *browsers*, never `curl` or server-to-server scripts.

<TopicAnchor id="m03-p3-topic-security" />

#### 10. Security: Defense-in-Depth & HTTP Security Headers

Backend **security** layers controls so no single failure compromises the system: enforce TLS/HTTPS (`Strict-Transport-Security`), set defensive headers via **`helmet`** (`X-Content-Type-Options: nosniff`, `Content-Security-Policy`, `Referrer-Policy`), run `npm audit` / lockfiles, and run containers as non-root with least-privilege DB credentials.

Keep secrets (`JWT_PRIVATE_KEY`, DB passwords) in a secret manager or runtime environment—never committed to Git or logged in errors.

<TopicAnchor id="m03-p3-topic-input-sanitization" />

#### 11. Input Sanitization: Validation First, Context-Aware Escaping

**Input sanitization** cleans or normalizes untrusted strings *after* strict schema validation: trim whitespace, strip null bytes (`\0`) and ASCII control characters, enforce allowlists on filenames/URLs, and sanitize rich HTML with a maintained parser like **DOMPurify** if HTML is ever required.

Avoid naive regex stripping (e.g., `str.replace("<script>", "")` fails on `<scr<script>ipt>`) and avoid vulnerable nested-quantifier regexes that cause **ReDoS** (Regular Expression Denial of Service).

<TopicAnchor id="m03-p3-topic-sql-injection" />

#### 12. SQL Injection: Parameterized Queries & Identifier Allowlists

**SQL Injection (SQLi)** occurs when untrusted input is concatenated into a SQL string (`"SELECT * FROM users WHERE email = '" + email + "'"`), letting `' OR 1=1 --` hijack the query structure.

The universal defense is **parameterized queries / prepared statements** (`db.query("SELECT id, email FROM users WHERE email = $1", [email])`), where the database driver sends SQL structure and data values separately. Because parameters cannot bind column or table names (`ORDER BY $1`), validate dynamic sort columns against an explicit **allowlist** (`Map`/`Set`).

<TopicAnchor id="m03-p3-topic-nosql-injection" />

#### 13. NoSQL Injection: Blocking Operator Objects & `$where` Execution

**NoSQL Injection** hits document databases like MongoDB when Express parses JSON/query strings into objects containing query operators: `{ email: { $ne: null }, password: { $ne: null } }` bypasses naive `findOne({ email: req.body.email, password: ... })` checks!

Always validate inputs to primitive `string`/`number` types with strict schemas (rejecting nested objects where a string is expected), strip keys starting with `$` or containing `.`, and disable server-side JavaScript operators like `$where`.

<TopicAnchor id="m03-p3-topic-api-security" />

#### 14. API Security: Complete OWASP API Defense Checklist

**API security** ties every backend layer together: enforce strong AuthN and object-level AuthZ (BOLA), validate schemas strictly to block mass assignment, cap payload sizes and pagination `limit`s, rate-limit per tenant/IP, enforce exact-origin CORS allowlists, and use parameterized DB queries.

Continuously monitor `401`, `403`, and `429` anomaly spikes with structured logs (never logging raw tokens or PII), and verify security invariants automatically in CI integration tests.

</TopicSection>

const scryptAsync = promisify(crypto.scrypt);

export async function verifyPasswordScrypt(password: string, saltHex: string, expectedHashHex: string): Promise<boolean> {

#### Example 2: Rotating Refresh Token Store With Reuse Detection (`createRefreshTokenStore`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models refresh token rotation + automatic family revocation on stolen token replay
function createRefreshTokenStore() {
  const tokens = new Map(); // tokenId -> { familyId, userId, used: boolean }
  const revokedFamilies = new Set();
  let seq = 0;

  return {
    issueInitial(userId) {
      if (typeof userId !== "string" || !userId.trim()) throw new TypeError("userId required");
      const familyId = "fam_" + (++seq);
      const token = "rt_" + (++seq);
      tokens.set(token, { familyId, userId, used: false });
      return { token, familyId };
    },
    rotate(token) {
      if (typeof token !== "string" || !tokens.has(token)) {
        return { ok: false, reason: "Unknown refresh token" };
      }
      const record = tokens.get(token);
      if (revokedFamilies.has(record.familyId)) {
        return { ok: false, reason: "Session family revoked" };
      }
      if (record.used) {
        // Replay detected: revoke the entire family immediately
        revokedFamilies.add(record.familyId);
        return { ok: false, reason: "Token reuse detected; family revoked" };
      }
      record.used = true;
      const nextToken = "rt_" + (++seq);
      tokens.set(nextToken, { familyId: record.familyId, userId: record.userId, used: false });
      return { ok: true, token: nextToken, familyId: record.familyId };
    },
    isFamilyActive(familyId) {
      return !revokedFamilies.has(familyId);
    }
  };
}

const store = createRefreshTokenStore();
const init = store.issueInitial("usr-1");
const rot1 = store.rotate(init.token);
const replay = store.rotate(init.token); // attacker replays old token!
console.log("Rotated ok?", rot1.ok, "| Replay blocked?", !replay.ok, "| Family active?", store.isFamilyActive(init.familyId));`}
/>

<CodeBlock

function createRateLimiter({ capacity, refillPerMs }) {
  if (!Number.isInteger(capacity) || capacity < 1) throw new TypeError("capacity must be integer >= 1");
  if (typeof refillPerMs !== "number" || !Number.isFinite(refillPerMs) || refillPerMs <= 0) {
    throw new TypeError("refillPerMs must be positive finite number");
  }
  const buckets = new Map();

  return {
    allow(key, nowMs) {
      if (typeof key !== "string" || !key.trim()) throw new TypeError("key required");
      if (typeof nowMs !== "number" || !Number.isFinite(nowMs) || nowMs < 0) throw new TypeError("invalid nowMs");
      const entry = buckets.get(key) || { tokens: capacity, lastMs: nowMs };
      const elapsed = Math.max(0, nowMs - entry.lastMs);
      const refilled = Math.min(capacity, entry.tokens + elapsed * refillPerMs);
      if (refilled < 1) {
        buckets.set(key, { tokens: refilled, lastMs: nowMs });
        return { allowed: false, retryAfterMs: Math.ceil((1 - refilled) / refillPerMs) };
      }
      buckets.set(key, { tokens: refilled - 1, lastMs: nowMs });
      return { allowed: true, remaining: Math.floor(refilled - 1) };
    }
  };
}

function evaluateCors(origin, allowlist) {
  if (!(allowlist instanceof Set)) throw new TypeError("allowlist must be a Set");
  if (!origin) return { allow: true, headers: {} }; // non-browser / same-origin
  if (origin === "null" || !allowlist.has(origin)) {
    return { allow: false, status: 403 };
  }
  return {
    allow: true,
    headers: {
      "Access-Control-Allow-Origin": origin,
      "Access-Control-Allow-Credentials": "true",
      Vary: "Origin"
    }
  };
}

const limiter = createRateLimiter({ capacity: 2, refillPerMs: 0.001 });
console.log("Req 1:", limiter.allow("ip:1", 1000).allowed, "| Req 2:", limiter.allow("ip:1", 1000).allowed, "| Req 3:", limiter.allow("ip:1", 1000).allowed);
const origins = new Set(["https:" + "//app.acme.dev"]);
console.log("CORS null origin blocked?", !evaluateCors("null", origins).allow, "| Evil blocked?", !evaluateCors("https:" + "//evil.dev", origins).allow);`}

const SORT_COLUMNS = new Map([
  ["createdAt", "created_at"],
  ["totalCents", "total_cents"]
]);

function buildOrderSearchSql({ tenantId, status, sortBy = "createdAt" }) {
  if (typeof tenantId !== "string" || !tenantId.trim()) throw new TypeError("tenantId required");
  if (typeof status !== "string" || !status.trim()) throw new TypeError("status required");
  const column = SORT_COLUMNS.get(sortBy);
  if (!column) throw new RangeError("Unsupported sort column: " + sortBy);
  return {
    sql: "SELECT id, status, total_cents FROM orders WHERE tenant_id = $1 AND status = $2 ORDER BY " + column + " DESC",
    params: [tenantId.trim(), status.trim()]
  };
}

function sanitizeNoSqlFilter(input, allowedFields) {
  if (!input || typeof input !== "object" || Array.isArray(input)) {
    throw new TypeError("Filter must be a plain object");
  }
  const safe = Object.create(null);
  for (const field of allowedFields) {
    if (!Object.hasOwn(input, field)) continue;
    const val = input[field];
    if (typeof val !== "string" && typeof val !== "number" && typeof val !== "boolean") {
      throw new TypeError("Disallowed non-primitive filter value for " + field);
    }
    safe[field] = val;
  }
  return safe;
}

console.log("SQL:", buildOrderSearchSql({ tenantId: "t-1", status: "paid' OR 1=1--", sortBy: "totalCents" }));
console.log("Safe NoSQL:", sanitizeNoSqlFilter({ email: "a@b.dev", extra: 1 }, ["email"]));`}

<TopicSection id="m03-p3-sec-e" letter="E" title="Step-by-Step Walkthrough">

Trace **`createRefreshTokenStore`** (**Example 2**) when a refresh token is stolen and replayed:

1. **Initial Login (`issueInitial`):** Creates `fam_1` and returns `rt_1` (`used: false`).
2. **Legitimate Refresh (`rotate("rt_1")`):** Marks `rt_1.used = true` and issues `rt_2` in the same family `fam_1`.
3. **Attacker Replays `rt_1`:** `rotate("rt_1")` sees `record.used === true`, adds `fam_1` to `revokedFamilies`, and rejects with `"Token reuse detected; family revoked"`.
4. **Immediate Containment:** Even `rt_2` (the legitimate user's current token) now fails with `"Session family revoked"`, forcing clean re-authentication.

</TopicSection>

<TopicSection id="m03-p3-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Eliminating BOLA / IDOR Across a Multi-Tenant Billing API

**Problem:** An endpoint `GET /v1/invoices/:id` checks `req.user` (valid JWT) and queries `WHERE id = $1`, allowing any authenticated customer to download another company's PDFs by incrementing invoice IDs.

**Production Solution:** Enforce both RBAC permission (`requirePermission("invoice:read")`) and tenant scoping inside every SQL query (`WHERE id = $1 AND tenant_id = $2` using `req.user.tenantId` from the verified token, never `req.query.tenantId`).

#### Scenario 2: Stopping Credential Stuffing & MongoDB Operator Injection on `/login`

**Problem:** Attackers send `{ email: { $ne: null }, password: { $ne: null } }` and hammer `/login` at 2,000 req/s.

**Production Solution:** Put a strict Redis token-bucket rate limiter (`429` + `Retry-After`) in front of `/login`, validate `email` and `password` strictly as non-empty `string` primitives before querying, and verify passwords via `scrypt`/`Argon2id` + `timingSafeEqual`.

</TopicSection>

<TopicSection id="m03-p3-sec-g" letter="G" title="Common Mistakes">

- **Accepting `alg: "none"` or skipping `iss`/`aud`/`exp` checks in JWT verification:** Allows forged tokens to pass authentication.
- **Putting sensitive PII or roles without re-checking DB state on critical mutations:** Stale JWT claims stay valid until `exp` expires.
- **Reflecting any `req.headers.origin` in `Access-Control-Allow-Origin` with `Allow-Credentials: true`:** Lets any malicious website read authenticated API responses.
- **Concatenating `ORDER BY ${req.query.sort}` into SQL strings:** Opens SQL injection even when `WHERE` clauses are parameterized.
- **Passing unvalidated `req.body` objects directly to MongoDB `findOne()`:** Enables `$ne`/`$gt`/`$regex` NoSQL operator injection.

</TopicSection>

<TopicSection id="m03-p3-sec-h" letter="H" title="Best Practices">

- **Hash passwords with `Argon2id` or `scrypt`**, and compare secrets/HMACs with `crypto.timingSafeEqual`.
- **Keep access JWTs short-lived (5–15 min)** and back long sessions with rotating `HttpOnly; Secure; SameSite` refresh tokens + reuse detection.
- **Enforce RBAC + object ownership (`tenant_id`/`user_id`)** in the service/repository query layer on every endpoint.
- **Use `helmet` security headers**, parameterized SQL + sort allowlists, strict primitive schemas for NoSQL, and token-bucket rate limits on auth routes.

</TopicSection>

<TopicSection id="m03-p3-sec-i" letter="I" title="Performance & Scalability">

- **Stateless JWT Verification vs. Session Store Lookups:** Verifying an `EdDSA`/`RS256` JWT takes microseconds in CPU without a Redis round-trip per request, while Redis-backed refresh/revocation lists only get hit on refresh or sensitive account changes.
- **Distributed Rate Limiting:** Store rate-limiter buckets in **Redis** (using atomic Lua scripts or sorted sets) rather than in-process `Map`s once you scale beyond 1 Node instance.
- **`scrypt` / `Argon2id` Offload:** Memory-hard password hashing is intentionally CPU-expensive (~50–100ms); keep concurrency bounded or run in `worker_threads` so login bursts do not starve the event loop.

</TopicSection>

<TopicSection id="m03-p3-sec-j" letter="J" title="Security Considerations">

- **OAuth2 PKCE + `state`:** Always enforce PKCE (`S256`) and verify a cryptographic `state` parameter on OAuth callbacks to block authorization-code interception and login CSRF.
- **Never Trust `Origin: "null"` in CORS:** Sandboxed `<iframe>`s send `Origin: null`—reject `"null"` in CORS allowlists.
- **Prepared Statements + Least-Privilege DB Roles:** Run your API with a DB user that has `SELECT`/`INSERT`/`UPDATE` on app tables only (never superuser), paired with parameterized queries.

</TopicSection>

<TopicSection id="m03-p3-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. Stateful Sessions vs. Short-Lived JWT + Rotating Refresh Tokens

| Dimension | Stateful Session Cookie | Access JWT + Rotating Refresh Token |
| --- | --- | --- |
| **Revocation Speed** | Instant (delete Redis/DB row) | Access JWT lives until `exp` (5–15m); refresh revoked instantly |
| **Cross-Service Auth** | Requires shared session store or introspection | Any microservice verifies signature with public key |
| **Storage** | `HttpOnly; Secure; SameSite` cookie | Memory (access) + `HttpOnly` cookie (refresh) |

#### 2. SQL Injection vs. NoSQL Injection Defenses

| Threat | Root Cause | Mandatory Defense |
| --- | --- | --- |
| **SQL Injection** | String concatenation in SQL (`WHERE` or `ORDER BY`) | Parameterized queries (`$1, $2`) + `Map`/`Set` allowlist for sort columns |
| **NoSQL Injection** | Unvalidated JSON objects (`$ne`, `$gt`, `$where`) | Strict primitive type validation (`typeof === "string"`) + disable `$where` |

#### 3. Rate Limiting Algorithms

| Algorithm | Burst Behavior | Memory / Redis Cost | Best For |
| --- | --- | --- | --- |
| **Fixed Window** | 2x burst at window edge | Very low (1 counter) | Coarse internal quotas |
| **Token Bucket** | Controlled burst up to `capacity` | Low (`tokens`, `lastMs`) | Public APIs & login endpoints |
| **Sliding Window Log** | Smooth, no boundary spike | Higher (timestamps list) | Strict security-critical endpoints |

</TopicSection>

<TopicSection id="m03-p3-sec-l" letter="L" title="Tips to Remember (Mnemonics & Mental Models)">

- **"JWTs are signed, not secret; short `exp` + explicit `alg` allowlist always."**
- **"Rotate refresh tokens; if an old one is replayed, burn the whole family."**
- **"AuthN (`401`) != AuthZ (`403`); scope every query by `tenant_id`/`user_id` to kill BOLA."**
- **"Parameterized values (`$1`) + allowlisted column names = zero SQLi; primitives only = zero NoSQLi."**

</TopicSection>

  if (typeof a !== "string" || typeof b !== "string") {
    throw new TypeError("Both inputs must be strings");
  }
  let diff = a.length ^ b.length;
  const len = Math.max(a.length, b.length);
  for (let i = 0; i < len; i++) {
    const ca = i < a.length ? a.charCodeAt(i) : 0;
    const cb = i < b.length ? b.charCodeAt(i) : 0;
    diff |= ca ^ cb;
  }
  return diff === 0;
}

function sanitizeInput(raw, maxLen = 120) {
  if (typeof raw !== "string") throw new TypeError("Input must be a string");
  if (!Number.isInteger(maxLen) || maxLen < 1) throw new TypeError("maxLen must be integer >= 1");

    const code = raw.charCodeAt(i);
    if (code <= 31 || code === 127) continue;
    out += raw[i];
  }
  return out.trim().slice(0, maxLen);
}

<TopicSection id="m03-p3-sec-q" letter="Q" title="Summary & Key Takeaways">

- **AuthN & Tokens:** Hash passwords with `Argon2id`/`scrypt`, compare secrets in constant time, enforce strict JWT `alg`/`iss`/`aud`/`exp` checks, and rotate refresh tokens with family reuse detection.
- **AuthZ & RBAC:** Stop BOLA/IDOR by checking fine-grained RBAC permissions AND scoping every DB query by `tenant_id`/`user_id`.
- **Perimeter Security:** Enforce exact-origin CORS allowlists (never `*` + credentials or `"null"`), Redis token-bucket rate limits (`429`), and `helmet` headers.
- **Injection Defense:** Use parameterized SQL (`$1`) + allowlisted sort columns, validate NoSQL filters to primitive types (`$` operators blocked), and sanitize control chars without ReDoS regexes.

</TopicSection>
