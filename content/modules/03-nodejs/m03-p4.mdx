<TopicSection id="m03-p4-sec-a" letter="A" title="Topic Introduction">

#### What is this?

Shipping a single Express endpoint is easy; operating a backend at scale requires **bounded queries** (**Pagination**, **Filtering**, **Sorting**), **safe binary & real-time I/O** (**File uploads**, **WebSockets**, **Connection pooling**), **asynchronous resilience** (**Background jobs**, **Queue systems**), **clean system architecture** (**Modular monolith**, **Microservices**, **Backend design patterns**, **Dependency injection**), and **automated confidence** (**Testing**, **Unit tests**, **Integration tests**, **API tests**, **Performance optimization**).

#### Why does it exist & what problem does it solve?

Unbounded `SELECT *` queries OOM the server, deep `OFFSET 100000` slows databases to a crawl, synchronous email/PDF generation inside HTTP routes causes `504` timeouts, unpooled DB connections exhaust Postgres `max_connections`, and premature microservices multiply network latency and deployment complexity.

#### Where is it used in real-world software?

Every mature Node.js platform—order pipelines, webhook processors, collaborative real-time apps, and multi-tenant SaaS APIs—relies on these exact patterns to stay fast, maintainable, and fault-tolerant.

</TopicSection>

<TopicSection id="m03-p4-sec-b" letter="B" title="Fundamentals (Simple Mental Models)">

<TopicAnchor id="m03-p4-topic-pagination" />

#### 1. Pagination: Offset vs. Keyset (Cursor) Pagination

**Pagination** bounds result sets so endpoints never dump 500,000 rows into RAM. **Offset pagination** (`LIMIT 20 OFFSET 40`) is simple for small jump-to-page UIs, but degrades linearly at high offsets (`OFFSET 100000` still scans and discards 100,000 rows) and skips/duplicates rows if items are inserted mid-scroll.

**Cursor (keyset) pagination** (`WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20`) uses an index seek in `O(log n)` regardless of page depth and stays stable under concurrent inserts.

<TopicAnchor id="m03-p4-topic-filtering" />

#### 2. Filtering: Allowlisted Predicates & Index-Friendly Bounds

**Filtering** lets clients narrow query results (`?status=paid&minTotal=1000`). Always validate filter keys and operators against an explicit allowlist, coerce and bound query values (`limit` capped at `100`), and avoid leading-wildcard `LIKE '%term%'` patterns that defeat B-tree indexes.

Combining strict filter validation with composite indexes `(tenant_id, status, created_at)` and parameterized placeholders keeps filtered multi-tenant queries fast across millions of rows.

<TopicAnchor id="m03-p4-topic-sorting" />

#### 3. Sorting: Deterministic Tie-Breakers & SQL Injection Defense

**Sorting** (`?sort=-createdAt`) orders results predictably for users and cursors. Always map client sort keys through an explicit `Map` or `Set` allowlist to real SQL column names—never interpolate `req.query.sort` directly into `ORDER BY`.

Always append a unique deterministic **tie-breaker** column (`ORDER BY created_at DESC, id DESC`) so rows with identical timestamps never shuffle or duplicate across pages.

<TopicAnchor id="m03-p4-topic-file-uploads" />

#### 4. File Uploads: Streaming, Magic Bytes & Direct-to-Object-Storage

Never buffer large **file uploads** in Node.js memory or save user-supplied filenames directly to local disk. Validate `Content-Length` limits, inspect file **magic bytes** (not just `.png` extension or `Content-Type` header), rename files to random UUIDs, and stream directly to object storage (S3/GCS).

For large files, the gold-standard pattern is **pre-signed upload URLs**: the Node API authenticates and issues a short-lived signed S3 URL so the browser uploads straight to object storage without tying up Node event-loop/bandwidth capacity.

<TopicAnchor id="m03-p4-topic-background-jobs" />

#### 5. Background Jobs: Returning `202 Accepted` & Keeping HTTP Fast

**Background jobs** move slow, non-critical, or failure-prone work (sending emails, generating PDFs, resizing video, syncing webhooks) out of the HTTP request-response cycle. The API validates the request, persists/enqueues the job, and returns **`202 Accepted`** in milliseconds.

Always design job handlers to be **idempotent** (using an `idempotencyKey` or DB unique constraint) because queues guarantee **at-least-once** delivery—meaning a worker crash after side effects can re-run the same job.

<TopicAnchor id="m03-p4-topic-queue-systems" />

#### 6. Queue Systems: Retries, Backoff, Concurrency & Dead-Letter Queues

**Queue systems** (BullMQ on Redis, SQS, RabbitMQ) decouple producers from workers, smoothing traffic spikes instead of overwhelming databases. Workers pull jobs with bounded concurrency, retry transient failures using **exponential backoff + jitter**, and route poison-pill jobs to a **Dead-Letter Queue (DLQ)** after `maxAttempts`.

Monitor queue depth, oldest job age, and DLQ count so silent worker stalls trigger alerts before backlogs grow out of control.

<TopicAnchor id="m03-p4-topic-websockets" />

#### 7. WebSockets: Full-Duplex Real-Time Connections & Scaling

**WebSockets** upgrade an HTTP/1.1 connection (`101 Switching Protocols`) into a persistent, bidirectional TCP channel ideal for live chat, collaborative cursors, and streaming dashboards (whereas **Server-Sent Events / SSE** suffice for simpler server-to-client feeds).

In production, send periodic **ping/pong heartbeats** to prune dead half-open sockets, enforce per-connection message size/rate limits, and back rooms with **Redis Pub/Sub** when scaling across multiple Node instances.

<TopicAnchor id="m03-p4-topic-connection-pooling" />

#### 8. Connection Pooling: Reusing Expensive TCP/TLS DB Handshakes

Opening a fresh PostgreSQL or Redis TCP + TLS + auth connection per HTTP request adds tens of milliseconds and quickly exhausts the database's `max_connections` limit. **Connection pooling** maintains a bounded set of warm reusable connections (`min`/`max`, `idleTimeoutMillis`, `connectionTimeoutMillis`).

Size each Node instance's pool carefully (`instances * maxPoolSize <= dbMaxConnections` minus admin headroom) and always release connections in a `finally` block so thrown errors never leak pool slots.

<TopicAnchor id="m03-p4-topic-microservices" />

#### 9. Microservices: Independent Deployment vs. Distributed Complexity

**Microservices** split a backend into independently deployable services owning their own data stores, communicating over HTTP/gRPC or async events. They shine when large teams need independent release cadences, isolated scaling (e.g., video transcoding vs. billing), or polyglot runtimes.

However, microservices introduce network latency, partial failures, distributed tracing, and eventual consistency (no cross-service ACID joins)—never adopt them before you actually hit team or scaling bottlenecks.

<TopicAnchor id="m03-p4-topic-modular-monolith" />

#### 10. Modular Monolith: Clean Domain Boundaries Without Network Tax

A **Modular Monolith** deploys as one application process while organizing code into strict domain modules (`orders/`, `billing/`, `inventory/`) that communicate only through explicit **public interfaces**—never reaching directly into another module's private tables or internal files.

You get fast in-process calls, single-DB ACID transactions, and zero distributed-systems overhead while keeping module boundaries clean enough to extract into a microservice later if needed.

<TopicAnchor id="m03-p4-topic-backend-design-patterns" />

#### 11. Backend Design Patterns: Controller-Service-Repository, Outbox & Circuit Breaker

Proven **backend design patterns** separate concerns cleanly: **Controller** (HTTP parsing/validation) -> **Service** (business rules/transactions) -> **Repository** (SQL/DB queries). Use the **Transactional Outbox** pattern to atomically write DB state and an outbox event in one transaction before publishing to a queue.

Protect outbound HTTP calls with **timeouts + Circuit Breakers** so a slow third-party API fails fast instead of exhausting all Node sockets and cascading into a full outage.

<TopicAnchor id="m03-p4-topic-dependency-injection" />

#### 12. Dependency Injection: Decoupling Wiring From Business Logic

**Dependency Injection (DI)** passes collaborators (`orderRepo`, `mailer`, `clock`) into a service's constructor or factory function instead of hardcoding `import db from "./db"` directly inside business logic.

In Node.js and TypeScript, explicit **constructor or factory DI** (without heavy reflection decorators) keeps module dependencies crystal clear, eliminates circular imports, and lets tests swap real Postgres or Stripe clients for fast deterministic fakes in one line.

<TopicAnchor id="m03-p4-topic-testing" />

#### 13. Testing: Backend Testing Pyramid & Deterministic Isolation

A reliable backend **testing** strategy balances fast **unit tests** (pure domain rules, validators, pagination math), **integration tests** (repositories against real containerized databases via Testcontainers), and **API tests** (full Express middleware, auth, status codes, and Problem Details contracts).

Keep tests deterministic by injecting clocks and IDs, isolating database state per test (rolled-back transactions or clean schemas), and never hitting live third-party payment or email APIs in CI.

<TopicAnchor id="m03-p4-topic-unit-tests" />

#### 14. Unit Tests: Fast Verification of Services, Rules & Edge Cases

**Unit tests** exercise individual functions and DI-wired services in milliseconds with zero network or disk I/O. Test boundary values (`limit = 0`, `limit = 101`, negative totals), state transitions, and expected error paths (`NotFoundError`, `ConflictError`).

Mock only external I/O boundaries (`mailer`, `paymentGateway`)—avoid over-mocking internal helper functions, which couples tests tightly to implementation details rather than observable behavior.

<TopicAnchor id="m03-p4-topic-integration-tests" />

#### 15. Integration Tests: Real Database Queries, Migrations & Constraints

**Integration tests** run your repositories, schema migrations, unique constraints, and connection pools against a real database (such as ephemeral PostgreSQL or Redis containers) rather than an in-memory SQLite mock that behaves differently.

They catch real-world SQL syntax bugs, missing indexes, transaction deadlock handling, and `UNIQUE` or `FOREIGN KEY` constraint violations before code ever reaches production.

<TopicAnchor id="m03-p4-topic-api-tests" />

#### 16. API Tests: End-to-End HTTP Contracts, Auth & Error Shapes

**API tests** (using `supertest` or Node `fetch` against an ephemeral Express server) verify the complete HTTP pipeline: route matching, Zod validation (`422`), AuthN (`401`), RBAC/BOLA (`403`), rate limiting (`429`), response headers (`X-Request-Id`, `Location`), and redacted `500` error bodies.

Every fixed production API bug should ship with an automated regression API test locking down the exact HTTP status code and JSON contract.

<TopicAnchor id="m03-p4-topic-performance-optimization" />

#### 17. Performance Optimization: Profiling, N+1 Elimination & Caching

Backend **performance optimization** starts with measuring p95/p99 latency, DB query plans (`EXPLAIN ANALYZE`), and Node event-loop delay before guessing. The biggest real-world wins come from eliminating **N+1 queries** (batching with `WHERE id = ANY($1)` or joins), adding missing composite indexes, caching hot reads in Redis, and keeping the event loop non-blocking.

Pair **HTTP compression** (`gzip`/`br` at the reverse proxy), **keep-alive connection reuse**, and **bounded pools/caches** so latency stays flat under peak concurrency.

</TopicSection>

  const params = [tenantId.trim()];
  const clauses = ["tenant_id = $1"];
  if (status !== undefined) {
    if (!ALLOWED_STATUSES.has(status)) throw new RangeError("Invalid status filter");
    params.push(status);
    clauses.push("status = $" + params.length);
  }
  if (cursor) {
    if (typeof cursor.value !== "string" || typeof cursor.id !== "string" || !cursor.id) {

  params.push(limit + 1);
  return {

#### Example 3: Bounded Database Connection Pool (`createConnectionPool`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models bounded connection pooling: reuse idle sockets, cap max connections, reject leaks
function createConnectionPool(maxSize = 2) {
  if (!Number.isInteger(maxSize) || maxSize < 1) throw new TypeError("maxSize must be integer >= 1");
  let created = 0;
  const idle = [];
  const inUse = new Set();

  return {
    acquire() {
      if (idle.length > 0) {
        const conn = idle.pop();
        inUse.add(conn);
        return conn;
      }
      if (created < maxSize) {
        const conn = { id: "conn_" + (++created) };
        inUse.add(conn);
        return conn;
      }
      throw new Error("Pool exhausted (max=" + maxSize + ")");
    },
    release(conn) {
      if (!inUse.has(conn)) throw new Error("Cannot release unowned or already-released connection");
      inUse.delete(conn);
      idle.push(conn);
    },
    stats() {
      return { created, idle: idle.length, inUse: inUse.size };
    }
  };
}

const pool = createConnectionPool(2);
const c1 = pool.acquire();
const c2 = pool.acquire();
pool.release(c1);
const c3 = pool.acquire(); // reuses conn_1 without creating a 3rd connection
console.log("Reused c1?", c3.id === c1.id, "| Pool stats:", pool.stats());`}
/>

#### Example 4: Background Job Queue With Idempotency, Exponential Backoff & DLQ (`createJobQueue`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models at-least-once job queue with idempotency dedup, exponential backoff, and DLQ
function createJobQueue(maxAttempts = 3, baseDelayMs = 100) {
  if (!Number.isInteger(maxAttempts) || maxAttempts < 1) throw new TypeError("maxAttempts must be integer >= 1");
  if (!Number.isInteger(baseDelayMs) || baseDelayMs < 1) throw new TypeError("baseDelayMs must be integer >= 1");
  const seenKeys = new Set();
  const pending = [];
  const dlq = [];
  const completed = [];

  return {
    enqueue(idempotencyKey, payload) {
      if (typeof idempotencyKey !== "string" || !idempotencyKey.trim()) {
        throw new TypeError("idempotencyKey required");
      }
      if (seenKeys.has(idempotencyKey)) return { queued: false, reason: "duplicate" };
      seenKeys.add(idempotencyKey);
      pending.push({ idempotencyKey, payload, attempts: 0, nextDelayMs: 0 });
      return { queued: true };
    },
    processNext(handler) {
      if (typeof handler !== "function") throw new TypeError("handler must be a function");
      if (pending.length === 0) return null;
      const job = pending.shift();
      job.attempts++;
      try {
        handler(job.payload);
        completed.push(job.idempotencyKey);
        return { status: "completed", attempts: job.attempts };
      } catch (err) {
        if (job.attempts >= maxAttempts) {
          dlq.push({ ...job, error: err instanceof Error ? err.message : String(err) });
          return { status: "dlq", attempts: job.attempts };
        }
        job.nextDelayMs = baseDelayMs * (2 ** (job.attempts - 1));
        pending.push(job);
        return { status: "retry", attempts: job.attempts, nextDelayMs: job.nextDelayMs };
      }
    },
    summary() {
      return { pending: pending.length, completed: completed.length, dlq: dlq.length };
    }
  };
}

const jq = createJobQueue(3, 50);
jq.enqueue("receipt:1", { orderId: 1 });
const dup = jq.enqueue("receipt:1", { orderId: 1 });
const r1 = jq.processNext(() => { throw new Error("SMTP timeout"); });
const r2 = jq.processNext(() => { throw new Error("SMTP timeout"); });
const r3 = jq.processNext(() => { throw new Error("SMTP timeout"); });
console.log("Dup blocked?", !dup.queued, "| Step 1:", r1, "| Step 3:", r3, "| Summary:", jq.summary());`}

<TopicSection id="m03-p4-sec-e" letter="E" title="Step-by-Step Walkthrough">

Trace **`createJobQueue(3, 50)`** (**Example 4**) handling a flaky SMTP server:

1. **Idempotent Enqueue:** First `enqueue("receipt:1")` registers the key in `seenKeys` (`queued: true`); second call with the same key returns `{ queued: false, reason: "duplicate" }`.
2. **Attempt 1 Fails:** `attempts` becomes `1 < 3`, so the job is re-queued with `nextDelayMs = 50 * 2^0 = 50ms`.
3. **Attempt 2 Fails:** `attempts` becomes `2 < 3`, doubling backoff to `100ms`.
4. **Attempt 3 Hits `maxAttempts`:** Instead of looping forever and blocking the queue, the job moves to `dlq` (`{ status: "dlq", attempts: 3 }`) for operator inspection and replay.

</TopicSection>

<TopicSection id="m03-p4-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Replacing Slow `OFFSET` Pagination & Sync PDF Generation on `/exports`

**Problem:** An admin orders endpoint takes 3.2 seconds at page 500 (`OFFSET 10000`), and exporting PDFs synchronously in Express causes `504 Gateway Timeout` errors under load.

**Production Solution:** Switch list reads to `(created_at, id)` **keyset cursor pagination** backed by a composite index, and move PDF generation to a BullMQ background job returning `202 Accepted` with a pre-signed S3 download link when ready.

#### Scenario 2: Preventing `max_connections` Exhaustion Across 12 Node Replicas

**Problem:** A service scales to 12 Kubernetes pods, each configured with `pool.max = 25` (`300` total connections), crashing a PostgreSQL instance with `max_connections = 200` during traffic bursts.

**Production Solution:** Size each pod's pool to `max = 10` (`120` total) or introduce **PgBouncer** in transaction-pooling mode, and release every connection in a `try/finally` block.

</TopicSection>

<TopicSection id="m03-p4-sec-g" letter="G" title="Common Mistakes">

- **Using `OFFSET 50000` on large tables:** Forces the database to scan and discard 50,000 rows per request.
- **Forgetting `finally { pool.release(conn); }`:** Leaks pool slots on exceptions until every request hangs waiting for a connection.
- **Running non-idempotent background jobs without dedup keys:** Sends duplicate emails or double charges when at-least-once queues retry.
- **Trusting `req.file.originalname` or `Content-Type` on file uploads:** Allows path traversal and spoofed executables.
- **Splitting into 15 microservices on day one:** Adds distributed latency, split-brain failures, and operational tax when a **Modular Monolith** fits cleanly.

</TopicSection>

<TopicSection id="m03-p4-sec-h" letter="H" title="Best Practices">

- **Start with a Modular Monolith** using strict module boundaries and constructor DI; extract microservices only when scaling or team independence demands it.
- **Use keyset cursor pagination** (`limit` capped &lt;= 100, deterministic tie-breaker `id`) for feeds and large tables.
- **Enforce `try/finally` connection release**, bounded pool sizes, and pre-signed URLs for large file uploads.
- **Lock critical flows with Unit + DB Integration + API tests** using deterministic DI fakes for external vendors and real DB containers for SQL constraints.

</TopicSection>

<TopicSection id="m03-p4-sec-i" letter="I" title="Performance & Scalability">

- **Eliminate N+1 Queries:** Batch child lookups (`WHERE order_id = ANY($1)`) or use SQL joins instead of querying inside a `for` loop.
- **Keyset Index Seeks:** Composite indexes matching `(tenant_id, created_at DESC, id DESC)` keep page 1 and page 10,000 equally fast.
- **Worker Concurrency & Backpressure:** Bound background worker concurrency and WebSocket room fan-out via Redis Pub/Sub so burst traffic degrades smoothly into queue latency rather than crashing pods.

</TopicSection>

<TopicSection id="m03-p4-sec-j" letter="J" title="Security Considerations">

- **File Upload Hardening:** Enforce max byte limits, verify magic bytes (JPEG/PNG/PDF signatures), store with generated UUID keys outside web roots, and serve user uploads from an isolated bucket/domain with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.
- **WebSocket Auth & Limits:** Authenticate the WebSocket upgrade handshake (`cookie` / short-lived ticket), re-check authorization on room joins, and cap frame size + message rate per socket.
- **Filter/Sort Allowlists:** Never pass raw query keys into `ORDER BY` or dynamic SQL `WHERE` clauses.

</TopicSection>

<TopicSection id="m03-p4-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. Offset vs. Keyset (Cursor) Pagination

| Dimension | Offset (`LIMIT/OFFSET`) | Keyset / Cursor (`WHERE (ts, id) < ...`) |
| --- | --- | --- |
| **Deep Page Speed** | Degrades (`O(offset + limit)`) | Constant (`O(log n)` index seek) |
| **Live Inserts Stability** | Can skip or duplicate rows | Stable, zero duplicates |
| **Random Page Jump (`Page 42`)** | Easy | Not supported (Next/Prev only) |

#### 2. Modular Monolith vs. Microservices

| Dimension | Modular Monolith | Microservices |
| --- | --- | --- |
| **Call Latency & Transactions** | In-process microseconds, ACID joins | Network hops, eventual consistency (Saga/Outbox) |
| **Deployment & Ops** | Single CI/CD pipeline | Independent deploys, service mesh, distributed tracing |
| **Best Fit** | Small–medium teams, rapid iteration | Large independent teams or isolated compute scaling |

#### 3. Backend Testing Layers

| Layer | Target | Dependencies | Speed |
| --- | --- | --- | --- |
| **Unit Tests** | Pure helpers & DI services | In-memory fakes | < 1ms |
| **Integration Tests** | Repositories, SQL, migrations | Real Postgres/Redis container | 10–100ms |
| **API Tests** | Routes, Auth, Zod, Status codes | Ephemeral Express app + test DB | 20–150ms |

</TopicSection>

<ExerciseCard
  title="Exercise 2: Lightweight DI Container & WebSocket Heartbeat Tracker (createContainer, createWsTracker)"
  prompt={
    <p>
      Implement <code>createContainer()</code> supporting singleton/factory registration with circular-dependency detection, plus <code>createWsTracker(timeoutMs)</code> to prune stale WebSocket connections missing heartbeats.
    </p>
  }
>
  <CodeBlock
    lang="javascript"
    runnable
    code={`function createContainer() {
  const factories = new Map();
  const instances = new Map();
  const resolving = new Set();

  return {
    register(name, factory) {
      if (typeof name !== "string" || !name.trim() || typeof factory !== "function") {
        throw new TypeError("Invalid registration");
      }
      factories.set(name, factory);
    },
    resolve(name) {
      if (instances.has(name)) return instances.get(name);
      if (!factories.has(name)) throw new Error("Unregistered dependency: " + name);
      if (resolving.has(name)) throw new Error("Circular dependency detected: " + name);
      resolving.add(name);
      try {
        const inst = factories.get(name)(this);
        instances.set(name, inst);
        return inst;
      } finally {
        resolving.delete(name);
      }
    }
  };
}

function createWsTracker(timeoutMs) {
  if (!Number.isInteger(timeoutMs) || timeoutMs < 1) throw new TypeError("timeoutMs must be positive integer");
  const sockets = new Map();
  return {
    heartbeat(id, nowMs) {
      sockets.set(id, nowMs);
    },
    pruneStale(nowMs) {
      const removed = [];
      for (const [id, lastMs] of sockets.entries()) {
        if (nowMs - lastMs > timeoutMs) {
          sockets.delete(id);
          removed.push(id);
        }
      }
      return removed;
    }
  };
}

const c = createContainer();
c.register("repo", () => ({ kind: "pg" }));
c.register("svc", (di) => ({ repo: di.resolve("repo") }));
const ws = createWsTracker(5000);
ws.heartbeat("s1", 1000);
ws.heartbeat("s2", 4000);
console.log("DI wired?", c.resolve("svc").repo.kind === "pg", "| Pruned at 7000ms:", ws.pruneStale(7000));`}

<TopicSection id="m03-p4-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Query Bounds:** Prefer keyset cursor pagination with deterministic `id` tie-breakers, allowlisted filters/sorts, and composite indexes.
- **Async & Real-Time:** Offload slow work to idempotent background queues (`202 Accepted` + backoff + DLQ), stream/pre-sign file uploads with magic-byte checks, and prune WebSockets with heartbeats.
- **Architecture & Pooling:** Size DB connection pools safely with `try/finally` releases, and build a DI-wired Modular Monolith before paying microservice complexity.
- **Testing & Speed:** Combine Unit + real-DB Integration + API tests, profile with `EXPLAIN ANALYZE`, and eliminate N+1 queries.
