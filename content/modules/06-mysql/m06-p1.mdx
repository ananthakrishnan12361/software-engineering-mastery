<TopicSection id="m06-p1-sec-a" letter="A" title="Topic Introduction">

#### What is this?

**MySQL** is the world's most widely deployed open-source relational database server, powering everything from small WordPress blogs to massive e-commerce platforms processing millions of transactions per second. Its pluggable **storage engine** architecture separates the SQL parsing layer from the physical data storage layer, allowing different engines (InnoDB, MyISAM, Memory) to coexist in one server instance with radically different durability, locking, and indexing trade-offs.

#### Why does it exist & what problem does it solve?

Relational data has natural transactional integrity requirements—bank transfers, order fulfilment, inventory reservations—where partial writes are catastrophic. MySQL's InnoDB engine was built to solve this with **ACID-compliant transactions**, row-level locking, and crash-safe redo/undo logs. The layered architecture means teams can opt-in to durability and locking overhead (InnoDB) for transactional tables and use lighter-weight engines (Memory) for in-process caching tables.

#### Where is it used in real-world software?

MySQL underpins SaaS multi-tenant applications, PHP/Node.js web backends (via mysql2 / Sequelize), e-commerce platforms (Magento, WooCommerce), and large-scale deployments at companies like Meta (originally), Twitter, Airbnb, and GitHub—often in InnoDB clusters with Group Replication or ProxySQL for high availability.

#### 1. MySQL Architecture: Parser, Optimizer, Storage Engine API

MySQL's server layer consists of the **Connection Thread Manager** (one OS thread per connection, with a thread cache), the **SQL Parser** (tokeniser → parse tree), the **Query Optimizer** (cost-based; rewrites joins, pushes predicates, chooses index access paths), and the **Storage Engine API** (`handlerton`). Every `SELECT`, `INSERT`, `UPDATE`, or `DELETE` travels Parser → Optimizer → Storage Engine API → physical engine.

The **binary log** (`binlog`) lives in the server layer—not in InnoDB—and records every committed statement or row change for replication and point-in-time recovery. InnoDB maintains its own **redo log** (`ib_logfile*`) and **undo log** segments; the two-phase commit protocol (`XA`) ensures the binlog and InnoDB redo log stay in sync at every `COMMIT`.

<TopicAnchor id="m06-p1-topic-storage-engines" />

#### 2. Storage Engines: Pluggable Architecture & the handlerton API

MySQL's pluggable **storage engine** layer separates engine-level metadata and transaction hooks (`handlerton`, a per-engine struct) from the per-table `handler` C++ class that every engine must implement (`open()`, `close()`, `write_row()`, `update_row()`, `delete_row()`, `rnd_next()`, `index_read()`). The optimizer talks to every table through this same API, making the SQL layer engine-agnostic.

Choosing the wrong engine is a critical production mistake: **InnoDB** is the ACID-safe default for transactional workloads; **MyISAM** trades durability for speed on read-heavy archives; **Memory** stores rows in RAM and vanishes on restart; **CSV** persists data as comma-separated text files. Run `SHOW ENGINES;` to see which are compiled in and their `TRANSACTIONS` / `SAVEPOINTS` support flags.

<TopicAnchor id="m06-p1-topic-innodb" />

#### 3. InnoDB: Buffer Pool, Redo Log, Undo Log & Doublewrite Buffer

<GlossaryTerm definition="MySQL's default ACID-compliant storage engine featuring a buffer pool, redo/undo logs, row-level locking, MVCC, and crash recovery via doublewrite buffer.">InnoDB</GlossaryTerm> is MySQL's default storage engine and the foundation of all transactional work. Its key subsystems are:

- **Buffer Pool** — shared LRU/midpoint-insertion cache of 16 KB data pages and index pages (target ≥ 70–80 % of RAM). All reads go through the buffer pool; dirty pages are flushed lazily.
- **Redo Log** (`ib_logfile0`, `ib_logfile1` pre-8.0.30) — write-ahead log of physical page changes. On crash, InnoDB replays redo entries from the last checkpoint then rolls back uncommitted transactions using undo segments. Since MySQL 8.0.30+, InnoDB manages a pool of `#ib_redo*` files inside `#innodb_redo/` sized dynamically via `innodb_redo_log_capacity`.
- **Undo Log Segments** — record old row versions for MVCC read views and transaction rollback. Long-running transactions bloat the undo tablespace and slow purge threads.
- **Doublewrite Buffer** — before writing a dirty 16 KB page to its final location InnoDB first writes it to the sequential doublewrite area, protecting against partial writes if a crash occurs mid-page-write.
- **Change Buffer** — batches secondary index leaf page merges for `INSERT`/`UPDATE`/`DELETE` on non-unique secondary indexes when the target page is not in the buffer pool.

<TopicAnchor id="m06-p1-topic-myisam-overview" />

#### 4. MyISAM Overview: Table-Level Locking, No Transactions & Full-Text Search

**MyISAM** (MySQL ISAM) stores data in `.MYD` (data) and `.MYI` (index) files with the index in a compact B-tree. It performs no transaction logging, acquires **table-level read/write locks** on every query, and cannot roll back changes—a crashed `UPDATE` midway leaves a corrupt half-written table that must be repaired with `REPAIR TABLE` or `myisamchk`.

The major remaining use case for MyISAM is **legacy full-text search** (`FULLTEXT` index + `MATCH ... AGAINST`) in pre-5.6 databases, but InnoDB has supported `FULLTEXT` indexes since MySQL 5.6, so there is now no good reason to choose MyISAM for new tables. Never use MyISAM for tables that hold financial, inventory, or any other data requiring crash safety.

<TopicAnchor id="m06-p1-topic-sql" />

#### 5. SQL in MySQL: Dialect Differences, Strict Mode & NO_ENGINE_SUBSTITUTION

MySQL's SQL dialect diverges from standard SQL in several important ways that trip up developers. Older versions (pre-5.7) defaulted to a **permissive mode** that silently truncated strings, converted invalid dates to `'0000-00-00'`, and inserted zero for out-of-range numbers. Since MySQL 5.7.5+ and 8.0, the default `sql_mode` enables **`ONLY_FULL_GROUP_BY`**, **`STRICT_TRANS_TABLES`**, **`NO_ZERO_IN_DATE`**, **`NO_ZERO_DATE`**, **`ERROR_FOR_DIVISION_BY_ZERO`**, and **`NO_ENGINE_SUBSTITUTION`**, rejecting invalid data with an error rather than coercing it.

Key MySQL-specific SQL features include: `REPLACE INTO` (delete-then-insert on duplicate key), `INSERT ... ON DUPLICATE KEY UPDATE`, `LIMIT ... OFFSET` (not standard SQL), `GROUP BY` historically allowing non-aggregated columns (fixed by `ONLY_FULL_GROUP_BY` in `sql_mode`), and `AUTO_INCREMENT` column semantics tied to InnoDB's sequence counter reset on server restart (pre-8.0). Always set `sql_mode` explicitly in production to avoid silent data corruption.

<TopicAnchor id="m06-p1-topic-transactions" />

#### 6. Transactions: BEGIN / COMMIT / ROLLBACK & SAVEPOINT

An InnoDB **transaction** groups one or more DML statements into an atomic unit: either all statements commit together or all roll back together. Start with `START TRANSACTION` (or `BEGIN`), issue DML, then `COMMIT` to persist or `ROLLBACK` to discard. By default, MySQL runs in **`autocommit = ON`** mode, wrapping each individual DML statement in its own transaction—set `autocommit = 0` or use `START TRANSACTION` explicitly for multi-statement transactions.

**`SAVEPOINT sp1`** marks an intermediate rollback target: `ROLLBACK TO SAVEPOINT sp1` undoes work since the savepoint without aborting the whole transaction; `RELEASE SAVEPOINT sp1` discards it. DDL statements (`ALTER TABLE`, `CREATE TABLE`, `DROP TABLE`) in MySQL **cause an implicit COMMIT** before they execute—there is no transactional DDL in MySQL (unlike PostgreSQL). Always design schema migrations with this in mind.

<TopicAnchor id="m06-p1-topic-acid" />

#### 7. ACID: Atomicity, Consistency, Isolation & Durability in InnoDB

**ACID** is the four-property contract that InnoDB makes for every committed transaction:

- **Atomicity** — undo log segments record the before-image of every modified row; a `ROLLBACK` or crash recovery replays undo entries to restore the original state.
- **Consistency** — constraint enforcement (`NOT NULL`, `FOREIGN KEY`, `UNIQUE`, `CHECK` in 8.0+) and trigger logic execute within the transaction before `COMMIT`, keeping data invariants intact.
- **Isolation** — MVCC read views and row-level locks prevent concurrent transactions from seeing each other's uncommitted data (at the configured isolation level).
- **Durability** — `innodb_flush_log_at_trx_commit = 1` (the default) flushes and `fsync()`s the redo log at every `COMMIT`, guaranteeing zero committed-data loss on crash. Setting it to `2` (flush but no fsync on commit, only on 1-second timer) or `0` (every 1 second) sacrifices up to 1 second of commits for throughput—use only where data loss is acceptable.

<TopicAnchor id="m06-p1-topic-isolation-levels" />

#### 8. Isolation Levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ & SERIALIZABLE

MySQL InnoDB supports all four SQL standard isolation levels:

- **`READ UNCOMMITTED`** — dirty reads allowed; transactions see uncommitted row versions. Never used in production.
- **`READ COMMITTED`** — no dirty reads; each statement gets a fresh read view, so non-repeatable reads and phantom reads are possible. Commonly used in high-concurrency OLTP to minimize lock contention; also the level used by MySQL row-based replication internally.
- **`REPEATABLE READ`** (default) — a single consistent read view for the entire transaction (via MVCC); no dirty or non-repeatable reads, but **phantom reads are prevented by gap locks and next-key locks** in InnoDB (unlike standard SQL's REPEATABLE READ).
- **`SERIALIZABLE`** — all `SELECT` statements become `SELECT ... FOR SHARE`, making reads locking; highest isolation with lowest concurrency.

Change per session with `SET SESSION TRANSACTION ISOLATION LEVEL ...` or globally via `SET GLOBAL transaction_isolation = 'READ-COMMITTED'`.

<TopicAnchor id="m06-p1-topic-locking" />

#### 9. Locking: Row Locks, Gap Locks & Next-Key Locks

InnoDB implements **row-level locking** at the index record level, not the data row level. The three lock granularities are:

- **Record Lock** — locks a single index record (`WHERE id = 42`).
- **Gap Lock** — locks the gap *before* an index record (prevents `INSERT` into a range, e.g., `WHERE id BETWEEN 10 AND 20` locks the gap even if no row has `id = 15`). Gap locks exist only in `REPEATABLE READ` and `SERIALIZABLE` to prevent phantom reads.
- **Next-Key Lock** — a record lock plus the gap before it (default for most range scans in `REPEATABLE READ`). This is the core mechanism that makes InnoDB's `REPEATABLE READ` phantom-safe.

**Intention locks** (`IS`, `IX`) at the table level are lightweight signals that a row-level lock is held or wanted, allowing table-lock requests to detect conflicts quickly without scanning all row locks.

<TopicAnchor id="m06-p1-topic-deadlocks" />

#### 10. Deadlocks: Detection, Automatic Resolution & Prevention

A **deadlock** occurs when transaction A holds lock X and waits for lock Y while transaction B holds lock Y and waits for lock X—neither can proceed. InnoDB's background **deadlock detector** runs continuously; it identifies the cycle in the lock-wait graph and automatically rolls back the **lighter transaction** (fewer undo records), returning `ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`.

Prevention strategies: always acquire locks in the **same consistent order** across all transactions; keep transactions short and commit quickly; use `SELECT ... FOR UPDATE` early in the transaction (not at the end) to surface conflicts before doing work; add indexes so lock scans are narrow (table-scans lock every gap in the table). Inspect recent deadlocks with `SHOW ENGINE INNODB STATUS\G` → `LATEST DETECTED DEADLOCK`.

</TopicSection>

<TopicSection id="m06-p1-sec-c" letter="C" title="Internal Working & Architecture">

#### InnoDB Page Layout & the Buffer Pool LRU

InnoDB stores every table row and index entry in **16 KB pages** organised into **tablespace files** (`.ibd` per table with `innodb_file_per_table = ON`, or the shared `ibdata1` system tablespace). Each page has a 38-byte header (page number, LSN, checksum), a row directory for variable-length record offsets, the actual row data, and a 8-byte trailer checksum.

The **Buffer Pool** is segmented into blocks of 16 KB. InnoDB uses a **midpoint-insertion LRU** (default: new pages enter at the 3/8 point from the tail) to protect the working set from full-table-scan evictions (`innodb_old_blocks_pct`, `innodb_old_blocks_time`). **Dirty pages** (modified but not yet flushed) are tracked in a flush list ordered by oldest LSN; the **page cleaner thread** flushes them asynchronously to stay within `innodb_max_dirty_pages_pct`.

#### Two-Phase Commit: InnoDB Redo Log ↔ Binary Log

Every InnoDB `COMMIT` goes through **two-phase commit (2PC)**:
1. **Prepare phase** — InnoDB flushes the redo log with a prepare record and marks the XID (transaction ID).
2. **Commit phase** — MySQL server writes the XID to the binary log and flushes it (`sync_binlog = 1`), then InnoDB writes the commit record to the redo log.

On crash recovery, InnoDB scans for prepared-but-not-committed XA transactions and cross-references the binary log. If the XID exists in the binlog, the transaction commits; otherwise, it rolls back. This guarantees the redo log and binlog are always consistent.

#### MVCC Read Views in InnoDB

InnoDB's **MVCC** works via hidden row fields: `DB_TRX_ID` (last-modifying transaction), `DB_ROLL_PTR` (undo log pointer for the previous version), and `DB_ROW_ID` (auto row ID if no PK). A `SELECT` obtains a **read view** (snapshot of active transaction IDs at the moment the view is created) and uses the undo log chain to reconstruct the visible version: if the row's `DB_TRX_ID` is after the read-view's snapshot, InnoDB walks the `DB_ROLL_PTR` chain backward until it finds a version committed before the snapshot.

#### Example 1: MySQL InnoDB Storage Engine Simulator (`createInnodbMvccEngine`)

This runnable example simulates InnoDB's MVCC read-view logic: each committed transaction gets an ID, row writes store the transaction ID, and a concurrent reader sees only versions committed before its read-view snapshot.

<CodeBlock lang="javascript" runnable title="InnoDB MVCC Read-View Simulator" code={`
// createInnodbMvccEngine — simulates InnoDB MVCC read-view snapshot isolation
function createInnodbMvccEngine() {
  let nextTrxId = 1;
  // rows: Map<rowId, Array<{trxId, value, deleted}>>
  const rows = new Map();
  const activeTrxs = new Set();
  const committed = new Set();
  // snapshots: Map<trxId, { maxTrxId: number, activeAtStart: Set<number> }>
  const snapshots = new Map();

  function beginTransaction() {
    const id = nextTrxId++;
    snapshots.set(id, { maxTrxId: id, activeAtStart: new Set(activeTrxs) });
    activeTrxs.add(id);
    return { id, committed: false };
  }

  function validateActiveTrx(trx) {
    if (trx == null || typeof trx.id !== "number" || !activeTrxs.has(trx.id) || trx.committed) {
      throw new Error("Invalid or already committed transaction");
    }
  }

  function write(trx, rowId, value) {
    validateActiveTrx(trx);
    if (typeof rowId !== "string" || rowId.length === 0) throw new Error("rowId must be non-empty string");
    if (!rows.has(rowId)) rows.set(rowId, []);
    rows.get(rowId).push({ trxId: trx.id, value, deleted: false });
  }

  function remove(trx, rowId) {
    validateActiveTrx(trx);
    if (typeof rowId !== "string" || rowId.length === 0) throw new Error("rowId must be non-empty string");
    if (!rows.has(rowId)) return; // row doesn't exist, no-op
    rows.get(rowId).push({ trxId: trx.id, value: null, deleted: true });
  }

  function commit(trx) {
    validateActiveTrx(trx);
    activeTrxs.delete(trx.id);
    committed.add(trx.id);
    trx.committed = true;
  }

  // read: returns latest version visible to snapshotTrxId's Read View
  function read(rowId, snapshotTrxId) {
    if (typeof rowId !== "string" || rowId.length === 0) throw new Error("rowId must be non-empty string");
    if (!Number.isInteger(snapshotTrxId) || snapshotTrxId < 1 || !snapshots.has(snapshotTrxId)) {
      throw new Error("snapshotTrxId must be a positive integer");
    }
    if (!rows.has(rowId)) return null;
    const snap = snapshots.get(snapshotTrxId);
    const versions = rows.get(rowId);
    // Walk newest → oldest along undo chain, skipping uncommitted & post-snapshot versions
    for (let i = versions.length - 1; i >= 0; i--) {
      const v = versions[i];
      const visible =
        v.trxId === snapshotTrxId ||
        (committed.has(v.trxId) && v.trxId < snap.maxTrxId && !snap.activeAtStart.has(v.trxId));
      if (visible) {
        return v.deleted ? null : v.value;
      }
    }
    return null;
  }

  return { beginTransaction, write, remove, commit, read };
}

const engine = createInnodbMvccEngine();

// T1: insert row 'order:1' = { total: 100 }
const t1 = engine.beginTransaction();
engine.write(t1, "order:1", { total: 100 });
engine.commit(t1);

// T2: update to { total: 200 } — not yet committed

<TopicSection id="m06-p1-sec-e" letter="E" title="Step-by-Step Walkthrough">

#### How InnoDB Processes a Committed Transaction

1. **Application Issues `START TRANSACTION` + DML:** InnoDB assigns a transaction ID (`DB_TRX_ID`) from the global sequence. For each modified row, it writes the before-image to the **undo log** (linked via `DB_ROLL_PTR`) and stores the new version in the buffer pool page with the current `DB_TRX_ID`.
2. **Redo Log Write-Ahead:** Before any buffer pool dirty page is flushed to disk, the corresponding redo log records are written to the in-memory redo log buffer. At `COMMIT`, the buffer is flushed and `fsync()`d to `#ib_redo*` files (`innodb_flush_log_at_trx_commit = 1`).
3. **Binary Log Write & Two-Phase Commit:** The server layer writes the transaction's events to the binary log and flushes (`sync_binlog = 1`). InnoDB's prepare/commit marks are coordinated so crash recovery can determine whether to commit or roll back orphaned prepared transactions.
4. **Lock Release:** Row-level locks (record locks, gap locks, next-key locks) are released at `COMMIT` or `ROLLBACK`. Intention locks at the table level are also released. Other waiting transactions in the lock queue can now proceed.
5. **Purge Thread Cleans Old Undo Versions:** The InnoDB **purge thread** periodically scans the undo log for versions no longer needed by any active read view and physically frees the space. Long-running transactions hold the purge position and bloat undo tablespace.

</TopicSection>

<TopicSection id="m06-p1-sec-f" letter="F" title="Real-World Use Cases">

#### E-Commerce Order Placement (InnoDB ACID)

An online store's checkout service runs: `START TRANSACTION; UPDATE inventory SET qty = qty - 1 WHERE sku = ? AND qty > 0; INSERT INTO orders (...); COMMIT;`. InnoDB's row-level locking ensures two simultaneous checkouts for the last item serialise correctly—one will commit, the other will see `0` rows updated and can retry or return "out of stock".

#### Read Scaling with MySQL Replication

A high-traffic SaaS reads product listings from **read replicas** (connected through ProxySQL's `hostgroup` rules) while writes go to the primary. The binary log replicates row changes to replicas asynchronously (or semi-synchronously), typically with sub-second lag for OLTP workloads.

#### Deadlock Avoidance in Payment Systems

Payment processors lock `sender_account` and `receiver_account` rows in ascending `account_id` order universally. This eliminates the cyclic wait condition that would cause deadlocks when two transfers run in opposite directions simultaneously.

#### Schema Migrations with Implicit DDL Commit

A DevOps team using `pt-online-schema-change` or `gh-ost` performs large `ALTER TABLE` operations without `ACCESS EXCLUSIVE`-equivalent blocks by writing to a shadow table and swapping atomically, since MySQL's DDL causes implicit commits and cannot be rolled back transactionally.

</TopicSection>

<TopicSection id="m06-p1-sec-g" letter="G" title="Common Mistakes">

- **Leaving `autocommit = ON` in Long Business Transactions:** Developers sometimes issue multiple `UPDATE` statements without an explicit `START TRANSACTION`, assuming they are atomic. With `autocommit = ON`, each statement is its own transaction—a failure after the first `UPDATE` leaves the database in an inconsistent intermediate state. Always use explicit transactions for multi-statement operations.
- **Using MyISAM for Transactional Data:** Choosing MyISAM because it was once faster for reads is dangerous: a server crash mid-write corrupts the table irrecoverably without `REPAIR TABLE`. InnoDB's performance on NVMe SSDs is superior to MyISAM for virtually every modern workload.
- **Acquiring Locks in Inconsistent Order:** Application code paths that acquire the same set of row locks in different sequences will deadlock under concurrent load. Always document and enforce lock acquisition order across all transaction paths.
- **`SELECT ... FOR UPDATE` After Doing Work:** Placing `SELECT ... FOR UPDATE` at the *end* of a transaction (after calculations) causes lock contention later and may read a stale version the transaction already computed against. Lock early, work inside the lock, commit quickly.
- **`innodb_flush_log_at_trx_commit = 0` in Production:** Setting this to `0` means the redo log is flushed only once per second regardless of `COMMIT`—up to 1 second of committed transactions can be lost on crash.
- **Ignoring `sql_mode` Differences Between Environments:** A `STRICT_TRANS_TABLES` mismatch between development (lenient) and production (strict) causes otherwise-working queries to fail in production when inserting values that would be silently truncated in dev mode.

</TopicSection>

<TopicSection id="m06-p1-sec-h" letter="H" title="Best Practices">

- **Always run InnoDB**—it is the only engine that provides ACID transactions, row-level locking, foreign keys, and crash recovery.
- **Set `innodb_buffer_pool_size` to 70–80 % of RAM** on a dedicated MySQL server to maximise in-memory data page hits.
- **Use `innodb_flush_log_at_trx_commit = 1` and `sync_binlog = 1`** in production for full durability. Accept the write latency as the cost of data integrity.
- **Use `REPEATABLE READ` (the default)** for most transactional workloads. Switch to `READ COMMITTED` explicitly only when gap-lock contention is measured and documented.
- **Keep transactions short**: open, do minimal work, commit. Long-running transactions bloat undo logs, hold locks, and block purge threads.
- **Enforce consistent lock ordering** across all code paths to structurally eliminate deadlock cycles.
- **Always handle `ERROR 1213` (deadlock)**: implement retry logic with exponential backoff in application code—deadlocks are a normal InnoDB event, not a bug.
- **Set `sql_mode = 'STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION'`** in all environments to get consistent behavior.

</TopicSection>

<TopicSection id="m06-p1-sec-i" letter="I" title="Performance & Scalability">

#### Buffer Pool Sizing & Hit Ratio

The single biggest InnoDB performance lever is **buffer pool size**. Monitor the buffer pool hit ratio:
```sql
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
-- hit_ratio = 1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)
```
Target > 99 % for OLTP workloads. If hit ratio is low, increase `innodb_buffer_pool_size` (and `innodb_buffer_pool_instances` on 8+ core servers, one per ~1 GB chunk).

#### InnoDB I/O Capacity Tuning

Configure `innodb_io_capacity` (default 200 IOPS) to match your storage tier: 2000–10000 for NVMe SSDs, 200–400 for spinning disks. The page cleaner thread uses this to throttle background flush rate. Under-configured `innodb_io_capacity` causes dirty page spikes that stall foreground writes.

#### Connection Scaling with ProxySQL

MySQL does not support async connection handling—each client connection spawns one OS thread. Beyond ~1000–2000 connections, thread context-switching dominates. Use **ProxySQL** (or MySQL Router) for connection pooling and read/write splitting, keeping the actual backend thread count proportional to CPU cores.

#### Redo Log Sizing (MySQL 8.0+)

Pre-8.0: `innodb_log_file_size` × `innodb_log_files_in_group` determines how much redo can be buffered before a checkpoint stall. Set to at least 1–4 GB on write-intensive workloads. MySQL 8.0 automates this with dynamic redo log resizing.

</TopicSection>

<TopicSection id="m06-p1-sec-j" letter="J" title="Security Considerations">

#### Principle of Least Privilege for MySQL Accounts

Never connect production applications with `root` or any account granted `SUPER`, `PROCESS`, `FILE`, or `SHUTDOWN`. Create a dedicated application account: `GRANT SELECT, INSERT, UPDATE, DELETE ON app_db.* TO 'app'@'%'`. Use `SHOW GRANTS FOR 'app'@'%';` to audit.

#### SQL Injection via MySQL's `sql_mode`

Permissive `sql_mode` (without `NO_BACKSLASH_ESCAPES`) can interact with multi-byte character set encodings (e.g., `GBK`) to produce escape sequence confusion in raw string concatenation. Always use **parameterised prepared statements** (`mysql2` driver's `connection.execute(sql, params)`) and never interpolate user input into SQL strings.

#### Encrypted Connections & Data-at-Rest

Enable TLS for client connections (`ssl_ca`, `ssl_cert`, `ssl_key` in `my.cnf`) and enforce it per user: `ALTER USER 'app'@'%' REQUIRE SSL;`. For data-at-rest encryption, configure a MySQL keyring component (`component_keyring_file` / `component_keyring_kmip`) and enable InnoDB tablespace encryption with `ENCRYPTION = 'Y'` (or `default_table_encryption = ON`).

#### Audit Logging

Enable the MySQL Enterprise Audit plugin (`audit_log`) or a community alternative such as Percona Audit Log to record all connection and query events. Logs should be shipped to a centralised SIEM and not stored on the same host as the database.

</TopicSection>

<TopicSection id="m06-p1-sec-l" letter="L" title="Tips to Remember (Mnemonics & Mental Models)">

- **"ACID = Undo + Redo + MVCC + fsync":** Atomicity uses the **undo log**; Consistency enforces **constraints + triggers**; Isolation uses **MVCC read views + row locks**; Durability flushes the **redo log + fsync** at commit.
- **"RURS = Read Uncommitted → Read Committed → Repeatable Read → Serializable":** Anomalies decrease moving right; concurrency decreases too. In MySQL, `REPEATABLE READ` is stronger than the SQL standard—InnoDB's next-key locks also block phantoms.
- **"Lock Order = Alphabetical or Ascending PK":** Pick a canonical consistent ordering rule (smallest PK first, alphabetical table name first) and apply it everywhere to prevent deadlock cycles.
- **"Buffer Pool → Dirty Pages → Page Cleaner → Disk":** Data reads land in the buffer pool. Writes dirty pages there, and the page cleaner thread flushes them in LSN order.
- **"Deadlock: InnoDB Rolls Back the Lighter Side":** When InnoDB detects a cycle, it rolls back the transaction with fewer undo rows and returns `ERROR 1213`. Always catch and retry.

</TopicSection>

function detectDeadlock(waitGraph) {
  if (!(waitGraph instanceof Map)) throw new Error("waitGraph must be a Map");

  // Iterative cycle detection (out-degree <= 1 per transaction)
  const visited = new Set();

  for (const startNode of waitGraph.keys()) {
    if (visited.has(startNode)) continue;
    const pathIndex = new Map();
    const path = [];
    let current = startNode;

    while (current !== undefined) {
      if (!Number.isFinite(current) && typeof current !== "string") {
        throw new Error("Node IDs must be numbers or strings");
      }
      if (pathIndex.has(current)) {
        const cycleStart = pathIndex.get(current);
        return {
          hasDeadlock: true,
          cycle: path.slice(cycleStart).concat([current]).map(String)
        };
      }
      if (visited.has(current)) break;
      visited.add(current);
      pathIndex.set(current, path.length);
      path.push(current);
      current = waitGraph.get(current);
    }
  }
  return { hasDeadlock: false, cycle: null };
}

// No deadlock: T1 waits T2, T2 waits T3 (linear chain)

console.log(result.hasDeadlock, result.cycle); // true ['1','2','3','1']

function createLockManager() {
  // locks: Map<rowKey, Array<{trxId, mode}>>
  const locks = new Map();
  // waitQueue: Map<rowKey, Array<{trxId, mode}>>
  const waitQueue = new Map();

  function isCompatible(heldMode, requestedMode) {
    return heldMode === "S" && requestedMode === "S";
  }

  function acquireLock(trxId, rowKey, mode) {
    if (typeof trxId !== "number" || !Number.isFinite(trxId)) throw new Error("trxId must be a finite number");
    if (typeof rowKey !== "string" || rowKey.length === 0) throw new Error("rowKey must be non-empty string");
    if (mode !== "S" && mode !== "X") throw new Error('mode must be "S" or "X"');

    const held = locks.get(rowKey) ?? [];
    if (held.some(l => l.trxId === trxId && l.mode === mode)) {
      return { granted: true, waitingFor: null };
    }

    const queue = waitQueue.get(rowKey) ?? [];
    const conflicting = held.find(l => l.trxId !== trxId && !isCompatible(l.mode, mode));
    // Prevent new S locks from bypassing queued X waiters (FIFO fairness)
    const blockedByQueue = !held.some(l => l.trxId === trxId) && queue.length > 0;
    if (conflicting || blockedByQueue) {
      if (!waitQueue.has(rowKey)) waitQueue.set(rowKey, []);
      const q = waitQueue.get(rowKey);
      if (!q.some(w => w.trxId === trxId && w.mode === mode)) {
        q.push({ trxId, mode });
      }
      return { granted: false, waitingFor: conflicting ? conflicting.trxId : queue[0].trxId };
    }

    if (!locks.has(rowKey)) locks.set(rowKey, []);
    locks.get(rowKey).push({ trxId, mode });
    return { granted: true, waitingFor: null };
  }

  function releaseLocks(trxId) {
    if (typeof trxId !== "number" || !Number.isFinite(trxId)) throw new Error("trxId must be a finite number");
    const unblocked = new Set();

    // Remove trxId from all wait queues (e.g., if rolled back as deadlock victim)
    for (const [rowKey, queue] of waitQueue.entries()) {
      const cleaned = queue.filter(w => w.trxId !== trxId);
      waitQueue.set(rowKey, cleaned);
    }

    for (const [rowKey, held] of locks.entries()) {
      const remaining = held.filter(l => l.trxId !== trxId);
      if (remaining.length !== held.length) {
        locks.set(rowKey, remaining);
        const queue = waitQueue.get(rowKey) ?? [];
        const stillWaiting = [];
        for (let i = 0; i < queue.length; i++) {
          const waiter = queue[i];
          const conflict = remaining.find(l => l.trxId !== waiter.trxId && !isCompatible(l.mode, waiter.mode));
          if (!conflict && stillWaiting.length === 0) {
            if (!remaining.some(l => l.trxId === waiter.trxId && l.mode === waiter.mode)) {
              remaining.push({ trxId: waiter.trxId, mode: waiter.mode });
            }
            unblocked.add(waiter.trxId);
          } else {
            stillWaiting.push(waiter);
          }
        }
        waitQueue.set(rowKey, stillWaiting);
      }
    }
    return unblocked;
  }

  return { acquireLock, releaseLocks };
}

const lm = createLockManager();

// T1 acquires X lock on row:1
console.log(JSON.stringify(lm.acquireLock(1, "row:1", "X"))); // {granted:true,waitingFor:null}

// T2 tries X lock on same row — blocked

#### Key Takeaways

- **InnoDB is non-negotiable** for any transactional workload: it alone provides ACID, row locking, foreign keys, and crash recovery in MySQL.
- **MVCC enables non-blocking reads**: readers don't block writers and writers don't block readers—concurrent `SELECT` and `UPDATE` on the same row proceed using undo log versions.
- **`REPEATABLE READ` is MySQL's default and is stronger than the SQL standard**: InnoDB's next-key locking prevents phantom reads that the standard only prevents at `SERIALIZABLE`.
- **Deadlocks are normal and must be handled**: always catch `ERROR 1213` and retry; prevent deadlocks by using consistent lock ordering and keeping transactions short.
- **`innodb_flush_log_at_trx_commit = 1`** is the correct production setting for durability; never use `0` for data you cannot afford to lose.
- **The binary log and InnoDB redo log stay in sync via two-phase commit**, ensuring replication and point-in-time recovery are consistent with committed data.
