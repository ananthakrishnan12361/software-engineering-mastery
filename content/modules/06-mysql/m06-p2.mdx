<TopicSection id="m06-p2-sec-a" letter="A" title="Topic Introduction">

#### What is this?

**MySQL indexing, query optimization, and high-availability operations** turn a single-node InnoDB database into a predictable, low-latency production system. This part covers how InnoDB organizes data inside clustered and secondary B+Trees, how the optimizer selects access paths shown by `EXPLAIN`, how stored programs and views behave, and how to scale and protect clusters with GTID replication, partitioning, connection pooling, and hot backups.

#### Why does it exist & what problem does it solve?

Unindexed lookups, broken composite index prefixes, `UUIDv4` primary-key page splits, and `Using filesort` / `Using temporary` plans quickly saturate disk I/O and CPU. Similarly, poorly planned replication, unpooled connection storms, or untested logical dumps turn routine traffic spikes or hardware failures into prolonged outages. Mastering these internals gives you deterministic control over query latency and cluster recovery.

#### Where is it used in real-world software?

High-throughput OLTP SaaS platforms, multi-region read-replica topologies, e-commerce order archives (`PARTITION BY RANGE`), ProxySQL / MySQL Router pools, and automated Percona XtraBackup + binary log point-in-time recovery (PITR) pipelines.

<TopicAnchor id="m06-p2-topic-indexes" />

#### 1. Indexes: B+Tree Structure, Selectivity & Write Amplification

In InnoDB, every standard index is a **B+Tree** stored in 16 KB pages where internal nodes hold routing keys and leaf nodes hold sorted entries linked doubly for fast range scans. An index speeds up `WHERE`, `JOIN`, `ORDER BY`, and `GROUP BY` lookups from `O(n)` full table scans to `O(log n)` tree traversals.

Every index carries a **write amplification** cost: every `INSERT`, `UPDATE` on an indexed column, or `DELETE` must update all affected B+Trees (assisted by the InnoDB Change Buffer for non-unique secondary indexes). Prioritize high-selectivity columns (`cardinality / rows` close to 1) and drop unused or redundant indexes visible in `sys.schema_unused_indexes`.

<TopicAnchor id="m06-p2-topic-composite-indexes" />

#### 2. Composite Indexes: Leftmost Prefix Rule & Covering Indexes

A **composite index** `(a, b, c)` sorts rows first by `a`, then by `b` within equal `a`, then by `c` within equal `(a, b)`. Because of this lexicographical sort, MySQL follows the **leftmost prefix rule**: the index serves queries filtering on `(a)`, `(a, b)`, or `(a, b, c)`, but cannot use the B+Tree order for `WHERE b = 10` alone (unless MySQL 8.0's `Index Skip Scan` applies on very low-cardinality `a`).

A **range predicate** (`>`, `<`, `BETWEEN`) on column `b` stops further B+Tree equality matching on `c`, so put **equality columns first, range columns last** (`(tenant_id, status, created_at)`). When all columns in `SELECT`, `WHERE`, and `ORDER BY` exist inside the index, InnoDB performs a **covering index scan** (`Extra: Using index`) without touching the base table.

<TopicAnchor id="m06-p2-topic-clustered-indexes" />

#### 3. Clustered Indexes: InnoDB Primary Key Organization

<GlossaryTerm definition="An InnoDB B+Tree index whose leaf pages store the entire row data sorted by the Primary Key; every InnoDB table has exactly one clustered index.">Clustered index</GlossaryTerm> means the table *is* the primary key B+Tree: leaf pages hold the full row columns directly alongside the primary key. If you omit an explicit `PRIMARY KEY`, InnoDB picks the first `UNIQUE NOT NULL` index, or generates a hidden 6-byte `DB_ROW_ID` counter shared globally.

Because rows are physically ordered by the PK, **sequential inserts** (`AUTO_INCREMENT` or time-ordered `UUIDv7`) append cleanly at the right edge of the B+Tree with high page fill. By contrast, random `UUIDv4` primary keys scatter inserts across random 16 KB pages, causing frequent page splits, fragmentation, and poor Buffer Pool cache density.

<TopicAnchor id="m06-p2-topic-secondary-indexes" />

#### 4. Secondary Indexes: PK Pointer & Double Lookup Cost

Every non-primary index in InnoDB is a **secondary index** whose leaf nodes store `(indexed_columns, primary_key)` rather than a physical row pointer. This keeps secondary indexes stable when clustered pages split, because secondary entries only need updating if the PK itself changes.

However, a non-covering secondary index query incurs a **double lookup**: InnoDB first traverses the secondary B+Tree to find matching PKs, then probes the **clustered index** B+Tree for each PK to fetch the remaining columns. Keep your `PRIMARY KEY` compact (`BIGINT` = 8 bytes vs. 36-byte `CHAR(36)` UUID) because every single secondary index embeds a copy of the PK in every leaf entry.

<TopicAnchor id="m06-p2-topic-query-optimization" />

#### 5. Query Optimization: SARGable Predicates, Keyset Pagination & Join Order

**Query optimization** focuses on letting the optimizer use indexes and minimize rows examined. Always write **SARGable** predicates (`created_at >= '2026-11-01' AND created_at < '2026-12-01'`) instead of wrapping columns in functions (`DATE(created_at) = ...`), which disables B+Tree range scans unless you create a MySQL 8.0 functional index `((DATE(created_at)))`.

Replace deep `LIMIT 50 OFFSET 100000` (which scans and discards 100,000 rows) with **keyset pagination** (`WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 50`). Also avoid `SELECT *` so covering indexes remain eligible, and verify implicit type conversions (comparing a `VARCHAR` column to an integer literal silently forces a full table scan).

<TopicAnchor id="m06-p2-topic-explain" />

#### 6. EXPLAIN: Reading Access Types, Key Selection & Extra Flags

Running `EXPLAIN` (or `EXPLAIN FORMAT=TREE` / `EXPLAIN ANALYZE` in MySQL 8.0.18+) reveals how the optimizer plans to execute a query. The most important columns are `type` (access method, from best to worst: `system`, `const`, `eq_ref`, `ref`, `range`, `index`, `ALL`), `possible_keys`, `key` (chosen index), `rows` (estimated rows examined), and `filtered` (percentage surviving `WHERE`).

Watch the `Extra` column closely: `Using index` is great (covering index), whereas `Using filesort` (extra sort pass in `sort_buffer_size` or disk) and `Using temporary` (internal temp table for `GROUP BY` / `DISTINCT`) signal tuning opportunities. `EXPLAIN ANALYZE` actually executes the query and prints real `actual time` and `loops` per iterator.

<TopicAnchor id="m06-p2-topic-query-execution" />

#### 7. Query Execution: Parser, Optimizer, Volcano Iterators & Joins

During **query execution**, MySQL parses SQL into an AST, resolves table/column privileges, and passes the tree to the cost-based **Query Optimizer**, which estimates I/O and CPU costs using InnoDB index statistics (`mysql.innodb_index_stats`) and MySQL 8.0 histograms. Note that MySQL 8.0 **removed the legacy Query Cache** completely because its global mutex caused severe contention on multicore servers.

The execution engine uses an iterator model (Volcano-style `Init()` / `Read()` in MySQL 8.0) and chooses between **Index Nested-Loop Join** and **Hash Join** (added in MySQL 8.0.18+ for equi-joins lacking usable indexes, replacing the older Block Nested-Loop). Understanding `join_buffer_size` and `sort_buffer_size` prevents unexpected per-session memory spikes or disk spills.

<TopicAnchor id="m06-p2-topic-stored-procedures" />

#### 8. Stored Procedures: Routines, IN/OUT Parameters & Trade-Offs

A **stored procedure** (`CREATE PROCEDURE ...`) is a named SQL/procedural block stored in the data dictionary and executed via `CALL proc_name(...)`. It supports `IN`, `OUT`, and `INOUT` parameters, local variables (`DECLARE`), `IF`/`WHILE` control flow, cursors, and transaction control (`COMMIT` / `ROLLBACK`), whereas stored **functions** (`CREATE FUNCTION`) return a single value for use inside SQL expressions and cannot commit transactions.

In modern backend architectures, keep business logic in version-controlled application services rather than heavy stored procedures, because MySQL procedures lack rich unit-testing/debugging tooling and scale vertically on the primary database CPU. Reserve them for tightly scoped batch maintenance or legacy DBA interfaces.

<TopicAnchor id="m06-p2-topic-triggers" />

#### 9. Triggers: BEFORE/AFTER Row Hooks & Replication Caveats

A **trigger** (`CREATE TRIGGER ... BEFORE|AFTER INSERT|UPDATE|DELETE ON tbl FOR EACH ROW`) automatically executes SQL whenever a row is modified. `BEFORE` triggers can validate or normalize `NEW.col` values before the row is written, while `AFTER` triggers run post-write for audit logging or denormalized counters.

Use triggers sparingly: they add hidden latency to every DML row, cannot issue `COMMIT`/`ROLLBACK`, and are invisible to application developers reading service code. Under `binlog_format = ROW`, primary trigger changes are replicated as row events (so replicas must not re-fire triggers), and `gh-ost` avoids triggers altogether during online schema changes.

<TopicAnchor id="m06-p2-topic-views" />

#### 10. Views: Virtual Tables, MERGE vs. TEMPTABLE & Security

A **view** (`CREATE VIEW v AS SELECT ...`) is a stored query exposed like a virtual table to simplify joins or restrict exposed columns. MySQL evaluates views using either the **`MERGE`** algorithm (folds the view's `WHERE` and `SELECT` directly into the outer query so indexes work normally) or **`TEMPTABLE`** (materializes the view into an internal temporary table first, needed when the view uses `GROUP BY`, `DISTINCT`, `UNION`, or aggregates).

Always specify **`SQL SECURITY INVOKER`** (or audit `DEFINER` carefully) when creating views so permissions are checked against the calling user rather than escalating to a privileged `DEFINER` account. Note that standard MySQL views are not persisted on disk—unlike PostgreSQL materialized views, MySQL requires summary tables or scheduled refreshes if you need precomputed materialization.

<TopicAnchor id="m06-p2-topic-replication" />

#### 11. Replication: Binary Logs, GTIDs, Async vs. Semi-Sync & Group Replication

**MySQL replication** streams changes from a **source** (primary) to one or more **replicas** via the **binary log** (`binlog_format = ROW`). Each replica runs an I/O receiver thread that copies binlog events into a local **relay log**, and an SQL applier thread (or parallel `replica_parallel_workers`) that replays them.

Enable **GTID** (`gtid_mode = ON`) so every transaction gets a globally unique `server_uuid:sequence` identifier, making failover and replica repointing automatic without fragile binlog file/position math. Choose **asynchronous** replication for lowest primary latency, **semi-synchronous** (`rpl_semi_sync`) to wait for at least one replica ACK before returning `COMMIT`, or **Group Replication** (InnoDB Cluster) for Paxos-based multi-node automatic failover.

<TopicAnchor id="m06-p2-topic-partitioning" />

#### 12. Partitioning: RANGE, LIST, HASH & Pruning Mechanics

**Table partitioning** (`PARTITION BY RANGE|LIST|HASH`) splits one logical InnoDB table into multiple physical `.ibd` sub-tables managed transparently by the server. **Partition pruning** allows the optimizer to skip scanning irrelevant partitions when the query includes the partition key in its `WHERE` clause (e.g., `WHERE created_at >= '2026-11-01'`).

Partitioning shines for **time-series retention**: dropping a 30-day-old partition via `ALTER TABLE events DROP PARTITION p_2025_10` reclaims gigabytes in milliseconds with zero row-by-row `DELETE` or undo bloat. Critical MySQL rule: **every unique/primary key on a partitioned table must include all columns of the partitioning expression**, and avoid creating hundreds of partitions per table (keep under ~50–100) to prevent open-file and metadata overhead.

<TopicAnchor id="m06-p2-topic-performance-tuning" />

#### 13. Performance Tuning: Slow Query Log, Performance Schema & Memory Buffers

Effective **performance tuning** starts with measurement: enable the **Slow Query Log** (`slow_query_log = ON`, `long_query_time = 0.2`, `log_queries_not_using_indexes = ON` in staging) and inspect `performance_schema.events_statements_summary_by_digest` (or `sys.statements_with_runtimes_in_95th_percentile`) to rank queries by total latency and rows examined.

Check global vs. per-thread memory carefully: `innodb_buffer_pool_size` (70–80% of RAM) is global and shared, whereas `sort_buffer_size`, `join_buffer_size`, and `read_buffer_size` are **allocated per active session/query**. Over-inflating per-thread buffers causes OOM kills under concurrency spikes.

<TopicAnchor id="m06-p2-topic-connection-management" />

#### 14. Connection Management: Thread-per-Connection, Thread Cache & ProxySQL

Community MySQL defaults to a **one-OS-thread-per-connection** model. While `thread_cache_size` recycles idle threads to save thread creation overhead, having 3,000 active concurrent threads causes severe CPU context-switching and InnoDB mutex contention (`Threads_running` spiking far above `2 * vCPU`).

Cap `max_connections` realistically, configure `wait_timeout` / `interactive_timeout` so abandoned idle clients are reaped, and place **ProxySQL** or **MySQL Router** in front of the cluster. A pool multiplexes thousands of application connections onto a small, stable pool of backend MySQL threads while also handling read/write splitting across replicas.

<TopicAnchor id="m06-p2-topic-backup-and-recovery" />

#### 15. Backup and Recovery: mysqldump, MySQL Shell Dump, XtraBackup & PITR

Backups fall into **logical** (`mysqldump --single-transaction` or parallel **MySQL Shell** `util.dumpInstance()`), which export SQL/TSV for portable restores across versions, and **physical hot backups** (**Percona XtraBackup** or MySQL Enterprise Backup), which copy `.ibd` pages online while streaming InnoDB redo logs—restoring multi-terabyte databases 10x faster than SQL replay.

To achieve **Point-in-Time Recovery (PITR)**, combine a consistent full backup (recording its `GTID` / binlog position) with archived **binary logs**. Restore the full backup first, then replay binary logs with `mysqlbinlog --stop-datetime="..."` right up to the second before an accidental `DROP TABLE` or bad `UPDATE`. Always automate periodic restore drills onto an isolated instance.

</TopicSection>

<TopicSection id="m06-p2-sec-c" letter="C" title="Internal Working & Architecture">

#### Clustered vs. Secondary Index Traversal in InnoDB

In InnoDB, every table's data lives inside the **clustered B+Tree** ordered by `PRIMARY KEY`. A primary-key lookup (`WHERE id = 42`) descends the clustered B+Tree once (typically 3–4 levels for 100M rows) and reads the full row directly from the leaf page.

A **secondary index** (`INDEX (email)`) is a separate B+Tree whose leaf pages contain `(email, id)`. When a query executes `SELECT total_cents FROM orders WHERE email = 'a@b.com'`, InnoDB first descends `idx_email` to retrieve `id = 42`, then descends the clustered B+Tree for `id = 42` to read `total_cents` (**double lookup**). Extending the index to `(email, total_cents)` turns it into a **covering index**, eliminating the second B+Tree descent completely.

#### Example 1: InnoDB Clustered & Secondary Index Lookup Simulator (`createInnoDbIndexSimulator`)

This simulator models InnoDB's two B+Trees: a **clustered index** holding full rows keyed by `PK`, and a **secondary index** `(col, ...coveringCols, PK)`. Watch how a non-covering secondary lookup performs two B+Tree lookups (`clusteredReads > 0`), whereas a covering index returns `clusteredReads: 0`.

<CodeBlock lang="javascript" runnable title="InnoDB Clustered vs. Secondary Index Simulator" code={`
function createInnoDbIndexSimulator() {
  const clustered = new Map(); // pk -> full row object
  const secondaryIndexes = new Map(); // indexName -> { cols: string[], entries: Array<{ keyValues, pk }> }

  function insertRow(pk, row) {
    if (!Number.isInteger(pk) || pk < 1) throw new TypeError("pk must be a positive integer");
    if (row == null || typeof row !== "object" || Array.isArray(row)) {
      throw new TypeError("row must be a non-null plain object");
    }
    if (clustered.has(pk)) throw new Error("Duplicate primary key: " + pk);
    clustered.set(pk, { ...row, id: pk });

    for (const idx of secondaryIndexes.values()) {
      idx.entries.push({
        keyValues: idx.cols.map((c) => row[c]),
        pk
      });
    }
  }

  function createSecondaryIndex(name, cols) {
    if (typeof name !== "string" || name.trim().length === 0) throw new TypeError("Index name required");
    if (!Array.isArray(cols) || cols.length === 0) throw new TypeError("cols must be a non-empty array");
    const entries = [];
    for (const [pk, row] of clustered.entries()) {
      entries.push({ keyValues: cols.map((c) => row[c]), pk });
    }
    secondaryIndexes.set(name, { cols: [...cols], entries });
  }

  function queryBySecondary(indexName, filterCol, filterVal, selectCols) {
    const idx = secondaryIndexes.get(indexName);
    if (!idx) throw new Error("Unknown index: " + indexName);
    if (!Array.isArray(selectCols) || selectCols.length === 0) {
      throw new TypeError("selectCols must be a non-empty array");
    }
    if (idx.cols[0] !== filterCol) {
      return { accessType: "ALL", covering: false, secondaryReads: 0, clusteredReads: clustered.size, rows: [] };
    }

    const indexColSet = new Set([...idx.cols, "id"]);
    const covering = selectCols.every((c) => indexColSet.has(c));

    let secondaryReads = 0;
    let clusteredReads = 0;
    const out = [];

    for (const entry of idx.entries) {
      secondaryReads++;
      if (entry.keyValues[0] === filterVal) {
        if (covering) {
          const proj = {};
          for (const c of selectCols) {
            proj[c] = c === "id" ? entry.pk : entry.keyValues[idx.cols.indexOf(c)];
          }
          out.push(proj);
        } else {
          clusteredReads++;
          const full = clustered.get(entry.pk);
          const proj = {};
          for (const c of selectCols) proj[c] = full[c];
          out.push(proj);
        }
      }
    }

    return {
      accessType: "ref",
      covering,
      secondaryReads,
      clusteredReads,
      rows: out
    };
  }

  return { insertRow, createSecondaryIndex, queryBySecondary };
}

const db = createInnoDbIndexSimulator();
db.insertRow(101, { email: "ada@acme.io", totalCents: 4900, status: "paid" });
db.insertRow(102, { email: "bob@acme.io", totalCents: 1200, status: "pending" });
db.createSecondaryIndex("idx_email_total", ["email", "totalCents"]);

console.log("Covering lookup:", JSON.stringify(db.queryBySecondary("idx_email_total", "email", "ada@acme.io", ["id", "totalCents"])));
console.log("Double lookup:", JSON.stringify(db.queryBySecondary("idx_email_total", "email", "ada@acme.io", ["id", "totalCents", "status"])));
console.log("Broken prefix:", JSON.stringify(db.queryBySecondary("idx_email_total", "totalCents", 4900, ["id"])));
`} />

#### Example 2: MySQL `EXPLAIN` & Composite Index Access Analyzer (`analyzeMysqlExplain`)

This analyzer inspects a MySQL `EXPLAIN` plan node (`type`, `rows`, `filtered`, `extra`) and surfaces optimization warnings for full table scans (`ALL`), full index scans (`index`), `Using filesort`, `Using temporary`, and low filter selectivity.

<CodeBlock lang="javascript" runnable title="MySQL EXPLAIN Plan Analyzer" code={`
function analyzeMysqlExplain(plan) {
  if (plan == null || typeof plan !== "object" || Array.isArray(plan)) {
    throw new TypeError("plan must be a non-null plain object");
  }
  const { type, rows, filtered = 100, extra = "" } = plan;
  const validTypes = new Set(["system", "const", "eq_ref", "ref", "range", "index", "ALL"]);
  if (!validTypes.has(type)) throw new TypeError("Invalid EXPLAIN type: " + type);
  if (!Number.isInteger(rows) || rows < 0) throw new TypeError("rows must be a non-negative integer");
  if (!Number.isFinite(filtered) || filtered < 0 || filtered > 100) {
    throw new TypeError("filtered must be between 0 and 100");
  }
  if (typeof extra !== "string") throw new TypeError("extra must be a string");

  const findings = [];
  if (type === "ALL" && rows > 1000) {
    findings.push("FULL_TABLE_SCAN: Add selective index on WHERE/JOIN columns");
  } else if (type === "index" && rows > 1000) {
    findings.push("FULL_INDEX_SCAN: Narrow range or fix leftmost composite prefix");
  }
  if (extra.includes("Using filesort")) {
    findings.push("FILESORT: Align ORDER BY with composite index prefix");
  }
  if (extra.includes("Using temporary")) {
    findings.push("TEMP_TABLE: Align GROUP BY/DISTINCT with index or raise tmp_table_size");
  }
  if (filtered < 20 && rows > 500) {
    findings.push("LOW_FILTER_SELECTIVITY: Extend composite index with trailing filter columns");
  }

  const extraTokens = extra.split(";").map((s) => s.trim());

  return {
    type,
    rows,
    covering: extraTokens.includes("Using index"),
    healthy: findings.length === 0,
    findings
  };
}

console.log("Slow plan:", JSON.stringify(analyzeMysqlExplain({ type: "ALL", rows: 250000, filtered: 5, extra: "Using where; Using filesort" })));
console.log("Optimal plan:", JSON.stringify(analyzeMysqlExplain({ type: "ref", rows: 12, filtered: 100, extra: "Using index" })));
`} />

#### How `analyzeMysqlExplain` Evaluates a Query Plan

1. **Validate Plan Inputs:** Confirms `type` is one of MySQL's valid access paths (`system` through `ALL`), `rows` is a non-negative integer, and `filtered` falls within `0..100`.
2. **Detect Full Scans (`ALL` / `index`):** Flags `type === "ALL"` over 1,000 rows as `FULL_TABLE_SCAN` and `type === "index"` as `FULL_INDEX_SCAN` when a leftmost prefix is missing.
3. **Inspect `Extra` Flags:** Detects `Using filesort` (sort not satisfied by B+Tree order) and `Using temporary` (materialized temp table for grouping), while recording `covering: true` when `Using index` appears.
4. **Check Post-Index Filter Efficiency:** Flags `filtered < 20` on scans over 500 rows (`LOW_FILTER_SELECTIVITY`), signaling that InnoDB reads many rows only to discard most of them after the clustered lookup.

</TopicSection>

<TopicSection id="m06-p2-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Eliminating `Using filesort` on Multi-Tenant Dashboards

A SaaS orders endpoint ran `WHERE tenant_id = ? AND status = ? ORDER BY created_at DESC LIMIT 25` against 80M rows, stalling on `Using filesort`. Creating a composite covering index `(tenant_id, status, created_at DESC, total_cents)` dropped p99 latency from 1.4s to 2ms with `Using index`.

#### Scenario 2: Instant Retention Drops with Range Partitioning

An analytics ingestion table growing by 50M rows per month switched from nightly `DELETE` batches (which caused replication lag and undo bloat) to monthly `PARTITION BY RANGE (TO_DAYS(created_at))` partitions. Retiring old months via `ALTER TABLE ... DROP PARTITION` now completes in milliseconds.

#### Scenario 3: Zero-Lag Read Scaling & PITR Protection

An e-commerce cluster runs GTID-based asynchronous replication with ProxySQL splitting `SELECT` traffic across two read replicas and Percona XtraBackup taking nightly physical snapshots plus archived binary logs for sub-minute PITR.

</TopicSection>

<TopicSection id="m06-p2-sec-g" letter="G" title="Common Mistakes">

- **Using Random `UUIDv4` as an InnoDB Primary Key:** Random PKs fragment the clustered B+Tree, bloat every secondary index (which embeds the PK), and thrash Buffer Pool pages. Use `AUTO_INCREMENT BIGINT` or sequential `UUIDv7` (`BINARY(16)`).
- **Putting Range Columns Before Equality Columns in Composite Indexes:** An index on `(created_at, tenant_id)` cannot use `tenant_id` for a narrow lookup when `created_at` has a `>=` range filter. Always order `(equality_cols, range_or_sort_col)`.
- **Using `OFFSET` for Deep Pagination:** `LIMIT 20 OFFSET 200000` forces InnoDB to scan and discard 200,000 rows; use keyset cursor pagination instead.
- **Over-Sizing Per-Thread Buffers (`sort_buffer_size`, `join_buffer_size`):** Setting per-connection buffers to 64 MB globally can exhaust RAM and trigger the OS OOM killer when hundreds of queries run concurrently.
- **Skipping Restore Drills on Logical or Physical Backups:** Untested backups frequently fail during incidents due to missing binary logs, GTID gaps, or corrupted archive permissions.

</TopicSection>

<TopicSection id="m06-p2-sec-h" letter="H" title="Best Practices">

- Design compact, monotonically increasing primary keys (`BIGINT UNSIGNED AUTO_INCREMENT` or `UUIDv7`) to keep InnoDB clustered and secondary indexes dense.
- Apply the **Equality-First, Range/Sort-Last** rule on composite indexes and verify `Using index` with `EXPLAIN ANALYZE`.
- Enable `gtid_mode = ON` and `binlog_format = ROW` across all primary/replica nodes for safe failover and consistent replication.
- Place **ProxySQL** or **MySQL Router** between application pods and MySQL so `Threads_running` stays proportional to CPU cores.
- Pair physical hot backups (`Percona XtraBackup` or `MySQL Shell` parallel dumps) with continuous binary log archiving and automated monthly PITR restore tests.

</TopicSection>

<TopicSection id="m06-p2-sec-i" letter="I" title="Performance & Scalability">

- **Memory Allocation Split:** Dedicate 70–80% of host RAM to `innodb_buffer_pool_size` (shared), while keeping per-session buffers (`sort_buffer_size`, `join_buffer_size`) modest (256 KB–4 MB) globally and raising them only per session when needed.
- **Parallel Replication (`replica_parallel_workers`):** Configure `replica_parallel_type = LOGICAL_CLOCK` with multiple applier workers on MySQL 8.0 replicas so write bursts on the primary do not cause single-threaded replica lag.

</TopicSection>

<TopicSection id="m06-p2-sec-j" letter="J" title="Security Considerations">

- **View & Procedure Privilege Escalation:** Always declare `SQL SECURITY INVOKER` on Views and Stored Procedures unless elevated `DEFINER` privileges are strictly required and audited, preventing low-privilege callers from reading restricted tables through a view.
- **Replication & Backup Encryption:** Enforce `REQUIRE SSL` / TLS 1.3 on replication user accounts (`CHANGE REPLICATION SOURCE TO ... SOURCE_SSL=1`), and encrypt both XtraBackup/dump archives and archived binary logs with KMS keys.

</TopicSection>

<TopicSection id="m06-p2-sec-k" letter="K" title="Comparisons & Decision Tables">

#### Table K.1 — InnoDB Index Types & Lookup Cost

| Index Type | Leaf Contents | Lookup Cost | Best Use Case |
| --- | --- | --- | --- |
| **Clustered (PK)** | PK + full row columns | 1 B+Tree traversal | Primary key lookups & sequential inserts |
| **Secondary (Non-Covering)** | Indexed cols + PK | 2 B+Tree traversals (double lookup) | Filtering when full row columns are needed |
| **Covering Composite** | Indexed cols + `SELECT` cols + PK | 1 secondary B+Tree traversal | High-QPS `SELECT` queries (`Using index`) |

#### Table K.2 — MySQL `EXPLAIN` `type` Access Paths (Best to Worst)

| `type` | Meaning | Performance | Action Needed |
| --- | --- | --- | --- |
| `system` / `const` | 0 or 1 matching row via PK/`UNIQUE` | Fastest | None |
| `eq_ref` / `ref` | 1 or few rows per key via index | Fast (OLTP ideal) | Verify `Extra` has no `Using filesort` |
| `range` | Index range scan (`>`, `BETWEEN`, `IN`) | Good | Keep range narrow; avoid leading wildcards |
| `index` / `ALL` | Full index scan or full table scan | Slow on large tables | Add selective index or fix leftmost prefix |

#### Table K.3 — MySQL Backup & Replication Options

| Mechanism | Type | Speed / RPO | Best For |
| --- | --- | --- | --- |
| **Percona XtraBackup** | Physical hot backup | Very fast; PITR with binlogs | Multi-TB production InnoDB clusters |
| **MySQL Shell (`util.dumpInstance`)** | Parallel logical dump | Fast; version-portable | Cross-version upgrades & cloud migrations |
| **GTID Async Replication** | Asynchronous binlog | Lowest primary latency; small RPO | Read-scaling replicas |
| **Semi-Sync / Group Replication** | ACK / Paxos consensus | Zero-RPO failover; higher write RTT | High-availability primary failover |

</TopicSection>

<TopicSection id="m06-p2-sec-l" letter="L" title="Tips to Remember (Mnemonics & Mental Models)">

- **"Equality First, Range/Sort Last":** Order composite index columns as `(exact =, IN, range >/< or ORDER BY)` so the leftmost prefix stays intact.
- **"Every Secondary Index Carries the PK":** A bloated 36-byte UUID PK bloats every secondary index leaf page; keep PKs compact and sequential.
- **"`Using index` = Good; `Using filesort` / `Using temporary` = Check Prefix":** Read `EXPLAIN` `type` and `Extra` together before tuning memory buffers.
- **"Full Backup + Binary Logs = PITR":** Never rely on snapshots alone; archived binlogs let you recover to the exact second before human error.

</TopicSection>

#### Key Takeaways

- **Clustered vs. Secondary Indexes:** InnoDB stores rows inside the PK B+Tree; secondary indexes store `(key, PK)` and incur a double lookup unless the index is **covering** (`Using index`).
- **Composite Index Design:** Put equality columns first and range/sort columns last; keep primary keys compact and sequential (`BIGINT` or `UUIDv7`).
- **Execution & Optimization:** Use `EXPLAIN ANALYZE` to catch `ALL` scans, `Using filesort`, and `Using temporary`, and replace deep `OFFSET` with keyset pagination.
- **Replication & Partitioning:** Use `GTID` + `ROW` binlog with `LOGICAL_CLOCK` parallel workers, and use `PARTITION BY RANGE` for instant retention drops.
- **Pooling & Recovery:** Protect thread and memory budgets with ProxySQL, and test XtraBackup + binary log PITR restores continuously.
