<TopicSection id="m05-p3-sec-a" letter="A" title="Topic Introduction">

#### What is this?

PostgreSQL goes far beyond plain tables and ad-hoc `SELECT` queries. It provides **views** and **materialized views** for reusable/cached projections, **functions** and **stored procedures** for server-side logic, **triggers** and rich **constraints** (including `EXCLUDE USING` and `DEFERRABLE`) for automated invariants, and native **`JSON` / `JSONB`** types with **GIN** indexing for semi-structured payloads.

#### Why does it exist & what problem does it solve?

Without these primitives, teams duplicate complex reporting queries across services, hit race conditions on calendar overlaps, leak tenant rows through `SECURITY DEFINER` views, or store schemaless blobs that require slow sequential scans to filter. Knowing when to push logic into PostgreSQL—and when *not* to—keeps data consistent and fast.

#### Where is it used in real-world software?

Analytics dashboards (`MATERIALIZED VIEW`), booking/reservation engines (`EXCLUDE USING gist`), audit trails (`AFTER` triggers), batch backfill workers (`CREATE PROCEDURE` with intermediate `COMMIT`), and webhook/feature-flag stores (`JSONB` + `GIN`).

</TopicSection>

<TopicSection id="m05-p3-sec-b" letter="B" title="Fundamentals (Simple Mental Models)">

<TopicAnchor id="m05-p3-topic-views" />

#### 1. Views: Virtual Query Abstractions, Updatable Views & Security Invoker

A <GlossaryTerm definition="A named virtual table backed by a stored SELECT query that executes dynamically on each read without storing separate rows.">view</GlossaryTerm> (`CREATE VIEW active_orders AS SELECT ...`) acts as a saved virtual table: reading from it runs the underlying `SELECT` against live base tables every time, so results are never stale. Simple single-table views are even automatically updatable.

By default in older PostgreSQL versions, views checked permissions as the view *owner* (`SECURITY DEFINER`-like), which could bypass Row-Level Security (RLS). Since PostgreSQL 15, adding `WITH (security_invoker = true)` enforces the **caller's** permissions and RLS policies.

<TopicAnchor id="m05-p3-topic-materialized-views" />

#### 2. Materialized Views: Persisted Query Snapshots & REFRESH CONCURRENTLY

A **materialized view** (`CREATE MATERIALIZED VIEW ...`) executes an expensive query once and **persists the resulting rows on disk** like a real table, allowing B-tree or GIN indexes on pre-aggregated columns. Reads are instant, at the trade-off of staleness between refreshes.

Running `REFRESH MATERIALIZED VIEW` locks out readers with `ACCESS EXCLUSIVE`; adding a `UNIQUE` index on the materialized view enables **`REFRESH MATERIALIZED VIEW CONCURRENTLY`**, which computes a diff and swaps rows while readers continue querying smoothly.

<TopicAnchor id="m05-p3-topic-functions" />

#### 3. Functions: PL/pgSQL & SQL Functions, Volatility & Transaction Rules

PostgreSQL **functions** (`CREATE FUNCTION ... RETURNS ...`) execute inside the caller's single transaction, so they **cannot** run `COMMIT` or `ROLLBACK`. They can be used directly inside `SELECT`, `WHERE`, and expression indexes.

Always label function volatility accurately: **`IMMUTABLE`** (same inputs always return same output, required for expression indexes), **`STABLE`** (consistent within one statement/snapshot, like `now()`), or **`VOLATILE`** (default; can mutate data or vary per row, like `random()`).

<TopicAnchor id="m05-p3-topic-stored-procedures" />

#### 4. Stored Procedures: CALL, Explicit COMMIT/ROLLBACK & Batch Loops

Added in PostgreSQL 11, **stored procedures** (`CREATE PROCEDURE ...`) are invoked with `CALL proc_name(...)` rather than `SELECT`. Unlike functions, procedures can issue **`COMMIT` and `ROLLBACK` inside loops** when not already wrapped in an outer transaction block.

This makes procedures ideal for multi-million-row batch backfills or archival jobs where committing every 5,000 rows releases row locks and lets `VACUUM` reclaim dead tuples incrementally.

<TopicAnchor id="m05-p3-topic-triggers" />

#### 5. Triggers: BEFORE/AFTER, ROW vs. STATEMENT & Audit/Sync Patterns

A **trigger** automatically invokes a trigger function (`RETURNS trigger`) before or after `INSERT`, `UPDATE`, `DELETE`, or `TRUNCATE`. **`BEFORE` row triggers** can inspect/modify `NEW` values (such as auto-updating `updated_at`) before constraints run, whereas **`AFTER` triggers** record immutable audit logs once the row change is finalized.

For bulk updates touching 10,000 rows, `FOR EACH STATEMENT` with transition tables (`REFERENCING NEW TABLE AS inserted_rows`) avoids firing 10,000 separate row-trigger invocations.

<TopicAnchor id="m05-p3-topic-constraints" />

#### 6. Constraints: CHECK, UNIQUE, Exclusion (EXCLUDE USING), Deferrable & NOT VALID

Beyond `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, and `CHECK`, PostgreSQL supports **Exclusion Constraints** (`EXCLUDE USING gist (room_id WITH =, during WITH &&)`), which guarantee no two rows overlap in time or space—preventing double-bookings at the storage layer.

Foreign keys and `UNIQUE` constraints can be marked **`DEFERRABLE INITIALLY DEFERRED`** to check invariants at `COMMIT` instead of per-statement (useful for cyclic swaps), while `CHECK (...) NOT VALID` + `VALIDATE CONSTRAINT` adds rules to huge live tables without blocking writes.

<TopicAnchor id="m05-p3-topic-json" />

#### 7. JSON: Text-Preserving Storage, Key Order & Serialization Semantics

PostgreSQL's **`json`** data type stores an exact copy of the input UTF-8 text, preserving **whitespace**, **key ordering**, and **duplicate keys**. Because it validates syntax on write without decomposing the tree, `INSERT` is slightly faster than `jsonb`.

However, every query extracting a field (`payload->>'tier'`) must re-parse the raw text from scratch, and `json` does **not** support `GIN` indexing or equality (`=`) operators cleanly—making `json` suitable mostly for raw audit/webhook archival when exact formatting must stay untouched.

<TopicAnchor id="m05-p3-topic-jsonb" />

#### 8. JSONB: Binary Decomposed Storage, GIN Indexes & Containment (@>)

<GlossaryTerm definition="PostgreSQL's binary decomposed JSON storage format that deduplicates keys, strips whitespace, and supports GIN inverted indexing and @> containment queries.">JSONB</GlossaryTerm> parses JSON into a decomposed binary format on write: it strips whitespace, deduplicates keys (last key wins), sorts keys for fast lookup, and supports **GIN** indexes.

With a GIN index (`CREATE INDEX ... ON events USING GIN (payload jsonb_path_ops)`), containment queries like `WHERE payload @> '{"plan": "pro"}'` run in milliseconds even over tens of millions of flexible documents.

</TopicSection>

#### Example 2: View vs. Materialized View Concurrent Refresh Simulator (`createMaterializedViewEngine`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models live VIEW vs cached MATERIALIZED VIEW with CONCURRENTLY unique-key diff requirement
function createMaterializedViewEngine({ baseRows = [], uniqueKey }) {
  if (!Array.isArray(baseRows)) throw new TypeError("baseRows must be an array");

  let liveTable = baseRows.map((r) => ({ ...r }));
  let snapshot = liveTable.map((r) => ({ ...r }));
  let refreshCount = 1;

  return {
    insertBaseRow(row) {
      if (!row || typeof row !== "object") throw new TypeError("row must be an object");
      liveTable.push({ ...row });
    },
    queryLiveView() {
      return liveTable.map((r) => ({ ...r }));
    },
    queryMaterializedView() {
      return snapshot.map((r) => ({ ...r }));
    },
    refresh({ concurrently = false } = {}) {
      if (concurrently && !uniqueKey) {
        throw new Error("UniqueIndexRequired: CONCURRENTLY requires a uniqueKey index");
      }
      if (concurrently) {
        const seen = new Set();
        for (const r of liveTable) {
          const k = r[uniqueKey];
          if (k === undefined || k === null || seen.has(k)) {
            throw new Error("UniqueViolation: duplicate or null key in concurrent refresh");
          }
          seen.add(k);
        }
      }
      snapshot = liveTable.map((r) => ({ ...r }));
      refreshCount += 1;
      return { refreshCount, concurrently, rowCount: snapshot.length };
    }
  };
}

const mv = createMaterializedViewEngine({ baseRows: [{ id: 1, rev: 100 }], uniqueKey: "id" });
mv.insertBaseRow({ id: 2, rev: 250 });
console.log("Stale MatView:", mv.queryMaterializedView());
console.log("Fresh Live View:", mv.queryLiveView());
console.log("Concurrent Refresh:", mv.refresh({ concurrently: true }));
console.log("Updated MatView:", mv.queryMaterializedView());`}
/>

#### Example 3: JSON vs. JSONB Storage & GIN Containment Index (`createJsonbGinStore`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models JSONB key deduplication + GIN inverted index supporting @> containment queries
function createJsonbGinStore() {
  const docs = [];
  const ginIndex = new Map(); // "key:jsonValue" -> Set(docId)

  function indexEntries(doc, prefix = "") {
    const tokens = [];
    for (const key of Object.keys(doc).sort()) {
      const val = doc[key];
      const path = prefix ? prefix + "." + key : key;
      if (val && typeof val === "object" && !Array.isArray(val)) {
        tokens.push(...indexEntries(val, path));
      } else {
        tokens.push(path + "=" + JSON.stringify(val));
      }
    }
    return tokens;
  }

  function containsPattern(doc, pattern) {
    for (const [k, v] of Object.entries(pattern)) {
      if (!(k in doc)) return false;
      if (v && typeof v === "object" && !Array.isArray(v)) {
        if (!doc[k] || typeof doc[k] !== "object" || !containsPattern(doc[k], v)) return false;
      } else if (doc[k] !== v) {
        return false;
      }
    }
    return true;
  }

  return {
    insert(rawJsonText) {
      if (typeof rawJsonText !== "string") throw new TypeError("rawJsonText must be JSON string");
      const parsed = JSON.parse(rawJsonText); // JSONB deduplicates duplicate keys (last key wins)
      if (!parsed || typeof parsed !== "object" || Array.isArray(parsed)) {
        throw new TypeError("Document must be a JSON object");
      }
      const id = docs.length + 1;
      docs.push({ id, jsonText: rawJsonText, jsonb: parsed });
      for (const tok of indexEntries(parsed)) {
        if (!ginIndex.has(tok)) ginIndex.set(tok, new Set());
        ginIndex.get(tok).add(id);
      }
      return { id, jsonb: parsed };
    },
    queryContainment(pattern) {
      if (!pattern || typeof pattern !== "object" || Array.isArray(pattern)) {
        throw new TypeError("pattern must be a JSON object");
      }
      const tokens = indexEntries(pattern);
      let candidateIds = null;
      for (const tok of tokens) {
        const postings = ginIndex.get(tok) || new Set();
        candidateIds = candidateIds === null
          ? new Set(postings)
          : new Set([...candidateIds].filter((id) => postings.has(id)));
      }
      const ids = candidateIds ? [...candidateIds] : docs.map((d) => d.id);
      return ids.map((id) => docs[id - 1]).filter((d) => containsPattern(d.jsonb, pattern));
    }
  };
}

const store = createJsonbGinStore();
store.insert('{ "tier": "free", "tier": "pro", "region": "us" }');
store.insert('{ "tier": "free", "region": "eu" }');
console.log("JSONB @> pro:", store.queryContainment({ tier: "pro" }));`}
/>

<TopicSection id="m05-p3-sec-e" letter="E" title="Step-by-Step Walkthrough">

Let us trace how `createJsonbGinStore` executes `insert` and `queryContainment`:

1. **Parsing & Key Deduplication (`insert`)**: `JSON.parse` parses `'{ "tier": "free", "tier": "pro", "region": "us" }'`, collapsing duplicate `"tier"` keys to `"pro"` (just like PostgreSQL `jsonb`, whereas `json` keeps the raw string in `jsonText`).
2. **GIN Posting Lists**: `indexEntries` extracts `region="us"` and `tier="pro"` and appends document `id = 1` to each token's `Set` in `ginIndex`.
3. **Containment (`@>`) Intersection**: `queryContainment({ tier: "pro" })` intersects the GIN posting lists (`candidateIds = {1}`) and verifies `containsPattern`, returning doc `1` in `O(postings)` instead of scanning all rows.

</TopicSection>

<TopicSection id="m05-p3-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Double-Booking Prevention via `EXCLUDE USING gist`

Hotel, meeting-room, and clinic schedulers enforce `EXCLUDE USING gist (room_id WITH =, during WITH &&)` directly in PostgreSQL—eliminating race conditions even when two requests book overlapping slots at the exact same millisecond.

#### Scenario 2: Multi-Million-Row Backfill via `CREATE PROCEDURE`

Instead of running one giant `UPDATE` holding locks for 40 minutes, a PL/pgSQL `PROCEDURE` iterates in 5,000-row keyset batches and calls `COMMIT` after each batch, keeping replication lag and WAL spikes bounded.

</TopicSection>

<TopicSection id="m05-p3-sec-g" letter="G" title="Common Mistakes">

- **Forgetting `security_invoker = true` on Views:** Standard views run with the view creator's privileges by default, which can accidentally expose cross-tenant rows even when Row-Level Security (RLS) is enabled on the underlying table.
- **Indexing `JSONB` with `B-tree` for `@>` containment:** B-tree supports `=` and `<`, not `@>` containment—you must use `USING GIN (col)` (or `jsonb_path_ops` for smaller/faster `@>` indexes).
- **Putting business orchestration in Triggers:** Deeply chained `AFTER` triggers make write latency opaque and hard to debug; keep triggers limited to lightweight invariants/auditing (`updated_at`, audit log) rather than complex multi-table workflows.

</TopicSection>

<TopicSection id="m05-p3-sec-h" letter="H" title="Best Practices">

- Default to **`JSONB`** over `JSON` unless exact key order/whitespace preservation is legally required.
- Always create a `UNIQUE` index on materialized views so `REFRESH MATERIALIZED VIEW CONCURRENTLY` never blocks dashboard readers.
- Harden any `SECURITY DEFINER` function with `SET search_path = pg_catalog, public` (or explicit schema) to prevent object-shadowing attacks.

</TopicSection>

<TopicSection id="m05-p3-sec-i" letter="I" title="Performance & Scalability">

- **`jsonb_ops` vs. `jsonb_path_ops`:** Default `GIN (col)` indexes every key and value separately (supporting `?`, `?&`, `?|`, and `@>`). `GIN (col jsonb_path_ops)` hashes full paths, cutting GIN index size by ~30–50% and speeding up `@>` containment queries.
- **Trigger Overhead on Bulk Loads:** Row-level triggers execute once per row; for bulk ETL (`COPY` / batch inserts), switch to `FOR EACH STATEMENT` transition tables (`REFERENCING NEW TABLE`) or disable/bypass non-critical audit triggers carefully.

</TopicSection>

<TopicSection id="m05-p3-sec-j" letter="J" title="Security Considerations">

- **`SECURITY INVOKER` Views (PG 15+):** Enable `WITH (security_invoker = true)` on tenant-facing views so caller RLS policies apply automatically.
- **`SECURITY DEFINER` `search_path` Hijacking:** A `SECURITY DEFINER` function without an explicit `SET search_path` can be tricked into executing a malicious user-schema function or operator; always pin `SET search_path` and revoke `EXECUTE` from `PUBLIC`.

</TopicSection>

<TopicSection id="m05-p3-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. Views vs. Materialized Views

| Feature | Standard `VIEW` | `MATERIALIZED VIEW` |
| --- | --- | --- |
| **Storage** | Virtual (query definition only) | Persisted heap table on disk |
| **Freshness** | Always 100% live | Snapshot as of last `REFRESH` |
| **Indexable** | No (uses base table indexes) | Yes (own B-tree / GIN indexes) |
| **Refresh Lock** | N/A | `ACCESS EXCLUSIVE` unless `CONCURRENTLY` + `UNIQUE` index |

#### 2. Functions vs. Stored Procedures

| Feature | `CREATE FUNCTION` | `CREATE PROCEDURE` (PG 11+) |
| --- | --- | --- |
| **Invocation** | `SELECT fn(...)` / `WHERE` | `CALL proc(...)` |
| **Return Value** | Scalar, record, or `TABLE` | Optional `INOUT`/`OUT` only |
| **Transaction Control** | Single caller tx (no `COMMIT`) | Can `COMMIT`/`ROLLBACK` in loops |
| **Best Fit** | Pure helpers, triggers, computed columns | Batched backfills & maintenance jobs |

#### 3. JSON vs. JSONB in PostgreSQL

| Dimension | `json` | `jsonb` |
| --- | --- | --- |
| **Storage Format** | Raw UTF-8 text | Decomposed binary tree |
| **Whitespace / Key Order / Dupes** | Preserved exactly | Stripped, sorted, deduplicated (last wins) |
| **Read / Query Speed** | Slower (reparses text each read) | Fast binary field traversal |
| **GIN Indexing & `@>`** | Not supported | Supported (`jsonb_ops` / `jsonb_path_ops`) |

</TopicSection>

  <CodeBlock

    code={`function createExclusionConstraintTable() {
  const rows = [];

  return {
    insert({ roomId, startMs, endMs }) {
      if (!Number.isInteger(roomId) || roomId < 1) throw new TypeError("roomId must be positive integer");
      if (!Number.isFinite(startMs) || !Number.isFinite(endMs) || startMs >= endMs) {
        throw new TypeError("Invalid half-open interval: startMs must be < endMs");

      }

    },

      return rows.map((r) => ({ ...r }));
    }
  };
}

  if (!row || typeof row !== "object") throw new TypeError("row must be an object");
  if (typeof validateConstraints !== "function") throw new TypeError("validateConstraints must be a function");

  let nextRow = { ...row };
  if (typeof beforeTrigger === "function") {
    const mutated = beforeTrigger({ ...nextRow });
    if (mutated === null) return { committed: false, reason: "Suppressed by BEFORE trigger" };
    nextRow = { ...mutated };
  }

  const auditEvents = [];
  if (typeof afterTrigger === "function") {
    auditEvents.push(afterTrigger({ ...nextRow }));
  }

  return { committed: true, row: nextRow, auditEvents };
}

<TopicSection id="m05-p3-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Views (`security_invoker = true`)** abstract live queries safely under caller RLS, while **Materialized Views (`REFRESH CONCURRENTLY` + `UNIQUE` index)** cache heavy aggregations without read locks.
- **Functions** run inside the caller's transaction (`IMMUTABLE` / `STABLE` / `VOLATILE`), whereas **Stored Procedures (`CALL`)** can `COMMIT` across batches.
- **`BEFORE`/`AFTER` triggers** and **`EXCLUDE USING gist` / `NOT VALID` constraints** enforce domain invariants cleanly at the database layer.
- **`JSONB` + `GIN (jsonb_path_ops)`** provides fast binary storage and `@>` containment indexing compared to text-preserving `JSON`.
