<TopicSection id="m04-p2-sec-a" letter="A" title="Topic Introduction">

#### What is this?

**Normalization** is the systematic process of structuring relational tables to eliminate redundant data and prevent **insert, update, and delete anomalies** using formal rules (**1NF**, **2NF**, **3NF**, **BCNF**). **Denormalization** is the intentional, measured reversal of normalization—duplicating derived or joined columns to speed up hot read queries at the cost of extra write coordination.

#### Why does it exist & what problem does it solve?

Storing a customer's `email` and `address` on every single row of `orders` wastes storage and creates **anomalies**: updating an address requires updating 500 rows (if one fails, data is inconsistent), deleting the last order wipes out the customer's record entirely, and you cannot insert a new customer before they buy something.

#### Where is it used in real-world software?

Every relational OLTP schema (e-commerce, banking, SaaS multi-tenant apps) starts normalized to **3NF/BCNF** for correctness and selectively denormalizes hot read paths (such as `orders.total_cents`, materialized views, or read-model counters) only after measuring real query bottlenecks.

</TopicSection>

<TopicSection id="m04-p2-sec-b" letter="B" title="Fundamentals (Simple Mental Models)">

<TopicAnchor id="m04-p2-topic-normalization" />

#### 1. Normalization: Eliminating Redundancy & Data Anomalies

**Normalization** organizes attributes into tables so every fact is stored in **one canonical place**. By decomposing mixed-concept tables along **functional dependencies** (`A -> B`, meaning knowing `A` uniquely determines `B`), you eliminate three classic bugs: **insertion anomalies** (cannot add a product without an order), **update anomalies** (changing a price leaves stale copies elsewhere), and **deletion anomalies** (deleting an order erases product metadata).

In practice, most production OLTP schemas target **3NF** or **BCNF** as the default baseline.

<TopicAnchor id="m04-p2-topic-denormalization" />

#### 2. Denormalization: Intentional Read Speed vs. Write Complexity

**Denormalization** intentionally re-introduces controlled redundancy—for example, caching `item_count` or `total_cents` on `orders`, storing a snapshot of `unit_price_cents` on `order_items` (which is also a business snapshot!), or maintaining a summary read table—to avoid expensive multi-table `JOIN`s or `COUNT(*)`/`SUM()` scans.

Never denormalize blindly upfront: every duplicated column must have a clear **consistency mechanism** (single-transaction update, DB trigger, or async outbox rebuild) so reads never drift out of sync with the source of truth.

<TopicAnchor id="m04-p2-topic-1nf" />

#### 3. 1NF (First Normal Form): Atomic Values & No Repeating Groups

A table is in **First Normal Form (1NF)** when every column holds **atomic (indivisible) scalar values**, there are **no repeating column groups** (`tag1, tag2, tag3` or comma-separated `"sql,node,react"`), and every row is uniquely identifiable by a Primary Key.

Violating 1NF forces ugly `LIKE '%tag%'` scans, breaks foreign-key integrity, and makes counting or updating a single item error-prone—fix it by moving repeating items into a child table (`post_tags`).

<TopicAnchor id="m04-p2-topic-2nf" />

#### 4. 2NF (Second Normal Form): Eliminating Partial Dependencies

A table is in **Second Normal Form (2NF)** when it is in **1NF** and **every non-key column depends on the ENTIRE Primary Key**—never on just *part* of a composite key (**partial dependency**).

For example, in `order_items(order_id, product_id, quantity, product_name)`, the composite PK is `(order_id, product_id)`, yet `product_name` depends only on `product_id`! Moving `product_name` to `products` achieves 2NF and stops duplicating product names on every line item.

<TopicAnchor id="m04-p2-topic-3nf" />

#### 5. 3NF (Third Normal Form): Eliminating Transitive Dependencies

A table is in **Third Normal Form (3NF)** when it is in **2NF** and **no non-key column depends on another non-key column** (**transitive dependency**: `PK -> A -> B`).

For instance, in `orders(id, customer_id, customer_email)`, `id -> customer_id -> customer_email` means `customer_email` depends transitively on `id` via `customer_id`. Moving `customer_email` to `customers` achieves **3NF** (*"the key, the whole key, and nothing but the key"*).

<TopicAnchor id="m04-p2-topic-bcnf-overview" />

#### 6. BCNF Overview (Boyce-Codd Normal Form): Every Determinant Is a Candidate Key

**BCNF** is a slightly stricter version of **3NF**: for every non-trivial functional dependency `X -> Y`, `X` **must be a superkey** (a candidate key). While 3NF allows an anomaly when a non-key attribute determines *part* of a composite candidate key, BCNF closes that edge case completely.

A classic example is `course_instructors(student_id, course_id, instructor_id)` where each instructor teaches only one course (`instructor_id -> course_id`): splitting `(instructor_id, course_id)` and `(student_id, instructor_id)` satisfies BCNF.

</TopicSection>

#### 2. Normalized Write Integrity vs. Selective Denormalization

Normalized tables store a single source of truth; selective denormalization trades write coordination (updating `orders.total_cents` atomically in the same transaction) to turn `O(k)` item scans into `O(1)` header reads.

#### Example 2: Functional Dependency & Normal Form Classifier (`classifyTableNormalForm`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Models 1NF, 2NF, 3NF, and BCNF checks given primaryKey, candidateKeys, and functional dependencies
function classifyTableNormalForm({ hasAtomicColumns, primaryKey, candidateKeys = [primaryKey], dependencies }) {
  if (typeof hasAtomicColumns !== "boolean") throw new TypeError("hasAtomicColumns must be boolean");
  if (!Array.isArray(primaryKey) || primaryKey.length === 0) throw new TypeError("primaryKey must be non-empty array");
  if (!Array.isArray(dependencies)) throw new TypeError("dependencies must be an array");
  if (!hasAtomicColumns) return { highestForm: "UNF", reason: "Non-atomic or repeating column groups violate 1NF" };

  const keyAttrs = new Set(candidateKeys.flat());
  const nonTrivialDeps = dependencies.map((dep) => {
    if (!Array.isArray(dep.lhs) || !dep.rhs) throw new TypeError("Each dependency requires lhs[] and rhs");
    const lhsSet = new Set(dep.lhs);
    const isSuperkey = candidateKeys.some((ck) => ck.every((k) => lhsSet.has(k)));
    return { dep, lhsSet, isSuperkey, isTrivial: lhsSet.has(dep.rhs) };
  }).filter((item) => !item.isTrivial);

  // Check 2NF: non-key attribute depending on a proper subset of any composite candidate key
  for (const { dep, lhsSet, isSuperkey } of nonTrivialDeps) {
    const rhsIsNonKey = !keyAttrs.has(dep.rhs);
    const lhsStrictSubsetOfCandidateKey =
      !isSuperkey &&
      lhsSet.size > 0 &&
      candidateKeys.some((ck) => lhsSet.size < ck.length && [...lhsSet].every((a) => ck.includes(a)));
    if (rhsIsNonKey && lhsStrictSubsetOfCandidateKey) {
      return { highestForm: "1NF", reason: "Partial dependency (" + dep.lhs.join(",") + " -> " + dep.rhs + ") violates 2NF" };
    }
  }

  // Check 3NF: non-superkey determinant determining a non-key (non-prime) attribute
  for (const { dep, isSuperkey } of nonTrivialDeps) {
    const rhsIsNonKey = !keyAttrs.has(dep.rhs);
    if (!isSuperkey && rhsIsNonKey) {
      return { highestForm: "2NF", reason: "Transitive dependency (" + dep.lhs.join(",") + " -> " + dep.rhs + ") violates 3NF" };
    }
  }

  // Check BCNF: every non-trivial determinant lhs must be a superkey
  for (const { dep, isSuperkey } of nonTrivialDeps) {
    if (!isSuperkey) {
      return { highestForm: "3NF", reason: "Determinant (" + dep.lhs.join(",") + ") is not a superkey (violates BCNF)" };
    }
  }

  return { highestForm: "BCNF", reason: "All determinants are superkeys" };
}

console.log("CSV tags:", classifyTableNormalForm({ hasAtomicColumns: false, primaryKey: ["id"], dependencies: [] }));
console.log("Partial dep:", classifyTableNormalForm({ hasAtomicColumns: true, primaryKey: ["order_id", "product_id"], dependencies: [{ lhs: ["product_id"], rhs: "product_name" }] }));
console.log("Transitive dep:", classifyTableNormalForm({ hasAtomicColumns: true, primaryKey: ["id"], dependencies: [{ lhs: ["customer_id"], rhs: "customer_email" }] }));
console.log("Clean 3NF/BCNF:", classifyTableNormalForm({ hasAtomicColumns: true, primaryKey: ["id"], dependencies: [{ lhs: ["id"], rhs: "customer_id" }] }));`}
/>

<CodeBlock

  runnable
  code={`// Models why denormalized totals require atomic updates and how drift happens if skipped
function createSyncedOrderStore() {
  const orders = new Map(); // orderId -> { cachedTotalCents, items: [] }

  return {
    createOrder(orderId) {
      if (!Number.isInteger(orderId) || orderId < 1) throw new TypeError("orderId must be positive integer");
      orders.set(orderId, { cachedTotalCents: 0, items: [] });
    },
    addItem(orderId, { qty, unitPriceCents, syncCache = true }) {
      const ord = orders.get(orderId);
      if (!ord) throw new Error("Order not found");
      if (!Number.isInteger(qty) || qty < 1 || !Number.isInteger(unitPriceCents) || unitPriceCents < 0) {
        throw new TypeError("Invalid item qty or price");
      }
      ord.items.push({ qty, unitPriceCents });
      if (syncCache) ord.cachedTotalCents += qty * unitPriceCents;
    },
    inspect(orderId) {
      const ord = orders.get(orderId);
      if (!ord) throw new Error("Order not found");
      const normalizedSum = ord.items.reduce((sum, it) => sum + it.qty * it.unitPriceCents, 0);
      return {
        cachedTotalCents: ord.cachedTotalCents,
        normalizedSum,
        inSync: ord.cachedTotalCents === normalizedSum
      };
    }
  };
}

const store = createSyncedOrderStore();
store.createOrder(1);
store.addItem(1, { qty: 2, unitPriceCents: 1500, syncCache: true });
console.log("Synced:", store.inspect(1));
store.addItem(1, { qty: 1, unitPriceCents: 500, syncCache: false }); // simulated bug skipping cache update
console.log("Drifted:", store.inspect(1));`}

<TopicSection id="m04-p2-sec-e" letter="E" title="Step-by-Step Walkthrough">

Trace **`classifyTableNormalForm`** (**Example 2**) on `order_items(order_id, product_id, product_name)`:

1. **1NF Check:** `hasAtomicColumns === true`, so scalar atomicity passes.
2. **2NF Check:** `primaryKey` is composite (`["order_id", "product_id"]`, length `2`). Dependency `["product_id"] -> "product_name"` has `lhs.length (1) < 2` and `"product_id"` is in `pkSet`, while `"product_name"` is non-key. The checker stops and reports `highestForm: "1NF"` (2NF violated!).
3. **3NF & BCNF Checks:** Once `product_name` moves to `products`, the checker scans for non-key transitive chains (`customer_id -> customer_email` -> reports `2NF`) and finally verifies every determinant is a superkey (`BCNF`).

<TopicSection id="m04-p2-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Preserving Historical Invoice Prices Without Violating 3NF

**Problem:** An `order_items` table references `products.price_cents`. When the catalog team raises a product's price from \$20 to \$25, past customer invoices suddenly show \$25!

**Production Solution:** Copying `unit_price_cents` onto `order_items` at purchase time is **not** redundant denormalization—it is a distinct temporal fact (*"price at time of purchase"*), whereas `products.current_price_cents` represents the live catalog price. Both belong in a clean 3NF schema.

#### Scenario 2: Speeding Up a Dashboard Feed With Selective Denormalization

**Problem:** A SaaS feed lists 50 posts per page and runs `COUNT(*)` on `post_likes` and `post_comments` for every post, causing slow query plans at 10M likes.

**Production Solution:** Keep `post_likes` and `post_comments` normalized as the source of truth, and add `like_count` / `comment_count` integer columns on `posts` updated atomically inside the same DB transaction (or via batched background reconciliation).

</TopicSection>

<TopicSection id="m04-p2-sec-g" letter="G" title="Common Mistakes">

- **Storing comma-separated IDs or tags (`"1,2,3"`) in a `TEXT` column:** Violates 1NF, breaks foreign keys, and forces slow substring scans.
- **Denormalizing every table before measuring performance:** Multiplies write bugs, stale totals, and migration pain for zero measurable gain.
- **Forgetting to update denormalized caches on `DELETE` and `UPDATE`:** Developers often increment `like_count` on `INSERT` but forget to decrement on `DELETE`.
- **Confusing historical snapshots (`order_items.unit_price_cents`) with denormalization:** Snapshotting immutable point-in-time facts is proper domain modeling, not redundancy.

</TopicSection>

<TopicSection id="m04-p2-sec-h" letter="H" title="Best Practices">

- **Normalize to 3NF/BCNF by default** for all core OLTP entities.
- **Denormalize only proven read bottlenecks** (backed by `EXPLAIN ANALYZE` or p95 telemetry), and document the exact sync mechanism (transaction, trigger, or materialized view).
- **Use junction tables** (`product_tags`, `order_items`) instead of CSV strings or `tag1, tag2, tag3` columns.
- **Separate live catalog attributes from historical transaction snapshots** explicitly in column names (`current_price_cents` vs. `unit_price_cents`).

</TopicSection>

<TopicSection id="m04-p2-sec-i" letter="I" title="Performance & Scalability">

- **Write Amplification vs. Read Amplification:** Normalized schemas make writes small and atomic (`UPDATE customers SET email = ...` touches 1 row), while denormalized schemas speed up reads (`SELECT total_cents FROM orders` avoids joining `order_items`) at the cost of extra write locks.
- **PostgreSQL Materialized Views / Read Replicas:** Before duplicating columns across OLTP tables, consider indexed **Materialized Views** (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) or analytical read replicas.
- **Smaller Rows in Buffer Pool:** Normalized tables avoid repeating long strings (`customer_name`, `address`) across millions of child rows, keeping more hot index and data pages cached in RAM.

</TopicSection>

<TopicSection id="m04-p2-sec-j" letter="J" title="Security Considerations">

- **Single Canonical PII Location:** Storing `email`, `phone`, or `ssn` in one normalized `users` table makes GDPR deletion, masking, and access control auditable in one place rather than scattered across 12 denormalized tables.
- **Preventing Drift in Denormalized Authorization Fields:** Never cache mutable permission/role flags (`is_admin`) in denormalized secondary tables without atomic sync—stale copies can leave revoked users authorized.

</TopicSection>

<TopicSection id="m04-p2-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. Normal Forms Cheat Sheet

| Normal Form | Core Rule | Typical Violation Example | Fix |
| --- | --- | --- | --- |
| **1NF** | Atomic values, no repeating groups | `tags = "js,sql"` or `phone1, phone2` | Move to child table `user_phones` |
| **2NF** | 1NF + no partial key dependency | `(order_id, product_id) -> product_name` | Move `product_name` to `products` |
| **3NF** | 2NF + no transitive non-key dependency | `order_id -> customer_id -> customer_email` | Move `customer_email` to `customers` |
| **BCNF** | Every determinant `X -> Y` is a superkey | Non-key `instructor_id -> course_id` in composite key | Split `(instructor_id, course_id)` |

#### 2. Normalization vs. Denormalization Trade-Offs

| Dimension | Normalized (3NF / BCNF) | Denormalized |
| --- | --- | --- |
| **Write Consistency** | High (single source of truth) | Harder (must sync all copies) |
| **Storage Footprint** | Compact | Larger (duplicated values) |
| **Read Speed (Simple Joins)** | Fast with proper indexes | Slightly faster (fewer joins) |
| **Read Speed (Heavy Aggregations)** | Slower (`COUNT`/`SUM` over child rows) | Very fast (`O(1)` precomputed column) |

#### 3. Denormalization Sync Strategies

| Strategy | Freshness | Write Overhead | Best Fit |
| --- | --- | --- | --- |
| **Same-Transaction App Update** | Immediate (ACID) | Moderate (extra SQL update + row lock) | Order totals, account balances, low-write counters |
| **Database Trigger** | Immediate (ACID) | High (hidden lock contention on hot parents) | Legacy apps where multiple writers bypass one service |
| **Materialized View (`REFRESH CONCURRENTLY`)** | Scheduled / Stale | Zero on OLTP writes; burst on refresh | Dashboards, reporting summaries, analytics |
| **Outbox + Async Worker / CDC** | Eventual (ms–sec) | Low on OLTP writes | Cross-service read models, search indexes, high-throughput feeds |

</TopicSection>

<TopicSection id="m04-p2-sec-l" letter="L" title="Tips to Remember (Mnemonics & Mental Models)">

- **"1NF = Atomic cells; 2NF = Whole key; 3NF = Nothing but the key; BCNF = Every determinant is a key."**
- **"Normalize until it hurts, denormalize until it works."**
- **"If you duplicate a column, write down how it stays in sync on INSERT, UPDATE, and DELETE."**
- **"Price at time of purchase is a historical fact, not denormalization."**

    }

      violations.push({ via: dep.from, target: dep.to });
    }
  }
  return violations;
}

<TopicSection id="m04-p2-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Normal Forms:** **1NF** enforces atomic scalar columns; **2NF** removes partial dependencies on composite keys; **3NF** removes transitive non-key dependencies; **BCNF** requires every determinant to be a superkey.
- **Anomalies:** Normalization prevents insertion, update, and deletion anomalies by storing each fact once.
- **Denormalization:** Apply selectively only for proven read bottlenecks, paired with atomic transaction/trigger/CDC synchronization.
- **Snapshots vs. Redundancy:** Recording immutable historical values (like `unit_price_cents` on `order_items`) is proper temporal modeling, not a normalization violation.
