<TopicSection id="m01-p5-sec-a" letter="A" title="Topic Introduction">

#### What is this?

**TypeScript** is a statically typed superset of JavaScript developed by Microsoft that compiles (**erases types**) down to standard ECMAScript. Its **type system** checks contracts—**interfaces**, **generics**, unions, and **type safety** invariants—at compile time before code ever ships to a browser or Node.js process.

#### Why does it exist & what problem does it solve?

In large JavaScript codebases, refactoring a function signature, renaming a DTO field (`user.fullName` &rarr; `user.displayName`), or forgetting a `null` check silently passes until a customer hits `TypeError: Cannot read properties of undefined` in production. TypeScript catches those entire bug classes in your editor and CI pipeline.

#### Where is it used in real-world software?

Nearly all modern React, Next.js, Node.js/NestJS, and full-stack teams use TypeScript (`strict: true`) to share API contracts between backend and frontend, type database query results (Prisma/Drizzle), and enforce exhaustive error handling across multi-team repositories.

</TopicSection>

<TopicAnchor id="m01-p5-topic-typescript-fundamentals" />

#### 1. TypeScript Fundamentals: Compile-Time Checking & Type Erasure

**TypeScript fundamentals** rest on one crucial mental model: TypeScript adds static type annotations (`const port: number = 3000;`) that `tsc` checks during build time and **completely erases** from the emitted `.js` output.

Because types do not exist at runtime in the emitted JavaScript, TypeScript cannot protect you from malformed JSON coming over an HTTP request or `JSON.parse()` unless you pair static types with runtime type guards or schema validators.

<TopicAnchor id="m01-p5-topic-type-systems" />

#### 2. Type Systems: Structural Typing, Unions & Narrowing

Unlike Java or C# (**nominal typing**, where two types with identical fields are incompatible unless they share a named class/interface), TypeScript uses a **structural type system** (*"duck typing at compile time"*): if `{ id: string; name: string }` has every required field of `{ id: string }`, it satisfies `{ id: string }` automatically.

TypeScript also excels at combining types (**union types** like `"idle" | "loading" | "error"`, **intersection types** `A & B`) and **control-flow narrowing** (`typeof`, `in`, `Array.isArray`, or discriminated-union `switch (res.kind)`).

<TopicAnchor id="m01-p5-topic-generics" />

#### 3. Generics: Reusable Type-Safe Abstractions

<GlossaryTerm definition="Type parameters (such as <T>) that let functions, classes, and interfaces preserve caller-specific types without falling back to any.">Generics</GlossaryTerm> (`function first<T>(items: T[]): T | undefined`) act like **function parameters for types**. Instead of duplicating `firstNumber(arr: number[])` and `firstUser(arr: User[])`—or losing all autocomplete with `any`—generics preserve the exact input type through to the output.

You can constrain generics with `extends` (`<T extends { id: string }>`) so a generic helper safely accesses `item.id` while still returning the caller's full specific subtype.

<TopicAnchor id="m01-p5-topic-interfaces" />

#### 4. Interfaces: Contracts, `type` Aliases & Declaration Merging

An <GlossaryTerm definition="A named TypeScript structural contract describing object shapes, method signatures, and optional/readonly properties.">Interface</GlossaryTerm> (`interface PaymentGateway { charge(cents: number): Promise<Receipt>; }`) defines the public contract a class or object must satisfy. Use `readonly` for immutable fields and `?` for optional properties.

`interface` and `type` overlap heavily for object shapes: prefer `interface` for public object/class contracts (clearer error messages, `extends`, and **declaration merging**—where multiple `interface` blocks with the same name in one scope automatically merge, whereas duplicate `type` aliases error) and `type` for unions (`Result<T>`), tuples, and mapped/conditional utility types (`Partial<T>`, `Pick<T, K>`, `Omit<T, K>`).

<TopicAnchor id="m01-p5-topic-type-safety" />

#### 5. Type Safety: `strict`, `unknown` vs. `any` & Runtime Boundaries

**Type safety** means the compiler guarantees operations only run on compatible values. Enabling `"strict": true` in `tsconfig.json` turns on `strictNullChecks`, `noImplicitAny`, and `strictFunctionTypes`—preventing silent `null`/`undefined` crashes.

Never use `any` (which disables type checking completely and spreads virally); use **`unknown`** for untrusted inputs (`JSON.parse`, `catch (err: unknown)`), forcing explicit runtime narrowing before accessing any property.

</TopicSection>

#### Example 2: Runtime Type Guard (`unknown` &rarr; Verified `OrderDTO`)

<CodeBlock
  lang="javascript"
  runnable
  code={`// Runtime type guard backing TypeScript's \`raw: unknown\` -> \`raw is OrderDTO\`
function isPlainRecord(value) {
  return value !== null && typeof value === "object" && !Array.isArray(value);
}

function parseOrderDTO(raw) {
  if (!isPlainRecord(raw)) {
    throw new TypeError("Order payload must be a plain object");
  }
  if (typeof raw.id !== "string" || raw.id.trim().length === 0) {
    throw new TypeError("Order.id must be a non-empty string");
  }
  if (!Number.isSafeInteger(raw.totalCents) || raw.totalCents < 0) {
    throw new RangeError("Order.totalCents must be a non-negative safe integer");
  }
  if (raw.currency !== "USD" && raw.currency !== "EUR") {
    throw new TypeError("Order.currency must be 'USD' or 'EUR'");
  }
  const totalCents = raw.totalCents === 0 ? 0 : raw.totalCents;
  return Object.freeze({ id: raw.id.trim(), totalCents, currency: raw.currency });
}

console.log("Parsed DTO:", parseOrderDTO({ id: "ord_1", totalCents: 2500, currency: "USD" }));`}
/>

#### Example 3: Exhaustive Discriminated Union Handler & `indexById` Generic Runtime

<CodeBlock
  lang="javascript"
  runnable
  code={`// Runtime implementation matching TS \`indexById<T extends { id: string }>\` & \`ApiResult<T>\`
function indexById(items) {
  if (!Array.isArray(items)) throw new TypeError("items must be an array");
  const map = new Map();
  for (let i = 0; i < items.length; i++) {
    const item = items[i];
    if (!item || typeof item !== "object" || typeof item.id !== "string" || item.id.trim().length === 0) {
      throw new TypeError(\`items[\${i}] must have a non-empty string id\`);
    }
    const id = item.id.trim();
    if (map.has(id)) throw new RangeError(\`Duplicate id: \${id}\`);
    map.set(id, item);
  }
  return map;
}

function formatApiResult(res) {
  if (!res || typeof res !== "object") throw new TypeError("Result must be an object");
  switch (res.ok) {
    case true:
      if (!Object.hasOwn(res, "data") || res.data === undefined) {
        throw new TypeError("Success result must include data");
      }
      return \`OK: \${JSON.stringify(res.data)}\`;
    case false:
      if (typeof res.code !== "string" || res.code.trim().length === 0 || typeof res.message !== "string") {
        throw new TypeError("Error result must include code and message strings");
      }
      return \`ERR[\${res.code}]: \${res.message}\`;
    default:
      throw new TypeError(\`Unhandled result variant: \${String(res.ok)}\`);
  }
}

const byId = indexById([{ id: "u1", role: "admin" }, { id: "u2", role: "viewer" }]);
console.log("Lookup u1:", byId.get("u1"));
console.log("Result:", formatApiResult({ ok: true, data: { count: byId.size } }));`}
/>

<TopicSection id="m01-p5-sec-e" letter="E" title="Step-by-Step Walkthrough">

Trace how **`parseOrderDTO`** (**Example 2**) bridges compile-time TypeScript and runtime JavaScript:

1. **Ingress as `unknown`:** An HTTP route receives `JSON.parse(body)` typed as `unknown` (never `any` and never an unsafe `body as OrderDTO` cast).
2. **Structural Object Guard:** `isPlainRecord(raw)` verifies `raw` is a non-null, non-array object before reading any property.
3. **Field-by-Field Narrowing:** Each check (`typeof raw.id === "string"`, `Number.isSafeInteger(raw.totalCents)`, union check on `currency`) narrows the type in TypeScript and throws an explicit `TypeError` or `RangeError` at runtime if violated.
4. **Immutable Return (`readonly`):** `Object.freeze(...)` aligns runtime immutability with TypeScript's `readonly` interface properties.

</TopicSection>

<TopicSection id="m01-p5-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: End-to-End API Contracts Between Express/Node.js & React

**Problem:** A backend engineer renames `order.amount` to `order.amountCents` in an API response, breaking three React components silently until customers see `$NaN` on checkout.

**Production Solution:** Share TypeScript `interface OrderDTO` contracts in a shared types package, enable `strict: true`, and validate payloads at the Express/fetch boundary with runtime guards (e.g., Zod or `parseOrderDTO`), turning breaking changes into immediate compile errors.

#### Scenario 2: Exhaustive State Machines in React Reducers & Workflow Engines

**Problem:** A payment workflow adds a new `"REFUNDED"` status, but two `switch` statements in billing and analytics forget to handle it, falling through silently.

**Production Solution:** Model statuses as a discriminated union and place `assertNever(state)` in the `default` branch so `tsc` fails the build until every consumer handles `"REFUNDED"`.

</TopicSection>

<TopicSection id="m01-p5-sec-g" letter="G" title="Common Mistakes">

- **Using `any` as an escape hatch:** Disables type checking across every caller that receives that value.
- **Trusting `data as MyInterface` on `fetch` / `JSON.parse`:** Type assertions tell the compiler *"trust me"* without emitting any runtime validation check!
- **Disabling `strictNullChecks`:** Allows `undefined`/`null` to slip into string/array methods until runtime crashes occur.
- **Over-complex conditional/mapped type gymnastics:** Unreadable 20-line type puzzles slow down `tsc` and confuse teammates when a simple discriminated union or generic interface suffices.

</TopicSection>

<TopicSection id="m01-p5-sec-h" letter="H" title="Best Practices">

- **Always enable `"strict": true` (and `noUncheckedIndexedAccess` for safer array/record indexing)** in `tsconfig.json`.
- **Use `unknown` at all external boundaries** (`JSON.parse`, `catch (err: unknown)`, `req.body`) and narrow with type guards or schema validators.
- **Prefer discriminated unions over optional-field soup** (e.g., `{ status: "ok"; data: T } | { status: "error"; error: Error }` instead of `{ loading?: boolean; data?: T; error?: Error }`).
- **Keep generics minimal and constrained** (`<T extends Entity>`), letting TypeScript infer type arguments from call sites whenever possible.

</TopicSection>

<TopicSection id="m01-p5-sec-i" letter="I" title="Performance & Scalability">

- **Zero Runtime Overhead from Types:** Erased interfaces, type aliases, and generics add **0 bytes** and **0ms** to production JavaScript bundles.
- **Compiler Build Speed (`tsc`):** Prefer `interface extends` over large `&` intersections for huge object graphs—`tsc` caches interface hierarchies much faster than flattened intersections. Use project references (`composite: true`) in monorepos.

</TopicSection>

<TopicSection id="m01-p5-sec-j" letter="J" title="Security Considerations">

- **The Type-Assertion Illusion (`as AdminUser`):** An attacker sending `{ "role": "admin" }` or `{ "totalCents": -500 }` bypasses compile-time types completely at runtime. Always pair TS interfaces with runtime validation at ingress.
- **Avoid `eval` / `Function` & Untyped `Record<string, any>`:** Use `Map<string, T>` or `satisfies Record<KnownKey, Handler>` so dynamic user keys cannot collide with `Object.prototype`.

</TopicSection>

<TopicSection id="m01-p5-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. `any` vs. `unknown` vs. `never`

| Type | Meaning | Allows Property Access Without Narrowing? | Primary Use Case |
| --- | --- | --- | --- |
| `any` | Disables type checking (top + bottom) | Yes (unsafe!) | Avoid; temporary legacy JS migration only |
| `unknown` | Type-safe top type (any value, unknown shape) | **No** (must narrow first) | Untrusted inputs (`JSON.parse`, `catch (err)`) |
| `never` | Bottom type (impossible/unreachable value) | N/A | Exhaustive `switch` checks, throwing functions |

#### 2. `interface` vs. `type` Alias

| Feature | `interface` | `type` |
| --- | --- | --- |
| Object & class `implements` | Yes (idiomatic) | Yes (for object types) |
| Unions (`A \| B`) & Primitives | No | **Yes** |
| Declaration merging | Yes | No |
| `tsc` performance on large graphs | Faster (`extends` caching) | Slower on deep `&` intersections |

#### 3. Structural Typing (TypeScript) vs. Nominal Typing (Java / C#)

| Dimension | Structural Typing (TypeScript) | Nominal Typing (Java / C#) |
| --- | --- | --- |
| Compatibility rule | Same shape/properties = compatible | Must explicitly declare `implements` / `extends` |
| Ergonomics with JSON/DTOs | Seamless with plain object literals | Requires explicit mapper classes |
| Trap to watch | Two distinct IDs (`UserId` vs `OrderId`) both typed `string` can be swapped | Prevented by distinct classes |

</TopicSection>

- **Type Erasure Rule:** *"TypeScript protects the build; runtime guards protect the wire."*
- **`unknown` vs `any`:** *"`any` turns the alarm off; `unknown` asks for ID at the door."*
- **Generics Rule:** *"Generics are type-level parameters that preserve caller precision without `any`."*
- **Exhaustiveness:** *"End every union `switch` with `default: return assertNever(x)` so the compiler catches missing cases."*

<TopicSection id="m01-p5-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Compile-Time Erasure:** TypeScript catches structural and nullability bugs before deployment, but types vanish at runtime—always validate external `unknown` inputs at I/O boundaries.
- **Structural Typing & Narrowing:** TypeScript checks shapes, not class names; combine discriminated unions with `switch` + `never` exhaustiveness checks.
- **Generics & Interfaces:** Use constrained generics (`<T extends Entity>`) instead of `any`, and `interface` for extensible object/class contracts.
- **Strict Type Safety:** Keep `"strict": true` enabled, replace `any` with `unknown`, and never trust `as T` on untrusted network data.

</TopicSection>
