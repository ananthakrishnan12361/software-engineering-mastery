<TopicSection id="m01-p4-sec-a" letter="A" title="Topic Introduction">

#### What is this?

**JavaScript internals** explain how the language actually executes behind the syntax: how **Scope**, **Hoisting**, and **Closures** govern variable lifetime; how **Prototypes** and **`this`** resolve property lookups and method receivers; how **Promises**, **Async/await**, and the **Event Loop** (**Microtasks** vs. **Macrotasks**) schedule asynchronous work on a single thread; and how **Memory management** and **Garbage collection** reclaim unreachable heap objects.

#### Why does it exist & what problem does it solve?

Most production JavaScript bugs—stale closures in React hooks, `this` becoming `undefined` when passing a method as a callback, `Promise.all` failing silently, microtask starvation freezing UI/Node.js, or unbounded `Map` caches leaking gigabytes of RAM—stem from treating JS syntax as magic instead of understanding the runtime model.

#### Where is it used in real-world software?

Every React hook, Redux selector, Express middleware, database connection pool, and `fetch`/API retry wrapper depends on closures, `this`/lexical binding, microtask ordering, and proper reference cleanup so long-lived Node.js servers and browser tabs stay fast and leak-free.

</TopicSection>

<TopicSection id="m01-p4-sec-b" letter="B" title="Fundamentals (Simple Mental Models)">

<TopicAnchor id="m01-p4-topic-javascript" />

#### 1. JavaScript: Single-Threaded, Event-Driven, Multi-Paradigm

**JavaScript** is a single-threaded, garbage-collected, dynamically typed language standardized by **ECMAScript (ECMA-262)**. Single-threaded means one Call Stack executes one synchronous instruction at a time—preventing low-level data races on shared JS variables.

To stay responsive on one thread, JavaScript delegates slow I/O, timers, and network requests to host APIs (browser Web APIs or Node.js `libuv`) and schedules their completion callbacks through the Event Loop.

<TopicAnchor id="m01-p4-topic-es6" />

#### 2. ES6+ (ES2015–Modern ECMAScript): Ergonomics & Safety

**ES6+ (ES2015 and later)** modernized JavaScript from a fragile scripting language into a structured application language: `let`/`const` block scoping, arrow functions, `class` syntax, ES modules (`import`/`export`), destructuring, and rest/spread (`...`).

Subsequent yearly releases added `Promise` combinators (`allSettled`, `any`), `async`/`await`, optional chaining (`?.`), nullish coalescing (`??`), `Map`/`Set`/`WeakMap`, `Object.hasOwn()`, and non-mutating array transforms (`toSorted()`, `toSpliced()`).

<TopicAnchor id="m01-p4-topic-scope" />

#### 3. Scope: Lexical Environments & the Scope Chain

<GlossaryTerm definition="The compile-time rule determining where declared variables and functions are visible, forming nested Lexical Environments.">Scope</GlossaryTerm> defines where a binding is visible. JavaScript uses **lexical (static) scope**: a function's outer scope is determined by where it is **written in source code**, not where it is called at runtime.

When resolving an identifier `x`, the engine checks the current Lexical Environment first and walks outward along parent environment links until reaching module/global scope (or throwing `ReferenceError` if undeclared).

<TopicAnchor id="m01-p4-topic-hoisting" />

#### 4. Hoisting: Creation Phase Registration & TDZ

<GlossaryTerm definition="The engine's creation-phase behavior of registering declarations in their scope before executing statements line by line.">Hoisting</GlossaryTerm> happens because the engine scans each scope during its creation phase before executing statements line by line. `function` declarations are bound with their full callable body, and `var` bindings are initialized to `undefined`.

By contrast, `let`, `const`, and `class` declarations are hoisted into the **Temporal Dead Zone (TDZ)** uninitialized, throwing a `ReferenceError` if any code reads or writes them before their declaration line executes.

<TopicAnchor id="m01-p4-topic-closures" />

#### 5. Closures: Functions That Remember Their Birth Scope

A <GlossaryTerm definition="A function bundled together with references to its enclosing lexical environment, preserving outer variables after the outer function returns.">Closure</GlossaryTerm> is created whenever an inner function references variables from an enclosing scope. Even after the outer function's stack frame pops, those captured bindings stay alive on the heap as long as the inner function remains reachable.

Because closures capture live variable bindings rather than static value copies, they power private state factories, memoization caches, and React hooks—and explain why `var` in a `for` loop shares one counter across all callbacks while `let` creates a fresh binding per iteration.

<TopicAnchor id="m01-p4-topic-prototype" />

#### 6. Prototype: The `[[Prototype]]` Delegation Link

Every JavaScript object has an internal `[[Prototype]]` link (inspectable via `Object.getPrototypeOf(obj)`) pointing to another object or `null` (as in `Object.create(null)`).

When reading `obj.toString`, the engine checks `obj`'s own properties first, then walks the **prototype chain** (`obj` &rarr; `Object.prototype` &rarr; `null`) until it finds the property or reaches `null` and returns `undefined`.

<TopicAnchor id="m01-p4-topic-prototypal-inheritance" />

#### 7. Prototypal Inheritance: Behavior Sharing via Delegation

**Prototypal inheritance** shares methods across instances without duplicating functions into every object on the heap. Both `Object.create(proto)` and ES2015 `class` (`ClassName.prototype`) rely on prototype delegation.

All instances share one method reference on the prototype, while each instance stores its own state properties—and mutating `Object.prototype` affects every delegating object across the runtime (which is why prototype pollution is severe).

<TopicAnchor id="m01-p4-topic-this" />

#### 8. `this`: Dynamic Call-Site Binding Rules

In regular functions, <GlossaryTerm definition="An execution-context binding determined by how a function is called (call site), except in arrow functions which capture it lexically.">this</GlossaryTerm> is determined by **how the function is called**, not where it is defined: `new fn()` binds `this` to the new instance, and `fn.call(ctx)` / `.apply(ctx)` / `.bind(ctx)` sets `this` explicitly.

Otherwise, `obj.method()` binds `this` to `obj`, whereas a bare `fn()` call (including a detached method `const f = obj.method; f()`) sets `this` to `undefined` in strict mode (or `globalThis` in sloppy mode).

<TopicAnchor id="m01-p4-topic-arrow-functions" />

#### 9. Arrow Functions: Lexical `this` & Callback Safety

**Arrow functions** (`(x) => x * 2`) do **not** create their own `this`, `arguments`, or `super` bindings—instead, they capture `this` lexically from their enclosing scope when created, and `.call`/`.bind` cannot override it.

That makes arrow functions ideal for array callbacks, timers, and Promise chains inside class methods, while making them unsuitable as `new` constructors (throws `TypeError`) or prototype methods that need a dynamic receiver.

<TopicAnchor id="m01-p4-topic-promises" />

#### 10. Promises: Composable Asynchronous State Machines

A <GlossaryTerm definition="An object representing the eventual completion or failure of an async operation, transitioning once from pending to fulfilled or rejected.">Promise</GlossaryTerm> represents a future value in one of three states: **pending**, **fulfilled**, or **rejected**. Once settled, its value or rejection reason is immutable and never changes again.

Chaining `.then()`, `.catch()`, and `.finally()` flattens nested callbacks into linear pipelines, while combinators (`Promise.all`, `Promise.allSettled`, `Promise.race`, `Promise.any`) coordinate concurrent async tasks with distinct failure semantics.

<TopicAnchor id="m01-p4-topic-async-await" />

#### 11. Async/Await: Syntactic Sugar Over Promises

`async` functions always return a `Promise`, and `await expr` pauses only the **current `async` function's execution**, yielding control back to the Event Loop so other requests and UI events continue running.

Once the awaited Promise settles, the continuation resumes as a **microtask**. Always wrap `await` in `try/catch` for rejection handling, and launch independent async calls with `Promise.all()` before `await`ing so you avoid sequential waterfalls.

<TopicAnchor id="m01-p4-topic-event-loop" />

#### 12. Event Loop: Orchestrating Sync Stack & Async Queues

The **Event Loop** coordinates JavaScript's single Call Stack with async completion queues. First, the synchronous Call Stack runs to completion. Next, the runtime drains **all** queued microtasks until the microtask queue is empty.

Only after the microtask queue is completely empty does the Event Loop pick **one** macrotask (e.g., `setTimeout`, I/O callback), execute it, and drain microtasks again before the next macrotask or browser frame render.

<TopicAnchor id="m01-p4-topic-microtasks" />

#### 13. Microtasks: High-Priority Promise Continuations

<GlossaryTerm definition="High-priority async callbacks (Promise .then/catch/finally, queueMicrotask, MutationObserver) drained completely after each task before the next macrotask or render.">Microtasks</GlossaryTerm> include `Promise.then/.catch/.finally`, `await` continuations, and `queueMicrotask()`. Even `await Promise.resolve(1)` schedules its continuation as a microtask rather than running synchronously.

Because the engine drains the **entire** microtask queue (including microtasks queued during draining) before moving on, recursive microtask scheduling starves timers, network I/O, and UI painting completely.

<TopicAnchor id="m01-p4-topic-macrotasks" />

#### 14. Macrotasks: Timers, I/O & UI Events

**Macrotasks** (Tasks) include `setTimeout`, `setInterval`, DOM/UI events, and Node.js I/O / `setImmediate` callbacks. Only **one** macrotask executes per Event Loop turn before microtasks drain again.

Yielding between macrotasks gives browsers a window to repaint frames (`~16.6ms` at 60Hz) and lets Node.js poll socket/file descriptors—making `setTimeout(..., 0)` or `setImmediate` useful for chunking heavy CPU loops.

<TopicAnchor id="m01-p4-topic-memory-management" />

#### 15. Memory Management: Allocation, Reachability & Leaks

JavaScript allocates objects, closures, and strings automatically on the heap and frees them when unreachable. Unlike C/C++, developers do not call `free()`, yet **memory leaks** still happen regularly in production.

Leaks occur whenever code keeps **unintended strong references** alive from roots—such as unbounded global `Map` caches, forgotten `setInterval` timers, unremoved event listeners, or closures retaining large unused buffers.

<TopicAnchor id="m01-p4-topic-garbage-collection" />

#### 16. Garbage Collection: Mark-and-Sweep & Generational Heaps

Modern JS engines (such as V8's **Orinoco** GC) determine liveness via **reachability** from **GC Roots** (global object, active Call Stack frames, active closures), rather than naive reference counting—so isolated circular references (`a.ref = b; b.ref = a`) are safely reclaimed by **Mark-and-Sweep**.

To keep pauses short, V8 splits the heap into a **Young Generation** (fast Scavenger for short-lived objects) and an **Old Generation** (concurrent/incremental Mark-Sweep-Compact for long-lived data).

</TopicSection>

When `user.toString()` runs, the engine checks `Object.hasOwn(user, "toString")`, follows `[[Prototype]]` (`Object.getPrototypeOf(user)`), and stops at the first match or `null`. Meanwhile, the Garbage Collector traces outward from GC Roots (global + active stack + live closures): any isolated cycle not reachable from a root is reclaimed.

    throw new RangeError("maxMicrotasks must be a positive safe integer");

  const macrotasks = [];

  const api = {

      microtasks.push(fn);
    },
    setTimeout0: (fn) => {
      if (typeof fn !== "function") throw new TypeError("macrotask must be a function");
      macrotasks.push(fn);
    }
  };

  function drainMicrotasks() {
    let drained = 0;
    while (microtasks.length > 0) {
      if (++drained > maxMicrotasks) {
        throw new RangeError("Microtask starvation detected");
      }
      const task = microtasks.shift();
      task(api);
    }
  }

  initialSync(api);
  drainMicrotasks();
  while (macrotasks.length > 0) {
    const macro = macrotasks.shift();
    macro(api);
    drainMicrotasks();
  }
  return log;
}

  rt.sync("start");
  rt.setTimeout0((t) => {
    t.sync("macro-1");
    t.queueMicrotask((m) => m.sync("micro-inside-macro"));
  });
  rt.queueMicrotask((m) => {
    m.sync("micro-1");
    m.queueMicrotask((m2) => m2.sync("micro-chained"));
  });
  rt.sync("end");
});

console.log("Execution order:", trace);`}

class BoundedCache {
  #map = new Map();
  #maxEntries;

  constructor(maxEntries = 100) {
    if (!Number.isSafeInteger(maxEntries) || maxEntries < 1) {
      throw new RangeError("maxEntries must be a positive safe integer");
    }
    this.#maxEntries = maxEntries;
  }

  set(key, value) {
    if (typeof key !== "string" || key.length === 0) {
      throw new TypeError("key must be a non-empty string");
    }
    if (this.#map.has(key)) {
      this.#map.delete(key); // Refresh recency
    } else if (this.#map.size >= this.#maxEntries) {
      const oldestKey = this.#map.keys().next().value;
      this.#map.delete(oldestKey); // Evict oldest entry
    }
    this.#map.set(key, value);
  }

  get(key) {
    if (!this.#map.has(key)) return undefined;
    const val = this.#map.get(key);
    this.#map.delete(key);
    this.#map.set(key, val);
    return val;
  }

  get size() {
    return this.#map.size;
  }
}

async function fetchUserProfile(userId) {
  if (typeof userId !== "string" || userId.trim().length === 0) {
    throw new TypeError("userId must be a non-empty string");
  }
  return { id: userId.trim(), status: "ok" };
}

const cache = new BoundedCache(2);
cache.set("u1", { name: "Ava" });
cache.set("u2", { name: "Ben" });
cache.get("u1"); // Refresh u1 so u2 becomes oldest
cache.set("u3", { name: "Cara" }); // Evicts u2

console.log("Cache size:", cache.size, "| u2 evicted?", cache.get("u2") === undefined);

<TopicSection id="m01-p4-sec-e" letter="E" title="Step-by-Step Walkthrough">

Trace every step of **`runEventLoopSimulation`** in **Example 3**:

1. **Synchronous Phase:** `rt.sync("start")` logs `"sync:start"`, `rt.setTimeout0(...)` queues `macro-1` into `macrotasks`, `rt.queueMicrotask(...)` queues `micro-1` into `microtasks`, and `rt.sync("end")` logs `"sync:end"`.
2. **First Microtask Drain:** Before touching `macrotasks`, `drainMicrotasks()` runs `micro-1` (logging `"sync:micro-1"`), which schedules `micro-chained`. Because the microtask queue drains until empty, `micro-chained` runs immediately next!
3. **Macrotask Turn 1:** Now that `microtasks` is empty, the Event Loop pops `macro-1` (`"sync:macro-1"`), which schedules `micro-inside-macro`.
4. **Post-Macrotask Drain:** Immediately after `macro-1` finishes, `drainMicrotasks()` runs `micro-inside-macro` before any subsequent macrotask or render.

<TopicSection id="m01-p4-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: React Stale Closures in Timers & Event Listeners

**Problem:** A React component registers `setInterval(() => setCount(count + 1), 1000)` on mount (`[]` dependencies). Because the closure captured `count = 0` from the initial render's Lexical Environment, every tick resets `count` to `0 + 1 = 1`.

**Production Solution:** Use functional state updates (`setCount((prev) => prev + 1)`) or `useRef` for mutable latest values, and always return a cleanup function (`() => clearInterval(id)`) so unmounted components do not leak closures.

#### Scenario 2: Fan-Out API Calls with `Promise.allSettled` & Bounded Concurrency

**Problem:** A Node.js aggregator calls 3 downstream services sequentially (`await a(); await b(); await c();`), tripling latency (`300ms -> 900ms`), or uses `Promise.all()` which aborts all results if one optional recommendation service fails.

**Production Solution:** Run independent I/O concurrently with `Promise.allSettled([a(), b(), c()])`, attach `AbortSignal.timeout(ms)` so hung sockets do not pin closures, and handle each `{ status: "fulfilled" | "rejected" }` explicitly.

</TopicSection>

<TopicSection id="m01-p4-sec-g" letter="G" title="Common Mistakes">

- **Using `var` in loops with async callbacks:** All callbacks share one function-scoped `var` binding instead of per-iteration `let` bindings.
- **Detaching class methods (`onClick={service.save}`):** Loses the `service.` call-site receiver, turning `this` into `undefined` in strict mode.
- **Sequential `await` inside `for` loops when calls are independent:** Creates unnecessary latency waterfalls instead of concurrent `Promise.all` / `Promise.allSettled`.
- **Forgetting `.catch()` / `try-catch` on Promises or `async` functions:** Triggers `UnhandledPromiseRejection` crashes in Node.js.
- **Recursive `queueMicrotask` / `Promise.then` loops:** Starves I/O, timers, and UI rendering completely.
- **Unbounded global `Map`/`Set` caches or forgotten event listeners:** Causes objects to survive into Old Generation and leak memory until OOM.

</TopicSection>

<TopicSection id="m01-p4-sec-h" letter="H" title="Best Practices">

- **Use `const`/`let` (never `var`)** and keep closures small so they do not accidentally retain large unused buffers.
- **Use arrow functions for callbacks inside methods** and `.bind(this)` (or arrow fields) when passing methods as event handlers.
- **Prefer `async`/`await` with `try/catch/finally`** and `Promise.all` / `Promise.allSettled` for concurrent independent I/O.
- **Clean up timers, subscriptions, and `AbortController`s** in `finally` blocks or React `useEffect` cleanup callbacks.
- **Bound all long-lived caches** (LRU / TTL / `WeakMap`) so server RSS memory stays flat under sustained traffic.

</TopicSection>

<TopicSection id="m01-p4-sec-i" letter="I" title="Performance & Scalability">

- **Young-Gen Scavenge vs. Old-Gen Mark-Sweep-Compact:** Short-lived request objects die quickly in V8's fast Young Generation; retaining objects across requests promotes them to Old Generation, causing heavier GC pauses.
- **Avoid Microtask Floods & Long Sync Tasks:** Any synchronous JS loop taking >50ms blocks browser frame rendering and Node.js I/O polling. Chunk CPU work with macrotasks (`setTimeout(..., 0)`) or offload to Worker Threads.
- **Shallow Prototype Chains:** Deep `Object.create` chains slow down property misses; keep inheritance shallow (1–2 levels).

</TopicSection>

<TopicSection id="m01-p4-sec-j" letter="J" title="Security Considerations">

- **Prototype Chain Pollution (`Object.prototype`):** Mutating `Object.prototype` (e.g., via unsafe merge of `__proto__`) affects every object delegating to `Object.prototype` across the process. Use `Map`, `Object.create(null)`, and `Object.hasOwn`.
- **Unhandled Rejections & Error Leakage:** Uncaught async rejections can crash Node.js processes (DoS) or leak internal stack traces/tokens if passed directly to HTTP responses.
- **Closure Secret Retention & Memory Exhaustion:** Never keep unbounded per-request buffers or raw credentials inside long-lived closures or un-evicted caches.

</TopicSection>

<TopicSection id="m01-p4-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. `var` vs. `let` vs. `const` & Hoisting Behavior

| Keyword | Scope | Hoisting & Initial Value | Redeclaration | Reassignment |
| --- | --- | --- | --- | --- |
| `var` | Function / Global | Hoisted, initialized to `undefined` | Allowed | Allowed |
| `let` | Block (`{ ... }`) | Hoisted into TDZ (`ReferenceError`) | Forbidden (`SyntaxError`) | Allowed |
| `const` | Block (`{ ... }`) | Hoisted into TDZ (`ReferenceError`) | Forbidden (`SyntaxError`) | Forbidden (`TypeError`) |

#### 2. Promise Combinators Comparison

| Combinator | Resolves When | Rejects When | Best Use Case |
| --- | --- | --- | --- |
| `Promise.all(list)` | **All** promises fulfill | **First** promise rejects (fail-fast) | Required parallel dependencies (DB + auth) |
| `Promise.allSettled(list)` | **All** promises settle (never rejects) | Never | Partial-success fan-outs, batch notifications |
| `Promise.race(list)` | **First** promise settles (fulfill or reject) | **First** settled is a rejection | Request timeouts (`fetch` vs `timeoutReject`) |
| `Promise.any(list)` | **First** promise fulfills | **All** reject (`AggregateError`) | Multi-mirror fallback requests |

#### 3. Microtasks vs. Macrotasks

| Queue | Examples | Execution Timing | Starvation Risk |
| --- | --- | --- | --- |
| **Microtask Queue** | `Promise.then`, `await`, `queueMicrotask` | Drained **100%** after every stack & macrotask | **High** (recursive microtasks freeze I/O & UI) |
| **Macrotask Queue** | `setTimeout`, `setInterval`, I/O, UI events | **1** task per Event Loop turn | Low (yields between turns) |

</TopicSection>

<TopicSection id="m01-p4-sec-l" letter="L" title="Tips to Remember (Mnemonics & Mental Models)">

- **Event Loop Order:** *"Sync first, drain ALL Micros, then ONE Macro, then drain ALL Micros."*
- **`this` Binding Priority:** *"`new` > explicit (`call`/`apply`/`bind`) > implicit (`obj.fn()`) > default (`undefined` in strict mode); arrows ignore all 4 and use lexical `this`."*
- **Closure Mental Model:** *"A closure is a backpack of live variable references carried by the inner function."*
- **GC Rule:** *"Reachability, not reference count—isolated cycles are swept automatically; accidental global/cache roots leak."*

</TopicSection>

<TopicSection id="m01-p4-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Scope, Hoisting & Closures:** JS uses lexical scope; `var` initializes to `undefined` while `let`/`const` enter the TDZ. Closures preserve live outer bindings on the heap—watch for `var` loop traps and stale React closures.
- **Prototypes & `this`:** Objects delegate up `[[Prototype]]`; regular functions bind `this` at the call site (`new` &gt; `.call/.bind` &gt; `obj.fn()` &gt; `undefined`), whereas arrow functions capture `this` lexically.
- **Async & Event Loop:** Synchronous stack runs first, then **all** microtasks (`Promise.then`, `await`, `queueMicrotask`) drain before **one** macrotask (`setTimeout`, I/O).
- **Memory & GC:** V8 Mark-and-Sweep collects unreachable cycles automatically; prevent leaks by bounding caches, using `WeakMap`/`WeakSet`, and cleaning up timers/listeners in `finally`.

</TopicSection>
