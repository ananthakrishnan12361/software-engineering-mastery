<TopicSection id="m01-p2-sec-a" letter="A" title="Topic Introduction">

#### What is this?

Once you know how single variables and functions work, real software needs ways to group related data and behavior together. <GlossaryTerm definition="An unordered collection of key-value pairs (properties and methods) stored on the heap.">Objects</GlossaryTerm> model structured entities (a user, an invoice, an HTTP request), while <GlossaryTerm definition="An ordered, zero-indexed list structure optimized for sequential storage and iteration.">Arrays</GlossaryTerm> model ordered collections of items.

<GlossaryTerm definition="A blueprint syntax in ES2015+ for creating objects with shared methods, constructors, and optional private fields.">Classes</GlossaryTerm> and <GlossaryTerm definition="Object-Oriented Programming: a paradigm organizing software around objects that bundle state and behavior using Encapsulation, Inheritance, Polymorphism, and Abstraction.">OOP</GlossaryTerm> give teams a structured way to protect internal invariants (**Encapsulation**), hide noisy implementation details (**Abstraction**), share contracts (**Inheritance**), and swap behaviors cleanly (**Polymorphism**). **SOLID fundamentals** are five practical design guidelines that keep object-oriented codebases modular, testable, and resilient to change.

#### Why does it exist & what problem does it solve?

Without objects, arrays, and modular boundaries, large codebases turn into hundreds of loosely related global variables and giant `if/else` chains where any change breaks unrelated features:

- **Objects & Arrays** replace dozens of disconnected variables (`user1Name`, `user1Email`) with cohesive data structures.
- **Encapsulation & Abstraction** prevent external callers from corrupting internal state (for example, setting `invoice.total = -500` directly).
- **Polymorphism & SOLID** let you add new payment providers, storage backends, or notification channels without rewriting tested core workflows.

#### Where is it used in real-world software?

Every production layer uses these concepts daily: React props and Redux state are immutable object/array trees; Express request/response objects and middleware chains use object composition; ORMs (Prisma, TypeORM), domain models, and backend service layers rely on classes, interfaces, dependency inversion, and polymorphism to keep business logic decoupled from databases and third-party APIs.

<TopicAnchor id="m01-p2-topic-objects" />

#### 1. Objects: Key-Value Records, Prototypes & Property Descriptors

An **object** in JavaScript is a mutable dictionary mapping string (or `Symbol`) keys to values. Values can be data (**properties**) or functions (**methods**). Every plain `{}` delegates missing key lookups to `Object.prototype`, so checking membership with `"toString" in {}` returns `true`. Always use `Object.hasOwn(obj, key)` (ES2022) to check own properties safely—even on `Object.create(null)` dictionaries that have no prototype.

Underneath every property sits a <GlossaryTerm definition="Metadata object describing a property's value/getter/setter and behavioral flags: writable, enumerable, and configurable.">Property Descriptor</GlossaryTerm> with four flags: `value`, `writable` (can be reassigned), `enumerable` (appears in `Object.keys` / `for..in` / `JSON.stringify`), and `configurable` (can be deleted or reconfigured). Calling `Object.freeze(obj)` sets `writable: false` and `configurable: false` on own properties—though only **shallowly**! Spread syntax `{ ...user }` is also shallow: nested objects like `user.address` remain shared by reference unless cloned deeply with `structuredClone(user)`.

For dynamic key-value collections, prefer `Map` and `Set` over plain `{}`—and when attaching metadata or visited-state to objects without preventing garbage collection, use **`WeakMap`** and **`WeakSet`**. Unlike `Map`/`Set`, weak collections hold **weak references** to object keys (so entries are automatically reclaimed when the key object becomes unreachable elsewhere) and are intentionally non-enumerable (no `.size`, `.keys()`, or `for..of` iteration).

<TopicAnchor id="m01-p2-topic-arrays" />

#### 2. Arrays: Ordered Lists, Mutation Traps & Non-Mutating Methods

An **array** is a specialized object optimized for non-negative integer indices `0, 1, 2, ...` and an auto-updating `.length` property. Appending or removing at the tail (`.push()`, `.pop()`) is amortized `O(1)`, whereas inserting or removing at index `0` (`.unshift()`, `.shift()`) shifts every remaining element (`O(n)`).

Pay close attention to **mutating vs. non-mutating** array methods. Classic methods like `.push()`, `.pop()`, `.splice()`, `.sort()`, and `.reverse()` mutate the array in place—which causes subtle bugs when sorting React props or shared state. Modern ES2023 non-mutating counterparts—`.toSorted()`, `.toReversed()`, `.toSpliced()`, and `.with(index, value)`—alongside `.map()`, `.filter()`, and `.slice()` always return a **new** array and leave the original untouched.

<TopicAnchor id="m01-p2-topic-classes" />

#### 3. Classes: Blueprints, Constructors, Accessors & Static Members

Introduced in ES2015, a **`class`** packages a `constructor` (which initializes each instance when invoked with `new`), shared instance methods (stored once on `ClassName.prototype`), `get`/`set` computed accessors, and `static` utility/factory methods attached directly to the class constructor itself (e.g., `User.fromDTO(dto)`).

Unlike legacy constructor functions, ES2015+ classes enforce critical runtime safety rules: the class body always runs in **strict mode**, methods are non-enumerable by default, and calling a class without `new` throws a `TypeError` immediately. Use `instanceof` to test whether an object's prototype chain includes a class constructor.

<TopicAnchor id="m01-p2-topic-oop" />

#### 4. OOP: Modeling Domains Around Collaborating Objects

**Object-Oriented Programming (OOP)** structures a codebase around domain objects that combine relevant state with the operations allowed on that state, rather than scattering raw data structures and unrelated helper functions across files. Each object acts as a boundary responsible for its own consistency.

OOP rests on four complementary pillars—**Encapsulation**, **Abstraction**, **Inheritance**, and **Polymorphism** (**A-P-I-E**). In modern JavaScript and TypeScript, engineers combine OOP boundaries for stateful domain entities (`LedgerAccount`, `Order`, `RateLimiter`) with functional immutability for data transformations.

<TopicAnchor id="m01-p2-topic-encapsulation" />

#### 5. Encapsulation: Protecting Invariants with `#private` State

<GlossaryTerm definition="Bundling state and behavior together while restricting direct external mutation so internal invariants cannot be bypassed.">Encapsulation</GlossaryTerm> ensures callers can only change an object's state through validated methods rather than corrupting fields directly (such as setting `account.balance = -500`). Naming conventions like `_balance` only ask nicely—external code can still read, mutate, and serialize `_balance`.

In ES2022+, prefixing a class field or method with `#` (e.g., `#balanceCents`) creates true runtime encapsulation: referencing `account.#balanceCents` outside the declaring class fails at parse time with a `SyntaxError`, and `#private` slots never leak into `Object.keys()`, `for..in`, or `JSON.stringify()`.

<TopicAnchor id="m01-p2-topic-abstraction" />

#### 6. Abstraction: Minimal Public Contracts Over Complex Internals

<GlossaryTerm definition="Exposing only a clean, minimal public interface while hiding complex internal workflows, protocols, or storage details.">Abstraction</GlossaryTerm> separates *what* a component does from *how* it does it. When `CheckoutService` calls `gateway.charge(amountCents)`, it only depends on a simple input/output contract (`charge(cents) -> Receipt`), hiding HTTP retries, HMAC signing, webhook verification, and vendor SDK quirks behind that boundary.

Good abstraction shrinks cognitive load and localizes change: if you swap payment providers or migrate from SMTP to AWS SES, callers depending only on the narrow abstraction require zero code changes.

<TopicAnchor id="m01-p2-topic-inheritance" />

#### 7. Inheritance: Shallow `extends` Taxonomies vs. Composition

<GlossaryTerm definition="Defining a specialized child class via extends that reuses and refines a parent class's contract while initializing parent state with super().">Inheritance</GlossaryTerm> creates a subtype relationship (`class RateLimitError extends AppError`) where the child class inherits prototype methods, initializes parent state via `super(...)`, and can override behavior while delegating back with `super.method()`. Note that a child class does **not** inherit direct access to a parent's `#private` fields—it must use the parent's public API.

Reserve inheritance for shallow, genuine *"is-a"* hierarchies (such as typed `Error` subclasses). Deep `extends` chains create tight coupling (**Fragile Base Class** problem); for sharing capabilities across services, prefer **composition** (*"has-a"*).

<TopicAnchor id="m01-p2-topic-polymorphism" />

#### 8. Polymorphism: Uniform Dispatch Across Interchangeable Types

<GlossaryTerm definition="Allowing different classes or objects implementing the same method contract to be used interchangeably through a shared caller interface.">Polymorphism</GlossaryTerm> (*"many forms"*) lets a single piece of orchestration code work uniformly across multiple implementations without `if (provider === "stripe") ... else if (provider === "paypal")` branches. Both `StripeGateway` and `MockGateway` implement `.charge(cents)` and return a consistent receipt shape.

Because JavaScript is dynamically typed, polymorphism works both via shared parent classes (`extends`) and via structural **duck typing** (any object exposing the expected method signature). To stay reliable, every polymorphic implementation must honor the same input, output, and error contract.

<TopicAnchor id="m01-p2-topic-solid" />

#### 9. SOLID Fundamentals: Five Guidelines for Modular Change

Coined and popularized by Robert C. Martin, <GlossaryTerm definition="Five object-oriented design principles (SRP, OCP, LSP, ISP, DIP) that keep software modular, extensible, and testable.">SOLID</GlossaryTerm> provides five practical guardrails against rigid, tightly coupled code:

1. **S — Single Responsibility Principle (SRP):** A class or module should serve one cohesive actor/reason to change (keep tax math separate from PDF rendering and SQL persistence).
2. **O — Open/Closed Principle (OCP):** Open for extension, closed for modification—add new variants (discount rules, notification channels) by registering a new class/strategy rather than editing core `switch` statements.
3. **L — <GlossaryTerm definition="Subtypes or interchangeable implementations must preserve the caller's expectations around inputs, return shapes, and error behavior.">Liskov Substitution Principle (LSP)</GlossaryTerm>:** Any subtype or strategy implementation must honor the base contract (never throwing unexpected error types or returning incompatible shapes).
4. **I — Interface Segregation Principle (ISP):** Prefer small, focused contracts (`Readable`, `Chargeable`) over bloated interfaces so callers and test mocks only implement what they actually use.
5. **D — <GlossaryTerm definition="High-level business policy should depend on minimal abstractions/interfaces injected from outside rather than concrete low-level SDKs.">Dependency Inversion Principle (DIP)</GlossaryTerm>:** High-level policy (`CheckoutService`) depends on an abstraction (`PaymentGateway`), and concrete adapters (`StripeGateway`) are injected via constructor parameters rather than imported and instantiated inside core logic.

</TopicSection>

#### 1. V8 Hidden Classes (Maps) & Inline Caches for Objects

In static languages like C++ or Java, the compiler knows the exact byte offset of `user.email` at compile time. In JavaScript, objects can gain or lose keys at runtime. To avoid slow hash-table lookups on every property access, V8 builds internal <GlossaryTerm definition="Internal V8 metadata (also called Shapes or Maps) describing an object's property names and byte offsets.">Hidden Classes</GlossaryTerm>:

- When you create `{ id: 1, name: "A" }`, V8 creates Hidden Class `C0` &rarr; `C1 (id @ offset 0)` &rarr; `C2 (name @ offset 1)`.
- If another object initializes keys in the **same order** (`{ id: 2, name: "B" }`), it shares `C2`. V8's **Inline Cache (IC)** remembers `C2` and reads `obj.name` in one pointer offset check.
- If a third object initializes keys in a **different order** (`{ name: "C", id: 3 }`) or dynamically adds `obj.role = "admin"` later, it branches into a different Hidden Class tree, turning fast monomorphic reads into slower polymorphic or dictionary lookups.

#### 2. V8 Array Elements Kinds (Packed vs. Holey Transitions)

Standard JS arrays are objects under the hood, but V8 optimizes numeric and dense arrays into contiguous C-style backing stores categorized by **Elements Kinds** *(V8 implementation detail, not an ECMA-262 rule)*:

- `PACKED_SMI_ELEMENTS`: Dense array of small 31-bit integers (`[1, 2, 3]`) — fastest, unboxed.
- `PACKED_DOUBLE_ELEMENTS`: Adding a float (`arr.push(1.5)`) downgrades the backing store to unboxed 64-bit floats.
- `PACKED_ELEMENTS`: Adding a string or object (`arr.push("ok")`) downgrades to generic tagged pointers.
- `HOLEY_*`: Leaving gaps (`[1, , 3]`, `arr[500] = 9`, or `delete arr[1]`) marks the array **holey**. Whenever you read a hole, V8 must check `Array.prototype` up the prototype chain in case someone defined a property at that index!
- **Crucial rule:** Elements Kind transitions are strictly **one-way** (specific &rarr; generic, packed &rarr; holey). Even if you later remove the string or fill the gap, V8 never upgrades that array back.

#### 3. How ES2015+ Classes & ES2022 `#private` Fields Work

Under the hood, an ES2015 `class` still creates a constructor function and places instance methods on `ClassName.prototype` (covered deeply in M01-P4). However, `class` adds critical runtime safeguards over old constructor functions:

- Class bodies run in **strict mode** automatically and cannot be called without `new` (throws `TypeError`).
- **ES2022 `#private` fields** are stored in internal per-instance private slots keyed by the class's lexical brand—not as string keys on the object! They do not appear in `Object.keys()`, `JSON.stringify()`, or `for..in`, and subclasses cannot access a parent's `#private` fields directly.

#### 4. Dependency Inversion & Composition Flow

Instead of high-level business logic instantiating concrete SDKs directly, Dependency Inversion reverses the compile-time/import arrow: both high-level policy and low-level adapters depend on a shared minimal contract.

#### Example 3: Classes, `#private` Encapsulation, Polymorphism & SOLID in Action

<CodeBlock
  lang="javascript"
  runnable
  code={`// Encapsulation + Abstraction: LedgerAccount enforces non-negative safe-integer invariants with #private fields
class LedgerAccount {
  #balanceCents;
  #entries = [];

  constructor(owner, initialCents = 0) {
    if (typeof owner !== "string" || owner.trim().length === 0) {
      throw new TypeError("owner must be a non-empty string");
    }
    if (!Number.isSafeInteger(initialCents) || initialCents < 0) {
      throw new RangeError("initialCents must be a non-negative safe integer");
    }
    this.owner = owner.trim();
    this.#balanceCents = initialCents;
  }

  deposit(cents) {
    if (!Number.isSafeInteger(cents) || cents <= 0) {
      throw new RangeError("Deposit must be positive integer cents");
    }
    if (!Number.isSafeInteger(this.#balanceCents + cents)) {
      throw new RangeError("Balance would exceed Number.MAX_SAFE_INTEGER");
    }
    this.#balanceCents += cents;
    this.#entries.push({ type: "CREDIT", cents });
  }

  get balanceCents() {
    return this.#balanceCents;
  }

  toJSON() {
    return { owner: this.owner, balanceCents: this.#balanceCents, count: this.#entries.length };
  }
}

// Polymorphism + OCP + DIP: CheckoutService depends only on a charge(cents) strategy
class StripeGateway {
  charge(cents) {
    return { provider: "stripe", ok: true, chargedCents: cents };
  }
}

class MockGateway {
  charge(cents) {
    return { provider: "mock", ok: true, chargedCents: cents };
  }
}

class CheckoutService {
  #gateway;
  constructor(gateway) {
    if (!gateway || typeof gateway.charge !== "function") {
      throw new TypeError("gateway must implement charge(cents)");
    }
    this.#gateway = gateway; // Dependency Inversion: injected abstraction
  }
  pay(account, amountCents) {
    if (!(account instanceof LedgerAccount)) {
      throw new TypeError("account must be a LedgerAccount");
    }
    if (!Number.isSafeInteger(amountCents) || amountCents <= 0) {
      throw new RangeError("amountCents must be a positive safe integer");
    }
    if (!Number.isSafeInteger(account.balanceCents + amountCents)) {
      throw new RangeError("Deposit would exceed Number.MAX_SAFE_INTEGER");
    }
    const receipt = this.#gateway.charge(amountCents);
    if (receipt?.ok) account.deposit(amountCents);
    return receipt;
  }
}

const acct = new LedgerAccount("Maya", 500);
const checkout = new CheckoutService(new MockGateway());
console.log("Receipt:", checkout.pay(acct, 1200));
console.log("JSON view (no #private leak):", JSON.stringify(acct));`}

Trace every step of **Example 3** (`LedgerAccount` + `CheckoutService`):

1. **Instantiation (`new LedgerAccount("Maya", 500)`):** V8 allocates a `LedgerAccount` instance on the heap, runs `constructor`, validates non-empty `owner` and non-negative safe-integer `initialCents`, sets public `this.owner = "Maya"`, and initializes private internal slots `#balanceCents = 500` and `#entries = []`.

Then it calls `.charge(1200)` uniformly across `StripeGateway`, `MockGateway`, or any compliant adapter (**Polymorphism** & **OCP**).
5. **Safe Serialization (`JSON.stringify(acct)`):** Because `toJSON()` is defined explicitly and `#private` slots are hidden from enumeration, only the safe public summary `{ owner, balanceCents, count }` is serialized.

<TopicSection id="m01-p2-sec-f" letter="F" title="Real-World Use Cases">

#### Scenario 1: Multi-Gateway Billing Service (Abstraction, Polymorphism, OCP & DIP)

**Problem:** An e-commerce backend starts with Stripe inside `processOrder()`. Six months later, adding PayPal and local bank transfers turns `processOrder()` into a 400-line `switch` statement where testing requires hitting real Stripe sandboxes.

**Production Solution:** Extract a minimal `PaymentProvider` interface (`charge`, `refund`) and inject implementations via a `Map<string, PaymentProvider>` registry. Core `OrderService` logic stays unchanged when adding providers (**OCP**), and unit tests inject an in-memory double (**DIP**).

#### Scenario 2: Immutable State Trees in React & Node.js Config Mergers

**Problem:** A React dashboard filters and sorts a user's `orders` prop using `orders.sort(...)`. Because `.sort()` mutates in place, React's shallow reference check (`prevOrders === nextOrders`) thinks nothing changed, skipping re-renders while silently scrambling parent state.

**Production Solution:** Use non-mutating transformations (`orders.toSorted(...)` or `[...orders].sort(...)`) and immutable object updates (`{ ...state, user: { ...state.user, name } }`) so references change cleanly along modified paths.

</TopicSection>

<TopicSection id="m01-p2-sec-g" letter="G" title="Common Mistakes">

- **Mutating arrays with `.sort()`, `.reverse()`, or `.splice()`** on props/state or omitting numeric comparators (`[10, 2].sort()` sorting as strings).
- **Using `delete arr[index]`**: Leaves sparse empty slots (`HOLEY_ELEMENTS`) while keeping `arr.length` unchanged. Use `.splice()` or `.filter()` instead.
- **Confusing shallow spread (`{ ...obj }`) with deep cloning**: Mutating nested properties still mutates the original object.
- **Overusing deep inheritance (`class Manager extends Employee extends Person extends Entity`)**: Tightly couples subclasses to parent internals (Fragile Base Class problem) and often violates **Liskov Substitution** (e.g., `Square extends Rectangle` breaking independent `setWidth`/`setHeight` assumptions).
- **Using plain `{}` as a dynamic dictionary for arbitrary keys**: User-supplied keys like `"constructor"` or `"toString"` collide with `Object.prototype` methods. Prefer `new Map()`.
- **Treating SOLID as a mandate for excessive boilerplate**: Wrapping a 10-line helper in five interfaces and abstract factories violates YAGNI.

</TopicSection>

<TopicSection id="m01-p2-sec-h" letter="H" title="Best Practices">

- **Favor composition ("has-a") over inheritance ("is-a"):** Compose small behaviors (`retryPolicy`, `logger`, `gateway`) via constructor injection instead of multi-level `extends` chains.
- **Use `#private` class fields for genuine invariants** (account balances, state machines, secret clients) and expose clean getters/methods.
- **Use `Object.hasOwn(obj, key)`** for own-property checks and **`Map` / `Set`** for dynamic collections with frequent additions/deletions.
- **Keep object shapes consistent** (initialize all fields in the same order, set optional fields to `null`/`undefined` upfront rather than adding them conditionally later).
- **Prefer non-mutating array operations** (`map`, `filter`, `toSorted`, `toReversed`, `toSpliced`) at application state boundaries.
- **Apply SOLID where change happens:** Split responsibilities when modules serve different actors (**SRP**), and introduce interfaces (**OCP/DIP**) at external I/O or multi-variant boundaries.

</TopicSection>

<TopicSection id="m01-p2-sec-i" letter="I" title="Performance & Scalability">

- **`Object` vs. `Map` at Scale:** Plain objects with static shapes optimize well for fixed-schema records (V8 Hidden Classes). `Map` is optimized for dynamic dictionaries with frequent key insertions/deletions and avoids prototype chain checks.
- **Preventing Memory Leaks with `WeakMap` / `WeakSet`:** Storing request or DOM-node metadata in a global `Map` or `Set` keeps strong references alive forever unless manually deleted. `WeakMap` and `WeakSet` allow the Garbage Collector to reclaim entries automatically once the key object is no longer referenced elsewhere.
- **Array Operation Complexity:** `.push()` and `.pop()` at the tail are amortized `O(1)`. `.shift()` and `.unshift()` at index `0` re-index every element (`O(n)`), becoming a bottleneck on queues of 50,000+ items (use a ring buffer or head-index pointer instead).
- **Keep Hot Arrays Dense & Homogeneous:** Avoid mixing integers, floats, and strings or leaving sparse holes in tight numeric loops so V8 stays in `PACKED_SMI` / `PACKED_DOUBLE` storage.
- **`structuredClone` Cost:** Deep cloning huge nested payloads on every request allocates significant heap memory. Clone only at untrusted boundaries or use structural sharing for incremental updates.

</TopicSection>

<TopicSection id="m01-p2-sec-j" letter="J" title="Security Considerations">

- **<GlossaryTerm definition="An injection flaw where untrusted __proto__, constructor, or prototype keys in recursive object merges mutate Object.prototype globally.">Prototype Pollution</GlossaryTerm> (`__proto__`, `constructor`, `prototype`):** Never merge untrusted objects recursively without blocking `"__proto__"`, `"constructor"`, and `"prototype"` keys and checking `Object.hasOwn(src, key)`. Polluting `Object.prototype` affects every object in a Node.js server!
- **Dynamic Property Lookup Injection:** Avoid `handlers[userInput]()` on a plain object—if `userInput === "toString"`, it invokes `Object.prototype.toString` or throws unexpectedly. Use `handlersMap.get(userInput)` with a `Map`.
- **Accidental Secret Leakage in Serialization:** Plain public properties like `user._passwordHash` are included by `JSON.stringify(user)`. Keep sensitive fields `#private` or return explicit DTOs / `toJSON()` outputs.
- **Freezing Shared Configuration:** Call `Object.freeze()` (or recursive deep freeze) on startup configuration objects so buggy plugins cannot mutate shared runtime settings.

</TopicSection>

<TopicSection id="m01-p2-sec-k" letter="K" title="Comparisons & Decision Tables">

#### 1. Plain `Object` vs. `Map` vs. `Set` vs. `WeakMap` / `WeakSet`

| Criterion | Plain `Object` | `Map` | `Set` | `WeakMap` / `WeakSet` |
| --- | --- | --- | --- | --- |
| Key / element types | `string` and `Symbol` only | Any value (objects, functions, primitives) | Unique values of any type | Objects (and non-registered `Symbol`s) only |
| Prototype collisions | Inherits `Object.prototype` (use `Object.hasOwn`) | None (clean key space) | None | None |
| GC & Memory behavior | Strong references (manual delete) | Strong references (manual `.delete()`) | Strong references (manual `.delete()`) | **Weak** references (auto-reclaimed by GC) |
| Size & iteration | `Object.keys(o).length` (`O(n)`) | `map.size` (`O(1)`), iterable | `set.size` (`O(1)`), iterable | Not enumerable (no `.size`, no `for..of`) |
| Best fit | Fixed-shape records, DTOs, JSON payloads | Dynamic dictionaries, caches, frequent add/delete | Deduplication, `O(1)` membership tests | Per-object private metadata, visited-object tracking |

#### 2. Shallow vs. Deep Copying Strategies

| Strategy | Depth | Circular Refs | Special Types (`Date`, `Map`, `Set`, `BigInt`, `fn`) | Cost & Best Fit |
| --- | --- | --- | --- | --- |
| `{ ...obj }`, `Object.assign()`, `[...arr]` | **Shallow** (top-level only) | Preserves top-level refs | Copies references as-is | `O(k)` fast; React/Redux structural sharing |
| `JSON.parse(JSON.stringify(x))` | Deep (JSON subset) | **Throws** `TypeError` | Drops `undefined`/`fn`/`Symbol`; stringifies `Date`; throws on `BigInt` | Slowest & lossy; avoid for rich JS objects |
| `structuredClone(x)` (Node 17+ / modern browsers) | **Deep** | **Supported** | Preserves `Date`, `Map`, `Set`, `RegExp`, `BigInt`; **throws** on `fn`/`Symbol`/DOM | Allocates full deep copy; untrusted/isolated snapshots |
| Structural sharing (`{ ...s, nested: { ...s.nested } }`) | Selective paths | Manual | Preserves everything along unchanged branches | Best balance of immutability & GC efficiency |

#### 3. Composition vs. Inheritance

| Dimension | Composition (*Has-A*) | Inheritance (*Is-A*) |
| --- | --- | --- |
| Coupling | Loose (depends on small public contract) | Tight (coupled to parent internals/lifecycle) |
| Runtime flexibility | Swap behaviors dynamically via constructor/props | Fixed class hierarchy at definition time |
| Multiple capabilities | Combine any number of collaborators cleanly | JS supports single `extends` only |
| Best fit | Services, plugins, UI patterns, retry/auth policies | Shallow taxonomies (e.g., custom `AppError extends Error`) |

#### 4. SOLID Principles Quick Decision Guide

| Principle | Core Question | Warning Sign of Violation |
| --- | --- | --- |
| **S**RP | Does this module change for one reason/actor? | A class mixes SQL queries, pricing math, and HTML formatting |
| **O**CP | Can we add a variant without editing core code? | A 10-branch `switch (provider)` duplicated across files |
| **L**SP | Can any subtype replace the base seamlessly? | Subclass throws `NotImplementedError` or changes return shape |
| **I**SP | Are callers forced to depend on unused methods? | A mock needs 15 dummy methods just to test 1 read call |
| **D**IP | Does domain logic depend on abstractions, not SDKs? | Business logic directly imports `mysql2` or `stripe` |

<TopicSection id="m01-p2-sec-q" letter="Q" title="Summary & Key Takeaways">

- **Objects & Arrays** are heap-allocated reference types: prefer `Object.hasOwn()`, `structuredClone()` for deep isolation, `Map`/`Set` for dynamic keys, and non-mutating array transforms (`toSorted`, `filter`, `map`).
- **V8 Performance Mental Model:** Keep object property initialization orders consistent (Hidden Classes) and keep arrays dense and type-homogeneous (avoiding one-way `HOLEY` downgrades).
- **OOP Pillars (`A-P-I-E`):** Use ES2022 `#private` fields for true encapsulation, clean interfaces for abstraction and polymorphism, and **composition over inheritance** for flexibility.
- **SOLID Pragmatically:** Separate unrelated actors (**SRP**), extend via registries/strategies (**OCP**), keep subtypes contract-compatible (**LSP**), keep interfaces small (**ISP**), and inject low-level dependencies (**DIP**).

</TopicSection>
