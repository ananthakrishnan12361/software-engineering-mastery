# Content Standards — Software Engineering Mastery

## Audience
A working software developer with practical exposure to web development, databases, cloud and AI, who wants stronger fundamentals and senior-level engineering confidence.

## Teaching style
- Use clear, simple English without making the technical content shallow.
- Explain unfamiliar terms before relying on them.
- Move from fundamentals to internals, then to advanced trade-offs.
- Explain why a technique is used, when it is appropriate and when it is not.
- Prefer practical engineering examples over abstract definitions.

## Standard lesson structure
Use the sections that fit the topic:
1. Learning objectives
2. What it is
3. Why it exists / problem it solves
4. Core concepts and terminology
5. Internal working
6. Step-by-step example or flow
7. Code examples with explanation
8. Real-world use cases
9. Performance considerations
10. Security, reliability and operational concerns
11. Alternatives and trade-offs
12. Common mistakes and best practices
13. Interview questions and detailed answers
14. Exercises and challenge tasks
15. Summary and revision points

## Interview question levels
Include a balanced range:
- Basic: definitions and foundational understanding.
- Intermediate: practical implementation and debugging.
- Advanced: internals, performance, failure modes and trade-offs.
- Senior/architect: requirements analysis, architecture decisions, scaling, reliability, cost and operational consequences.

Answers must explain the reasoning, not just state a short conclusion. Add follow-up questions where useful.

## Code quality
- Use realistic, runnable examples where practical.
- State language/runtime/framework assumptions and versions when relevant.
- Explain important lines and expected output.
- Include error handling and security considerations where appropriate.
- Do not present pseudocode as runnable code without labelling it.

## Diagrams and comparisons
Use diagrams for flows and architecture when they improve understanding. Comparison tables should explain decision criteria, not merely list features.

## Accuracy and completeness
- Do not invent facts, benchmark numbers or version-specific behaviour.
- Separate general principles from version-dependent details.
- Avoid filler, repeated explanations and superficial one-paragraph coverage of major topics.
- Never use placeholders for required content.
